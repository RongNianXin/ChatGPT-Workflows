# 任务未闭环却以非空答复提前结束

| 字段 | 当前记录 |
| --- | --- |
| 故障编号 | `TRB-010` |
| 解决状态 | 部分缓解：新 CLI 任务的独立验收与有限续作已实测；现有桌面对话未接入 |
| 工具状态 | 按任务启用的续执行守卫可运行；不保证所有宿主或专业任务适用 |
| 最后核验 | 2026-10-22 |
| 证据边界 | 一次普通用户多部分请求的原始回合、后续人工反馈及独立审查；能确认任务未闭环即进入非空 `final_answer`，不能确定模型、平台、客户端或上游层面的底层根因 |

> 发现答复只写“将要执行”却已结束时，先保留原回合和工具记录，把原任务标为“待补答”；不要把平台 `completed` 当作业务完成，也不要自动重放可能有副作用的动作。

## 一句话现象

用户提出“调研、判断、方案”等多部分请求后，AI 只给出初步结论和下一步承诺，未执行承诺的检索或逐项回答，却以非空最终答复结束。

## 复发形态：在途“调整方向”吞掉原任务

新增证据显示，另一种同类故障发生在任务执行中途：原请求包含多个事项，操作者通过客户端“调整方向”补充一个问题；AI 只处理补充问题并据此结束，既没有回到原执行账，也没有逐项报告原事项。该形态同时包含两层错误：

1. **执行层未闭合**：原事项仍处于未完成或结果未知，却被新输入覆盖。
2. **汇报层不完整**：最终答复只覆盖补充问题，未列出原事项的完成、阻断、取消或未执行状态。

默认规则应把补充、纠正和细化合并进原活跃请求；只有明确指向的取消或替代才局部终止对应项；提问或状态询问处理后必须回到原执行账。客户端按钮的宿主级拦截能力仍待确认，当前修复属于模型侧行为契约和离线回归。

## 当前是否解决

未解决项：现有桌面对话尚未接入自动验收与续作，真实专业业务的闭环效果仍待验证。

本案例尚未整体解决。工作流已补充请求项、承诺动作和阻断状态的收口核账，并增加目标载体消歧规则；仓库质量脚本可检查这些规则是否仍存在。新增的[任务续执行守卫](../../../实用小工具/Codex任务续执行守卫/README.md)已通过真实 CLI 与本机模拟模型的生命周期验证：独立验收失败后，宿主消费续作提示并再次执行。它不接入现有桌面对话，也不能保证最终文字尚未显示，更不能替代专业业务验收。

## 长任务复发：工具未结束与实测证据错绑

后续获准只读核验的执行记录显示，任务曾在长运行工具尚未取得最终状态和产物时收口。再次推进又发现：拿旧版本的对比数据解释当前修复、回放输入未稳定绑定、所谓重复测试改变了输入条件。相关修改随后被来源执行者撤回；反思文字、类型检查及合成测试均不能替代真实输入下的修前修后验收。追加预算后出现实际回放结果，也只能证明执行恢复，不能证明原目标完成。

现有核心规则已经要求授权内持续推进和最终出口核账，本次证据首先支持“规则未落实与证据链不完整”，不能单凭耗时推断是上下文、额度、路由或客户端故障。时间和高资源次数是上限，不要求耗满；目标未达且无有据停止条件时，也不能把一次短答当作整个任务完成。已取得的运行标识应在原任务内继续等待、回读最终状态与产物；只有确认失败或中止后，才判断是否重跑，避免重复消耗预算。

最小预防路径沿用原账：`反馈项 → 修复假设 → 精确版本和输入 → 实测产物 → 逐项验收`。输入绑定应包含原始材料、坐标或参数及实际处理数据的必要指纹；只比较同条件结果，不把随机改变输入称为稳定性复测。预算停止时保留未完及恢复条件，不把预算不足包装为成功。会话评估工具仍不负责持续执行；新的守卫仅供单独启动的新 CLI 任务使用，没有修改来源项目或向来源任务发送消息。

## 按任务启用的程序验收与有限续作

官方 CLI 的 `Stop` 钩子可在回合准备结束时运行程序，并通过 `decision: block` 将验收失败原因加入原回合继续执行。新守卫使用这个入口；AI 的完成声明、平台完成标记与 CLI 退出零都不能单独算验收通过。验收程序须由任务负责人按原授权目标准备并审查，只读、无网络、幂等、限时且不派生子进程；检查入口和必要依赖固定指纹，业务工作树与控制记录分离。此声明和路径约束不是操作系统级安全隔离。

- 只对明确启动的任务注入钩子，不写全局或项目配置，不安装后台服务，不接管桌面现有对话，不退出或重启客户端。
- 未完成且可继续时，宿主在累计时限、续作次数及无进展上限内自动续作。高资源次数仍由原任务约束，守卫的续作次数不能替代或增加该预算。
- 已观察到后台会话或未知工具结果时保留在途；只能等待并回读原调用，不能重跑副作用。未走钩子的后台活动仍须由任务检查器登记，不能宣称覆盖全部进程。
- 等待人工、权限拒绝、取消、未知验收、异常退出或预算到限时停止，保留未验收。唯一登记阻止同工作项换运行目录重置预算；不自动恢复旧 CLI。
- 退出时再次核对取消、钩子异常、在途与有效验收。早先通过后又发生工具活动或新的结束事件，须重新验收，不能用旧成功遮盖后续变化。

自动测试自行生成夹具，不要求操作者提供样本。真实 CLI 的对照实验中，无守卫时错误答案也会以零退出；启用后首次失败触发第二次模型请求，正确答案通过独立算术检查，业务命令执行零次。另有后台会话、未知/拒绝、脚本变化、重复启动、无进展、取消、异常与已有用户层钩子合并回归。这证明本机 CLI 的控制链可用，不证明真实模型专业能力、来源业务修复或桌面对话防复发效果。先前真实工具执行试验被本机策略拒绝，未绕过策略，业务工具全链仍未验证。

官方来源：[Hooks](https://developers.openai.com/codex/hooks)、[非交互模式](https://developers.openai.com/codex/noninteractive)。实现、停止入口与证据边界见工具说明；只在可形成独立验收标准的新授权任务中采用，不向运行中任务追装。

## 已确认事实、合理推断与待确认项

### 已确认事实

1. 用户明确要求依次回答是否需要做、是否建议做和怎样做，并补充了本地/远端、联网、分支与 PR、术语、竞品和实现路径等问题。
2. AI 返回了四条初步判断，并声明将使用工具核对竞品、Git/GitHub 能力和项目现状。
3. 该回合没有对应 Skill 读取、检索或其他工具调用，也没有覆盖上述多数问题，却以非空 `final_answer` 结束。
4. 因为输出非空，本案不是空输出；TRB-006 的空回合与漏回执仍是跨任务通信故障，不与本案合并。
5. 后续整改中，用户用人名描述接收对象但没有明确平台，AI 未先消歧就默认使用飞书，产生了无效的认证和联系人只读查询；权限不足后未发送消息，也未造成远端代码平台写入。

### 合理推断

- 直接行为缺口是没有把请求项和已承诺动作维护到终态便结束；现有多项请求和最终出口规则没有在该回合得到落实。
- 后续目标误判与主故障属于两个故障面。共同的上层缺口是意图没有转成可核验的动作和目标，但两者的检测与修复不同，不能共享根因。

### 待确认项

- 提前结束源于模型决策、宿主调度、客户端处理、上游输出还是共同作用。
- 同类行为在其他模型、版本和输入结构中的复现率。
- 现有桌面宿主是否支持与已实测 CLI 等价的结束检查，以及如何安全接入；不能从 CLI 成功推定桌面可用。

## 排查过程

1. 回读原始用户请求、最终答复和同回合工具记录，确认输出非空但承诺动作未执行。
2. 将用户事项逐项对照，确认竞品核验、联网方式、关系模型、术语和实现路径没有完成，也没有被标为阻断或待补。
3. 检查 TRB-006：其证据链围绕跨任务投递、入站、生成、回传和确认，不适合作为本案主记录。
4. 检查现有执行入口：核心规则能提供模型侧核账；仓库质量脚本只能做静态契约检查；会话交接评估脚本可作为 JSONL 事后检测基础，但当前不能判断多项语义是否完整覆盖。

## 解决或规避步骤

1. 对显式多部分请求，或本轮主动承诺工具/后续动作的请求，维护短清单：`请求项｜需要的证据或动作｜完成 / 阻断 / 取消`。
2. 进入最终答复前，对照实际工具结果和证据。已获授权且无阻断的承诺动作未执行，或仍有非终态请求项时，不得把本轮写成完成。
3. 确需暂停时明确写出未完成项、真实阻断、下一行动方和恢复条件；计划说明和未来建议本身不等于本轮工具承诺。
4. 对外发送前先确定目标类型，例如 `codex_thread`、`lark_user` 或 `lark_chat`，再使用对应列表唯一匹配。只有人名且平台不明时先询问，不默认选择平台。
5. 未接入守卫的现有会话，检测到疑似提前结束时只标记“待补答 / 待确认”，不自动重放工具、发送消息或改写业务完成状态。新任务只有在原授权和独立验收均已绑定时，才使用上述有限续作入口。

## 验证与回滚

- 静态验证：仓库质量脚本检查故障索引、主规则短语和案例结构；这只能证明规则存在。
- 建议的事后检测样本：非空最终答复含本轮执行承诺、无对应工具/阻断记录时报告 `POSSIBLE_PREMATURE_COMPLETION`；空最终答复单独报告 `EMPTY_FINAL`；无法判断多项请求状态时报告 `UNVERIFIABLE_COVERAGE`。
- 误报控制：只要求方案或描述未来步骤时不应报警；承诺动作已经执行并进入答复时不报警；明确阻断时保持待恢复，不能标完成。
- 路由验证：精确 Codex 任务标题唯一命中才走任务工具；人名且平台不明时停止并询问，不调用外部消息工具。
- 未验证：当前未实现上述会话告警，也未完成无副作用的真实多问题对话回归。
- 程序验证：`.github/scripts/Test-TaskContinuationGuard.mjs` 和工具的 `-SelfTest` 入口覆盖独立验收、宿主续作、退出核账及反例；最新结果保存在当前任务既有本地责任记录。合成事件与本机模拟模型不能代签真实专业任务。
- 回滚：文档与规则修改可由对应本地 Commit 回退；没有运行时数据迁移或远端副作用。

### 2026-10-11 复发形态的回归

- 新增核心规则的 steering 增量合并、局部取消、提问后续接门禁。
- `Test-WorkflowRefreshContract.mjs` 增加三类离线夹具：A+B 增补 C 保留 A/B、取消 B 只停止 B、状态询问不改变原队列。
- 该回归证明规则和状态转移契约存在，不证明真实客户端或宿主会在 `final_answer` 前强制拦截；真实复现仍需取得无副作用的会话样本。
