# Codex 桌面回合长时间无进展与暂停恢复

| 字段 | 当前记录 |
| --- | --- |
| 故障编号 | `TRB-015` |
| 解决状态 | 部分解决：现象与已报道的宿主或运行时停滞相近；具体根因和当前版本通用修复未确认 |
| 最后核验 | 2026-11-01 |
| 证据边界 | 本地回合记录、工具退出状态和用户截图已核对；官方资料与公开 Issue 已回读；没有修改宿主配置，也没有把一次暂停恢复当成根因修复 |

## 现象

长任务执行到一个工具调用或测试命令后，后台命令已经结束，但界面长时间没有下一步输出。操作者点击“暂停”再“继续”后，任务有时恢复。网络浏览器同时能访问网页，不能排除 Codex 自己的回合、app-server 或界面状态卡住。

本次本地证据显示：`Test-Repository.ps1` 的部分运行曾正常结束，但另一次回合在工具之后长时间保持进行中；暂停/恢复后继续推进。另一个窗口还触发了 MagPie 的重复 `write_stdin` 保护，说明“工具真的在运行”和“模型/宿主重复等待”必须分开判断。

## 已确认与未确认

已确认：

- 这不是普通网页网络畅通就能排除的故障。
- 官方文档建议先检查审批等待、在终端运行 `git status` 等基础命令；仍卡住时等待其他活动任务结束并重启应用。
- 官方公开 Issue 已记录相近现象：工具完成后持续 reasoning、桌面显示 Thinking、app-server 会话整体停止推进，以及 `thread/resume` 在“active 但没有正在运行的 turn”时无限等待。
- 本地工作区文件没有证据表明被暂停/恢复破坏。

未确认：

- 本次是否由界面渲染状态、app-server、模型持续 reasoning、MagPie 路由或某个单独的工具进程造成。
- 暂停/恢复是恢复了真正的后端回合，还是只让界面重新取得了已有结果。
- 公开 Issue 中的修复是否已经进入当前 Windows 安装版本。

## 安全处置顺序

1. 先看最近一个工具调用是否已有退出码、结果文件或进程终态；不要因为界面没有新文字就重复执行命令。
2. 先确认没有仍在执行或结果未知的删除、远端写入、部署等不可重复动作，也没有待处理的审批或人工验收；再有界等待，由操作者尝试一次暂停与恢复。无法确认时先保全证据，不重发命令。
3. 若恢复后仍没有新工具、结果或明确阻断，读取任务状态和日志，保存当前工作区与回合证据；不要连续点击继续，也不要重复 `write_stdin`。
4. 进入新窗口或新回合时，只带已保存的断点和结果文件，先核对实际副作用，再继续未完成动作。
5. 若多个任务同时停止推进，优先怀疑本机 app-server/宿主状态；若只有一个任务卡住，先检查该回合的工具、会话和工作区。

## 是否需要向官方反馈

可准备后续反馈。现象与已报道的宿主或运行时停滞相近，但具体根因及当前安装版本是否已有通用修复仍未确认；不能排除本地链路、中转或工具进程因素。反馈应优先跟进已有 Issue，附脱敏的时间、Windows/Codex版本、最后成功工具、暂停/恢复结果和最小日志片段；不要上传项目文件、完整会话、凭据或本地绝对路径。
