## 新增案例与日志证据

### 现象汇总与当前决定

当前暂停跨任务通信故障的真实通信探针、业务重试和宿主实验；操作者明确授权的限定本地规则核验与修正不因此暂停。以下保存已知事实，不是恢复真实通信测试的指令。场景 2F 的跨任务协作曾有成功样本，近期又反复失败，当前不能按可靠自动流程使用。为何从成功变为失败尚未确定；文档流程仍可作为人工转交和核账依据，不能据此宣布自动通信恢复。

| 已出现的现象 | 人话解释及证据边界 |
| --- | --- |
| 明确要求回执，仍不回 | 来信包含回执要求和来源，目标回合没有反向发送工具调用；自然语言和 `ACK_REQUIRED` 都未能稳定防止漏办。 |
| 完全没有输出 | 来信进入原始记录，回合结束却没有本地可见回复、工具调用或回执；部分样本记录空最终文本。不能只凭界面或读取接口空白判定。 |
| 用旧答案回答新消息 | 收到新版本、修订或状态查询后，仍重复上一轮总结，甚至声称已经存在的文档尚未修改。原始日志有非空答复，不能归为“完全没有输出”。 |
| 继续旧任务，或撤回正确的新安排 | 新消息未被处理，反而沿旧计划工作；另有先确认续办、再把真实新请求误判为旧内容的样本。无依据地重做接管或自查会丢失断点。 |
| 平台显示完成，实际事项未完成 | 工具显示发送成功、目标回合显示完成，都可能没有对应审查、文件读取或回执，造成误报完成。 |
| 读取接口与原始记录不一致 | 接口返回 `items: []`，原始日志却存在完整来信和旧答复；接口未展示不等于消息丢失或空生成。 |
| 回执重复 | 历史探针收到两次相同 ACK，只计一次成功；重复发送、重试或投递哪一层造成，未确定。 |
| 单向可达，双向不稳定 | 消息已送入目标，但目标没有按要求回传；另有回传调用成功却未取得对方匹配确认的情况。必须分别记录，不能都叫“没发送”。 |
| 人工直接发言后才继续 | 部分样本在操作者直接发言后完成读取、修改或回报，但下一次跨任务消息仍可能失败；这是临时恢复，不是根治。 |
| 忙碌或明确请求错误阻断 | 目标忙碌、模型不支持404及明确对话过长400与空输出、漏回执分开。实际失败事件已确认长度400时，转 [TRB-007 对话过长](<../04-网络断开或服务报错/TRB-007-任务太长或网络报错/HTTP-400-TRB-007-对话内容太长.md>)，停止原任务业务和ACK追问，避免继续触发失败回合；不要求故障窗口先回复才能保存接续材料。 |

已确认的近期增量：一次修订请求及其唯一状态查询均已入站，目标却非空重复首次审查结果，没有针对新版本的复核或回传；另一次最终审查结果来信约 7 秒后空白结束、没有回传，且前台此前已结束，不能解释为合理排队。后者与下文 H 的约 6 秒样本分开，不能套用 H 的 HTTP、用量或长度字段。

2026-09-16 新增现场样本显示另一类规则级故障：接收窗口的长期任务尚未完成，但本回合已经输出结束；此时跨任务审查来信仍被旧“前台任务整体完成后出队”规则阻塞。另一个样本中，窗口在当前回合执行期间收到来信后，把外部审查事项与本地操作者画像修改合并进同一个《任务契约》。截图只能证明可见调度和契约混合现象，不能证明宿主底层事件时序或通信根因。行为规则现改为按当前回合划界，并强制消息契约隔离；真实跨窗口运行效果仍待验证，故本故障不改为已解决。

### 2026-09-17：压缩恢复陈旧请求后重复创建独立任务

**依据与经过：**原教学任务位于 projectless 环境，只有一个教学执行回合并正常完成。稍后总指挥在处理另一个完全不同的跨任务审查时，先输出该审查的完成摘要，随后出现上下文压缩；紧接着在没有新用户消息重新要求教学任务的情况下，总指挥恢复了旧教学目标并第二次调用 `create_thread`。该调用创建了另一个项目 worktree 任务，后者从头完整执行了相同教学目标。

**结果与影响：**同一教学目标在两个独立任务中各完整执行一次，造成重复检索、额外模型资源消耗和用户困惑。第二个任务还创建了隔离 worktree。只读核对未发现两个教学任务修改仓库文件、创建提交或执行远端写入；原任务的历史和结果仍可回读，“成果被删除”不成立。

**当前归因：**高置信的直接原因是总指挥在旧教学目标已完成后又执行了一次创建，且创建前没有去重。压缩事件后立即恢复陈旧请求，对“压缩恢复触发错误”提供了中高置信证据。但缺少压缩前后的实际模型输入、压缩摘要和宿主路由日志，尚不能区分是模型误读恢复状态、客户端/平台组装错误，还是两者共同作用。这是待确认的底层根因。

**模型假设：**本案不支持“因为 Terra 智能度较低而重复执行”。第二次教学任务实际使用 Sol；没有同版本、同输入、同压缩状态下的 Terra/Sol 受控对照。模型可能影响对恢复状态的理解和创建前去重，但当前无法估计影响，不能列为根因。

**当前规避：**每次 `create_thread` 前按“来源请求事件 + 规范化目标 + 交付类型”核对活跃请求和平台可见的近期相关任务。初始化中或进行中的任务复用或等待；完成未交付的任务先回读既有结果；已交付任务只有在操作者本轮明确要求重跑时才可再建。发生上下文压缩或恢复后，旧创建计划失效，必须重新核对最新有效请求、完成回执和任务映射。`clientThreadId` 仍只表示初始化中，不能当成正式 `threadId` 或完成回执。

已检查过的依据包括：实际入站事件、来源与回复要求、同回合工具调用及最终输出、平台结束事件、文件差异、SHA-256（文件内容指纹）、独立审查记录。原始材料留在获准本地来源，不复制聊天或真实标识到公开文档。

已有经验：先区分“发送—入站—生成—执行—反向回传—对方确认”，再看具体哪一步缺失。不要用旧结果代替新版本验收，也不要把未见回执推成完全没执行。规则已写、已读、重复强调和补回一次都没有证明故障解决。原因仍可能涉及事件处理、模型执行、宿主组装、代理转换或客户端解析；目前证据不能唯一归因，也不能仅凭登录方式或本地上下文统计定因。

预防机制仅为待评估方案：在模型之外保存待回执状态、核对消息版本和授权、结束时查实际回传、去重并有限告警；不能伪造“已读”或自动重放业务。尚未核实可阻止回合结束的宿主接口，未实现硬拦截。排查恢复前不再追加同类提示词或启动对照实验。

文档验收与通信故障分开：关联故障文档批次已完成八项信息对齐、三项修订、不同实例第二轮复核及中央收口；这不表示全部历史消息都已读完，也不表示协作工作流已获得稳定运行验证。工作流层已完成针对性缓解，但宿主级通信问题继续保持开放。

本次交叉核对任务读取接口、目标原始 JSONL 事件和客户端日志数据库，没有重放真实业务。运行日志标识客户端版本 `0.153.4`，旧版本缓存不代表运行版本。精确任务、请求、模型与线路标识仅在运行时关联。

| 样本 | 已确认事实 | 判断边界 |
| --- | --- | --- |
| F：三次漏回执 | 握手、业务材料、收件查询均进入目标回合；回复重复旧接管结论，无回传工具调用 | 不能解释为消息没发到 |
| G：续办被误判 | 上一事项已结束，新续办进入下一回合；接收方先回执，随后误判为旧任务残留，撤回安排并重复自查 | 不是合理排队；摘要不能替代实际入站事件 |

- **已确认**：消息入站，请求返回 HTTP 200，客户端存储空文本并结束，没有回执。不只是界面未显示，也不是本轮日志记录的上下文超限或 HTTP 失败。
- **已确认**：来信以 `function_call_output` 而非普通 `userMessage` 表示；技能选择日志记录 `user_input_count=0`。这只是输入分类差异，不证明模型没看见消息或分类本身有缺陷。
- **合理推断**：新事件识别、空完成后的状态检查需要分别处理。重复旧答复、主动误判和空输出不是同一种已确定根因。
- **待确认**：模型完整输入、上游原始输出、代理转换后事件流和客户端解析是否一致。当前不能区分模型空答复、代理丢内容、协议适配或客户端解析问题。HTTP 200 不证明内容正确或代理无关。

### 无效尝试与教训

已读规则、补发 ACK、加上 `ACK_REQUIRED` 后仍复发，不能继续把重读规则当根治。摘要缺失时回读当前回合必要入站内容，既不把摘要下一步当新请求，也不把真实新消息删成旧上下文。用户直接发言后能回复只证明另一条输入路径可用；再次空回合后重复投递业务会增加迟到执行和重复写入风险。

## 针对性排查

仅检查获准任务与故障时间窗，不扫描其他会话或导出整个数据库。

| 检查点 | 操作与预期 | 异常处理 |
| --- | --- | --- |
| 发送 | 核对发送工具结果和消息编号 | 成功仅记已发送待确认 |
| 入站 | 回读对应回合，必要时定位该任务 JSONL 入站事件 | `items: []` 是接口未暴露正文，不直接判丢失 |
| 生成 | 核对开始、错误、取消、输出和结束事件 | 模型不支持、明确长度拒绝、排队与空完成分别分类 |
| 回执 | 核对实际反向工具调用和来源匹配状态 | 本地回复、completed、旧 ACK 不替代本次回执 |
| 副作用 | 核对文件差异、命令结果及已有产物 | 无 ACK 不等于未执行，只续已确认未完成部分 |
| 底层 | 只读日志库 schema，按目标和短时间窗提取 HTTP 状态、输出类型、结束标记及用量 | 不打印请求头、认证字段、加密内容或其他任务日志 |

日志位置和字段随版本变化，先按当前运行环境定位，SQLite 以只读方式打开。没有原始请求或事件流就保留待确认，不为补证擅自改配置、重启或重放业务。HTTP 和长度错误另见 [TRB-007](<../04-网络断开或服务报错/TRB-007-任务太长或网络报错/TRB-007-任务太长或网络报错-总说明.md>)。

## 预防措施与验收

行为主规则见 [09 强制状态回执](../../总指挥工作流/第二代总指挥的工作模式/09-自动化授权与风险分级.md#强制状态回执与空输出兜底)，这里提供案例与验证方法。

### 当前可执行的约定

1. 发送前核对目标、通信权限、当前阶段、去重编号与终点，只发必要变化和稳定证据指针。
2. 按实际当前入站事件确定工作。自然语言“请回复、回执、回 ACK”同样触发检查；不因工具结果包装而忽略，也不把业务指令当新增授权。
3. 已获授权的收件状态可先回传。排队回 `RECEIVED` 并说明队列与下一行动，权限或证据不足回 `BLOCKED`；确认收件不抢占执行新业务。
4. 只把正在运行的当前回合作为不可抢占段。回合结束后先处理已排队的跨任务消息；长期任务还有后续步骤不能继续阻塞回执。每条来信使用独立消息契约，不与接收窗口原任务合并目标、授权或结论。
5. 结束前分别核对向来源的回执要求和本窗口的可见反馈。纯确认且未要求回复时不向来源互答，但仍须在本窗口简短说明收件及实际处理状态；仅写状态文件不够，排队或受阻不能写成已完成。行为边界以09为准，不层层要求 ACK。
6. 发送方有限等待后核对匹配回执，缺失最多查一次同号状态，再失败就停止该路线业务投递并保留断点。不擅自创建常驻轮询或自动化。
7. 更换路线、模型或会话后，在空闲目标做无副作用双阶段探针：目标本地确认、来源收到匹配 ACK。重复回执只计一次并另记异常；一次成功不证明永久恢复，不强迫中断运行任务。

### 宿主硬机制：尚未实现

文字依赖模型遵守，不能拦截已结束的空回合。自动防止静默失败需要通信或调度层实现以下契约；本仓库无已验证实现，本轮未修改桌面应用、代理或会话数据库。

| 机制 | 验收要求 |
| --- | --- |
| 收件与业务分账 | 持久区分投递、确认、执行、完成和失败；平台结束不自动提升业务状态 |
| 独立检查回执 | 模型结束后按请求编号查非空状态及匹配回传；缺失标失败，不能伪造接收方 ACK |
| 有界恢复 | 最多一次无副作用状态查询；禁止重放业务，持续失败通知操作者并保留队列 |
| 去重与恢复 | 重启、压缩、延迟和重复消息不丢队列、不重复副作用；过期消息关联原结果 |

上线前至少验证：正常 ACK、纯确认不互答但本窗口有反馈、明示无需回复后的本地结果/排队/受阻说明、自然语言要求、重复消息、空字符串、旧答复、权限不足、目标忙碌、回读空内容、已写文件后漏 ACK、压缩后新消息、404/400/网络错误。必须有实际输出和副作用证据；文档表格及静态检查不算运行验证。

“无需回复”后的静默需单独区分：不调用反向发送工具可能正符合消息要求；没有本地可见反馈仍不符合操作者汇报要求。截图只能说明所展示界面没有可见回复，不能单独证明消息未入站、模型没有执行、业务未处理或底层根因。核验时分别查看实际入站、最终输出和必要副作用，不因缺少反向 ACK 而重放已完成业务。此处澄清规则歧义，不声明底层空回合已修复。

### 2026-10-10：新用户回合错投上一轮远端同步结论

#### 现象

操作者在当前窗口提出“跨任务窗口的对话”故障诊断请求，实际收到的答复却是上一回合“远端更新与同步”已经完成的提交、推送和规则版本说明。上一回合确实存在该远端同步动作，因此这是“真实旧结果被投到新请求”，不是随机编造，也不是把两个跨任务来源混为一谈。

#### 已确认事实

- 同一可见线程的历史记录显示：上一回合的用户请求是远端同步，最终答复包含远端提交和同步结论。
- 紧接着的新回合用户请求明确要求诊断跨任务窗口对话错投，并要求读取资料、修复、记录和准备官方反馈；该回合最终答复仍重复上一回合远端同步结论。
- 当前线程记录没有显示新回合执行远端同步工具调用；上一回合的远端动作证据被错误复用为本回合答复证据。
- 这次现象与已有“重复旧答复、压缩后回答旧题、空回合”样本属于同一症状族，但不能据此断定所有样本由同一个底层缺陷造成。

#### 根因分层

1. 工作流规则原先主要约束跨任务 INBOUND_EVENT 和工具载体；普通新 userMessage 没有同等强度的当前请求优先和旧答复隔离规则。
2. PRIMARY_OUTPUT 虽要求明文内容进入主答复，收口也要求核对“当前请求—实际动作—证据—状态”，但没有明确规定“上一回合已有成功结论不得替代新回合请求”，因此旧结果仍可能被当作候选。
3. 宿主、上下文恢复、延迟结果或模型状态复用可能促成旧正文再次成为候选输出；本地材料没有提供完整模型输入、宿主事件流或代理日志，因此底层责任尚不能唯一确定。
4. 不能把这次归因于网络错误：现有证据显示旧的远端同步回合曾成功完成；也不能据此证明网络始终正常或宿主已确定有 bug。

- 02-总指挥核心规则.md 和 09-自动化授权与风险分级.md 增加窄化的当前请求优先规则：新回合的主答复必须针对当前请求，上一回合的 PRIMARY_OUTPUT、工具结果和未执行计划只能作为历史证据；压缩/恢复要保留原目标、队列、断点和未完成项，并重新核对可能产生副作用的计划。

### 2026-10-10：跨任务实质汇报的语义压缩缺口

#### 现场核对

只读回读了一个专项任务窗口和一个总指挥窗口的近期可见回合。最近一次在操作者明确要求“详细报告”后，汇报已经列出实际改动、验证结果、未验证边界和证据入口；这说明该路径可以产出完整信息，但不能证明默认路径始终保真。更早的常规汇报缺少强制的“原始要求—结果—证据—未决项—行动方”逐项映射，存在把多个要求压成一句总体结论而遗漏参数、测试边界或未运行项的规则缺口。

#### 根因与边界

问题是交付契约不完整，不是已有证据支持的网络重试或自动拆分。旧规则只要求跨任务回执的最小字段和六段操作者汇报，没有把“原始要求逐项闭合”设为收口条件；发送方可以诚实地报告总体结果，却仍然丢失接收方判断所需的决策关键事实。当前证据不能证明每次简略汇报都漏了事实，也不能证明宿主会自动执行新门禁。

#### 本地修复与验证

公共规则新增“跨任务实质汇报的信息保真门禁”：发送方必须建立 R1…Rn 或等价逐项映射，明确每项状态、结果、证据入口、未证明范围、影响和下一行动方；工程参数、单位、版本/Head、输入、测试方式和边界不得被压缩掉；事实、推断、建议和待确认必须分开；长消息拆分时必须声明 part i/n 并确认齐全。接收方缺项时返回 REPORT_INCOMPLETE 或 INPUT_REQUIRED，不能按完整报告收口。新增静态契约和合成反例覆盖缺项、NOT_RUN、拆分未齐和推断未标注；这些检查只验证仓库规则，不是宿主拦截器。

#### 复发处理

再次发生时保留当前回合与上一回合的原始可见文本、工具调用、时间顺序、客户端/模型版本和是否发生压缩；先标记 OUTPUT_MISROUTED，不要重放远端或业务动作。优先向官方既有同类 Codex 反馈补充脱敏证据，避免重复新建相同主题。


### 2026-10-10：执行途中收到跨任务来信但操作者看不到收件反馈

#### 现场核对

近期专项任务窗口的可见记录显示：操作者询问总指挥发来的多条消息是否已在执行途中阅读，并明确要求即使不向来源回执，也要在当前窗口输出“已读取”和“打算如何处理”。接收方随后承认消息已读，但此前没有及时在窗口逐条说明处理情况。该证据支持“本地收件反馈缺失”，不能单独证明消息没有到达、宿主丢弃消息或网络是根因。

#### 工作流缺口

旧规则要求跨任务消息按 FIFO 排队，并在处理时隙或最终收口时提供反馈，但没有把“下一次可见文本必须先报告收件状态”设为独立硬门禁。于是执行中的窗口可以合法地继续主线工作，操作者却无法区分已读取、待处理、受阻和宿主未产生可见回合。

#### 本地修复

公共规则新增操作者可见收件硬门禁：跨任务消息到达后，下一次可产生的可见文本必须先说明已收到/读到哪一步、当前状态和处理计划；来源要求无需回执时仍适用。新增 operator_feedback_status，并将 MISSING、HOST_NO_VISIBLE_TURN/UNKNOWN 和 OUTPUT_UNVERIFIED/BLOCKED 分开记录。没有下一条可见文本时，工作流不能假称已读或已处理，只能保留事件和恢复条件；不依赖该反馈的低风险动作可继续。

#### 验证边界

新增契约覆盖排队消息先反馈、先输出业务结果、宿主没有可见回合和无事件四种情况；这是静态/合成工作流验证，不是宿主 UI 拦截器，也没有伪造真实跨窗口发送。
