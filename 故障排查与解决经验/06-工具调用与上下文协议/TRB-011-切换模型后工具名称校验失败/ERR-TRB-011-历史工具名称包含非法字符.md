# TRB-011：切换模型后，历史工具名称校验失败

| 字段 | 当前记录 |
| --- | --- |
| 故障编号 | `TRB-011` |
| 解决状态 | 已解决：本案例本地修复已验证，操作者确认原任务恢复并可继续 |
| 工具状态 | 本案例限定修复；未提供通用可分发工具 |
| 最后核验 | 2026-10-13 |
| 证据边界 | Windows、Codex Desktop 内置运行时 `0.162.0-alpha.17.2`；单个历史会话恢复，不证明其他客户端、供应商或版本普遍适用 |

先保留完整历史原件和错误，再定位具体非法字段。不要批量替换聊天文字、删除工具调用结果、清空上下文或反复重试；这些操作可能破坏证据、调用配对或分页定位。

## 一句话现象

一个已有工具调用历史的任务切换模型及请求线路后，无法继续，反复报告 `Invalid 'input[44].name': string does not match pattern`。另一个采用相同模型切换方向的任务仍能正常对话。

## 当前是否解决

本案例已恢复。修复前确认了历史中不合规的工具名称，修复后通过本地结构和内容保全检查；操作者随后确认原任务处理成功、可以继续。

这是一次历史兼容性修复，不是客户端或中转层的永久修复。没有抓取失败请求的完整发送载荷，尚不能逐项证明哪个历史条目最终成为 `input[44]`，也不能单独归责于模型、中转站或客户端。线上恢复属于操作者观察，不冒充 AI 已捕获修复后的响应。

## 适用环境与错误签名

- 环境：Windows、Codex Desktop；已有分页及压缩历史，通过兼容接口切换模型。
- 原错误类别：`invalid_request_error`。HTTP 状态码没有独立确认，因此文件名不写猜测的 `HTTP-400`。
- 最小脱敏错误：

```text
<PROVIDER_NAME>: Invalid ***.create payload:
Invalid 'input[44].name': string does not match pattern.
Expected a string that matches the pattern '^[a-zA-Z0-9_.-]+\z'.
```

该规则要求名称非空，且只含英文字母、数字、下划线、点号或连字符。`\z` 是结束标记，不是名称本身的字符。输入索引属于请求数组，不能直接当作聊天条目或工具调用的序号。

## 已确认事实、合理推断与待确认项

### 已确认事实

1. 平台错误及目标任务日志都出现了名称校验拒绝；再次尝试仍指向 `input[44].name`。
2. 在该任务的旧模型执行阶段，保存过三个含 `::` 的 `function_call.name`。对应工具返回均为 `unsupported call`，不能把这些调用写成执行成功。
3. 最后一次压缩后的历史仍含其中一个非法名称。离线使用报错中的字符规则检查真实历史，冒号校验失败。
4. 对照任务确有同方向的模型切换；其当时读取的 25 条历史函数调用名称均符合规则。这个反例排除了“切换模型必然失败”的解释。
5. 修复只变更三个名称字段中的六个冒号字符，替换后文件长度、行数、参数、调用标识及原工具返回保持不变。
6. 对目标任务八段历史中的 144 条函数调用重新检查，未发现剩余非法名称。同版本客户端的只读解析入口能读取该任务。
7. 操作者在本地修复后确认原任务恢复并可继续；没有公开原始聊天、备份或请求载荷。

### 原因分析

最有证据支持的解释是：旧上下文已经保存了不符合新请求链路要求的工具名称，切换后回放这些结构化历史时触发校验。非法历史名称、离线校验失败、相同字段的重复拒绝，以及最小修复后的恢复，形成了较强的因果证据链。

切换更像暴露问题的条件，而不是充分原因。对照任务没有相同的异常名称，因此能正常继续。不能据此断言旧模型普遍生成非法名称，或所有跨模型会话都不兼容。

### 待确认项

- 原始发送载荷的 `input[44]` 与具体历史条目的对应关系。
- 非法名称最初由模型生成、客户端转换还是其他适配环节引入。
- 校验拒绝的具体层，以及客户端是否已有上游修复。
- 同类修复在其他版本、工具命名映射及历史存储格式中的适用性。

## 排查与处理过程

| 阶段 | 动作与目的 | 实际结果 |
| --- | --- | --- |
| 定位 | 按精确任务标识读取目标错误；只提取必要模型、工具名称、压缩及错误元数据 | 独立确认报错，不接管来源业务 |
| 对照 | 核对成功任务的模型切换和名称字段 | 同方向切换成功；无非法名称 |
| 缩小范围 | 检查仅属于目标任务的历史分段，区分原历史与压缩后保留内容 | 找到三个含双冒号名称，其中一个仍在后续历史中 |
| 离线验证 | 对真实历史名称应用错误中的字符规则 | 双冒号确定不合规；没有付费 API 重放 |
| 修改前审查 | 检查分页截点、并发写入、语义保全及备份隐私 | 不改长度，不重写其他字段；写入前核对字节并取得拒绝其他写者的文件句柄 |
| 限定修复 | 完整保全原件，只将三个名称字段中的 `::` 替换为等长 `__` | 仅六字节变化；失败结果仍保留 |
| 修改后审查 | 逐字节比对、检查原件与修复件指纹、重新解析历史及调用名称 | 非预期变化为零；分页截点保持；名称校验通过 |
| 实际恢复 | 提示客户端重新加载，随后由操作者观察原任务是否能继续 | 操作者确认处理成功；具体重载操作及线上载荷未独立记录 |

本地修复完成不等于正在运行的客户端已经读取新历史。内存仍有旧上下文时，单改磁盘可能继续报相同错误。重新加载应在其他任务空闲后进行，不能擅自结束全局客户端或中断其他工作。

## 安全恢复路径

1. 保存原件；只读核验实际发送的名称或目标任务的结构化历史。没有发现非法名称时，不套用此修复。
2. 查明存储格式、调用与结果配对、分页截点及客户端缓存；确认任务不在写入该历史文件。
3. 优先采用已核实的客户端历史修复入口。确需手工修复时，只改已确认的名称字段，并核对工具命名映射；不要对整个 JSONL 做文本全局替换。
4. 本案例采用等长替换以保护字节截点。这是本案例的兼容处理，不保证 `::` 改 `__` 对所有工具都是正确映射；新调用仍必须使用客户端实际提供的工具名称。
5. 原结果已经表明调用失败，因此保留该结果，不补造成功回执。若名称修复会改变结果含义、需删除条目或改变字节长度，先重新设计恢复方案。
6. 重新加载客户端后，只重试需要恢复的原请求。出现其他错误时停止重复改名，按新的错误定位。

## 验证与回滚

- 验证已完成：脚本语法解析、虚构数据保全测试、异常源拒绝测试、真实源只读预检、精确写入与回读、全部目标分段解析及名称校验、同版本只读解析、操作者恢复确认。
- 通过标准：只允许计划中的名称字段改变；长度、行数和下游截点不变；其他字节相同；原件备份可回读；原任务恢复。
- 未验证：完整请求体对照、修复后的线上响应抓取、长期回归及其他环境。
- 回滚：原件留在私有证据区。回滚前必须核对当前文件仍为预期修复版本；若已有新对话追加或其他写入，不能用旧备份整文件覆盖。

## 公开相似报告与区别

截至本次核验，官方 Codex 仓库中有两条仍为 open 的相似报告：

- [Issue #6540](https://github.com/openai/codex/issues/6540)：同样拒绝 `input[N].name`；后续评论指出历史中含点号的工具名称，并有用户继续询问如何处理。
- [Issue #10563](https://github.com/openai/codex/issues/10563)：直接描述历史中的 `functions.exec_command` 导致续接失败；报告者已有本地规避方法，官方回复请求提交诊断反馈，不能把 open 状态等同于所有人都尚未恢复。

两帖报告的规则不允许点号，本案例的规则允许点号但不允许冒号。它们支持“结构化历史名称可能触发校验”这一排查方向，不证明模型、线路、版本或名称映射完全相同。

[PR #9447](https://github.com/openai/codex/pull/9447) 曾尝试归一化历史名称，但已关闭且未合并；官方评论明确表示该方案不是正确修复。因此不能把它当成已发布的官方修复，也不推荐任意字符替换或全局去前缀。

公开回复应只提供脱敏观察、核验路径与安全限制，不附私有会话、备份或针对原件的修复脚本。检索结果不代表穷尽互联网，也不单凭帖子状态断言实际恢复情况。

## 配套工具与失效条件

本次脚本仅为已绑定原件和已确认三处变化的私有修复，不公开为一键工具。没有通用工具测试、不同版本验证或稳定历史编辑契约，不能建议读者下载后自动扫描、批量改写全部会话。

运行时升级、存储 schema 或命名映射变化、分页算法变化、原件新增内容、工具结果配对异常、其他写者仍活动，以及错误字段不同，都需要重验。没有明显非法名称或来源不能核实时，只读收集最小脱敏证据，不继续修改。
