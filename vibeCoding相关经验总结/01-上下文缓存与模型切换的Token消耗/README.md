# 上下文缓存与模型切换的 Token 消耗

[English](README.en.md)

## 当前结论

稳定的请求前缀可能复用服务端缓存，但追加消息、切换模型或更换窗口都不保证命中。缓存范围、有效期、计费字段和价格取决于实际供应商、模型、端点及当时配置，不能把不同服务当成完全相同的机制。

本项目还没有“相同输入、相同任务、相同验收”的直接模型对照。因此，不能从脚本运行时间、缓存命中比例或模型单价推定整个工作流更快、更省 Token 或更省钱。

## 本地文件与请求前缀

修改本地文件，不等于已经修改模型收到的请求。只有文件内容被实际读取并进入后续输入时，才可能影响该次请求的前缀。

- 末尾追加内容可能保留较长的共同前缀，但是否命中仍以服务端实际用量为准。
- 改写较早的消息可能改变共同前缀；不能据此断言每次都从头重新计费。
- 切换模型或供应商时，不假定缓存可以共享，也不假定整段输入必然按未命中计费。
- 更换窗口还会产生摘要、交接和必要重读成本，不能只看单次请求。

## 怎样核对实际成本

1. 固定任务、输入、完成标准和资源限制，分别记录直接推进与脚本辅助两种做法。
2. 合计主窗口、子代理、返工、工具输出、重新读取、通信和人工转交，不能只算执行脚本的几秒钟。
3. 按实际响应字段区分输入、输出、缓存读写及推理用量；字段是否互相包含，先查对应服务的定义，避免重复相加。
4. Token、费用、耗时和质量分开比较。订阅额度与按请求扣费不是同一个单位。
5. 请求失败或重试是否收费，以实际 usage 和账单核对；不能从 `402` 错误码直接推出再次扣费。
6. 缺少字段、分母、账单或对照组时，写“待确认”，不补造节省比例。

## 历史样本与旧稿限制

旧稿记录过21个会话中8个切换模型、约84%的请求使用较高推理档位、约95%的输入缓存命中等汇总。当前审稿没有重读原始日志，也没有取得完整样本分母、缺失日数据与逐请求账单；这些数字只作为待复核线索，不能支持当前费用归因。

旧稿的模型价格、时段翻倍、模型能力比较、客户端完整历史转发、默认推理档位和子代理默认值，均未在本轮验证。它们退出当前建议；改前原件按本项目本地审计记录保留，不作为当前价格表或产品行为说明。

## 使用时的取舍

能通过现有解析器或脚本直接确认的事实，优先复用确定性证据。需要判断需求、权限、安全和取舍的部分仍交给模型；不要为了追求缓存而省略必要验收。

是否固定模型、拆分窗口或调用子代理，应由任务难度、独立审查需要和实际总成本决定。未经同口径对照，不预先宣称某种安排必然更省。

余额不足时停止重复请求，先核对实际用量和账单。需要测试收费请求、修改配置或启用备用供应商时，另按具体范围核权。
