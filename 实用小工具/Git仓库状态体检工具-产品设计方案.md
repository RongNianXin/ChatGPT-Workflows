# Git 仓库状态罗盘（Git State Compass）：产品设计方案

状态：方案已完成两轮执行者与独立审查者复核，并完成本轮桌面客户端补强审查；最新结论为 `PASS_WITH_ACCEPTED_RISKS`。

本文件只记录产品方向和开发边界，不代表已经开始实现、创建远端仓库或取得任何 GitHub 写入授权。

## 1. 最终决策

### 1.1 要不要做

可以做，但不能把产品定义为“Git 分支树查看器”或“PR 堆叠图”。这些能力已经有成熟或接近成熟的产品。

值得验证的产品方向是：

> 面向 Git 新手的本地优先桌面客户端：看清当前仓库状态，理解本地与 GitHub 的关系，并获得无需大模型的下一步建议。

它要回答五个实际问题：

1. 我当前在哪个仓库、worktree、分支和提交上？
2. 我的修改现在位于工作区、本地历史、远端跟踪引用还是 GitHub PR？
3. 针对“继续编辑、Commit、刷新事实、整合 Base、Push、更新 PR、合并 PR、清理分支”等具体动作，现在分别是否安全、是否需要授权？
4. 为什么给出这个判断，什么变化会让判断失效？
5. 当我明确选择“提交 PR、合并 PR、远端更新到本地”等目标后，现在最小且可靠的下一步是什么？

如果 v0 竞品对照不能证明它比现有工具更清楚地回答这些问题，应停止独立产品开发，改为使用或贡献现有项目。

### 1.2 仓库归属

独立审查者的最终裁定是：通过 v0 门禁后，建立独立远端仓库。

独立仓库负责：

- 产品代码、版本和 Release；
- Windows 二进制，后续的 macOS 构建；
- Issue、贡献指南、安全策略和发布校验；
- 产品文档、演示材料和测试夹具。

ChatGPT Workflows 只保留：

- 与场景四的入口和使用说明；
- 未来版本化、脱敏的 JSON/Markdown 导出协议；
- 指向独立产品的链接。

本裁定不授权现在创建 GitHub 仓库、Push 或修改远端内容。

### 1.3 产品名称

- 中文名：**Git 仓库状态罗盘**；
- 英文名：**Git State Compass**；
- 远端仓库名候选：`git-state-compass`；
- 英文副标题：`Visualize your Git repository state and know what to do next.`；
- 中文定位：看清仓库当前状态，知道下一步该往哪里走；
- 功能说明：可视化理解本地与远端 Git 状态、分支与 PR 关系，并根据当前目标获得无需大模型的下一步建议；
- 推荐 Topics：`git`、`github`、`repository`、`branch`、`pull-request`、`git-workflow`、`git-status`、`developer-tools`、`repository-visualization`、`beginner-friendly`、`offline-first`。

名称只负责品牌和记忆，不承担全部功能说明。`Git State` 直接限定产品处理的是 Git 状态，`Compass` 表达“当前位置、周围状态和下一步方向”。`State` 比 `Branch + PR` 更能覆盖 working tree、worktree、HEAD、本地历史、远端跟踪引用、GitHub、PR 和复现身份，也比单独的 `Repo Compass` 更具体。

截至 2026-09-21，当次 GitHub 公开仓库搜索未发现 `git-state-compass` 或 `Git State Compass` 明显同名结果。`repo-compass/RepoCompass` 已被多个仓库使用，部分项目也涉及仓库导航、解释或评估，因此不采用附件建议的 `Git Repo Compass`。搜索结果不能证明商标、域名、包名或其他平台名称可用；正式创建仓库前必须重新核对。

### 1.4 本轮建议审查

| 建议 | 结论 | 处理 |
| --- | --- | --- |
| 首页围绕位置、风险、目标和下一步 | 采纳 | 图退到详情层，不再占据首页中心 |
| 四级渐进披露 | 采纳 | 普通结论、原因、证据、原始技术详情分层 |
| 严格拆分刷新、查询、Fetch、整合和 Push | 采纳 | 为每个动作显示数据源、影响和只读边界 |

| `Git Repo Compass` | 不采纳 | 近似名称较多，改为 `Git State Compass` |

## 2. 已确认的问题与边界

### 2.1 用户问题

- 不熟悉 Git/GitHub 术语，看不懂当前分支、主干和 PR 的关系。
- 不知道当前是否应该继续开发，还是先处理分支或 PR 依赖。
- 不理解本地到远端、远端到本地分别发生了什么。
- 提交和合并 PR 时，不知道 Merge、Squash merge、Rebase merge 如何选择。
- 曾出现 PR 合并后，队友拉取代码却与作者本机运行效果不同。
- 希望通过可视化界面理解当前事实，同时学会正确判断，而不是背命令。
- 第一版面向 Windows，后续兼容 macOS；不希望租服务器。

### 2.2 Git 能确认什么

Git 可以确认：

- Commit 的父子关系；
- HEAD、分支和引用当前指向的 Commit；
- 工作区、暂存区、未跟踪文件和进行中的 Git 操作；
- 两个提交之间的祖先关系、共同祖先和提交差异；
- 本地分支配置的 upstream；
- 当前机器上的 worktree。

Git 不能可靠恢复：

- 一个分支最初从哪个“分支名”创建；
- 没有提交或推送的队友工作；
- 业务上的依赖关系；
- 作者当初为什么选择某条分支；
- 两台机器实际运行效果是否一致。

因此，工具不得把算法推断伪装成 Git 事实。

### 2.3 关系证据等级

所有关系和结论必须显示证据等级：

| 等级 | 含义 | 示例 |
| --- | --- | --- |
| Git 已确认 | 来自当前快照中的 Git 对象、引用或状态 | HEAD、Commit 祖先关系、工作区修改 |
| GitHub 已声明 | 来自指定 GitHub 仓库的只读查询 | PR Head/Base、PR 状态、Checks |
| 配置已声明 | 来自仓库规则或用户明确配置 | 默认主干、目标 remote、允许的合并方式 |
| 工具推断 | 由多个证据推导，可能存在其他解释 | 最可能的父分支、可能等价的提交内容 |
| 未知/不可用 | 证据不足、断网、无权限或工具缺失 | 私有 PR 无访问权、远端状态无法查询 |

“内容已合入”只使用 `confirmed / probable / unknown`，并列出各证据适用范围。SHA、patch-id、tree、Diff 或 PR 状态中的任何单项都不能在所有合并方式下独立证明内容等价。

## 3. 产品定位与竞品边界

### 3.1 不是这些产品

- 不是完整 Git 客户端；
- 不是另一个完整提交图；
- 不是堆叠 PR 管理平台；
- 不是自动替用户执行 Git 操作的机器人；
- 不是依靠大模型重复分析仓库的问答工具。

### 3.2 与现有产品的区别

| 产品/类别 | 主要能力 | 本产品需要证明的差异 |
| --- | --- | --- |
| `git log --graph`、lazygit、传统 Git GUI | 查看提交与分支 | 解释成果在哪一层、各动作是否安全及原因 |
| Graphite、Git Town、GitButler、git-branchless | 创建和管理堆叠分支/PR | 新手状态诊断与只读教学，不强迫采用特定工作流 |
| `gh-pr-graph` | 用 Go、本地浏览器和 `gh` 展示 PR/堆叠分支图 | 同时覆盖本机工作现场、本地/远端状态、动作矩阵和复现身份 |

PR 图只能是“GitHub 协作层”的一个视图，不能成为首页唯一主视觉，也不能作为核心差异化。核心差异还包括：用户明确选择目标后，工具用可复现的确定性规则给出一条最小下一步，并展示证据、风险和失效条件，不调用大模型、不消耗 Token。

## 4. 界面信息架构

### 4.1 桌面端主流程

首页不是提交图，也不是四层数据的总表。用户打开仓库后，主流程固定为：

1. 确认当前仓库、worktree、HEAD 和 branch；
2. 查看必须立即处理的风险或未知项；
3. 选择当前想完成的目标；
4. 阅读唯一的首要下一步、原因、影响和失效条件；
5. 需要核查时再进入状态层、关系图或技术证据。

桌面布局建议使用固定顶部状态栏、主工作区和详情标签页，不堆叠装饰性卡片：

```text
[仓库] [worktree] [branch] [本地快照：有效/已过期] [GitHub：状态与观察时间]
----------------------------------------------------------------------------
你现在在哪里                         当前需要注意什么
仓库、工作树、分支、修改所在层        冲突、脏工作区、未知 remote、过期事实

你想完成什么？
[继续开发] [建立 Commit] [提交/更新 PR] [合并 PR] [更多目标...]

首要下一步
结论 + 为什么 + 会影响什么 + 权限 + 未知项 + 失效条件 + 观察时间
----------------------------------------------------------------------------
[概览] [工作现场] [本地历史] [远端跟踪] [GitHub] [关系图] [复现身份] [证据]
```

顶部状态栏必须始终可见。仓库、worktree、branch、snapshot 和 GitHub 状态分别显示，不能压成一个含糊的“已同步”。关系图位于详情标签页，只解释当前问题涉及的关系，不承担首页导航。

### 4.2 四层状态

四层状态是详情结构和规则引擎输入，不是四个并列首页大面板。这样既保留专业信息，又避免新手一打开就面对完整 Git 数据。

#### 工作现场层

- 当前选择的仓库和 worktree；
- 当前 HEAD、分支或 detached HEAD；
- 未跟踪、未暂存和已暂存修改；
- 正在进行的 Merge、Rebase、Cherry-pick 等操作；
- 冲突和来源不明的本地修改。

#### 本地历史层

- 本地分支和 Commit；
- 相对目标 Base 的 ahead/behind；
- upstream 配置和缺失状态；
- 其他 worktree 及其分支占用情况。

#### 远端跟踪层

- 本机保存的 `refs/remotes/*`；
- 每个引用在当前快照中的 OID；
- 本工具观察到它们的时间；
- 明确提示它们可能陈旧，不能把它们称为 GitHub 查询时状态；
- 不伪造“最后 Fetch 时间”。

#### GitHub 协作层

- 用户明确选择的目标 host、remote 和 repository；
- 远端分支在查询时观察到的 OID；
- PR Head/Base、Draft、Review、Checks 和合并状态；
- 堆叠 PR 的声明关系；
- 后续可选的 Issue 关联。

多 remote、多 GitHub Host 或 fork 场景必须显式选择 `target_remote / target_host / target_repository`。其他 remote 只展示，不自动合并事实；无法唯一选择时，GitHub/PR 相关动作状态为 `NEEDS_CHECK`。

### 4.3 渐进披露

同一个判断按四级展开：

1. 人话结论：例如“你正在 `feature/login` 分支开发，本地有 2 个尚未推送的 Commit”；
2. 原因与影响：为什么得出结论、下一步会改变什么、是否涉及远端写入；
3. Git/GitHub 证据：ahead/behind、PR Head/Base、Checks、来源和观察时间；
4. 技术详情：OID、`rule_id`、`snapshot_id`、受控命令及经过脱敏的结构化输出。

默认只展开前两级。技术细节不能删除，但不应抢占主视觉。Git 术语第一次出现时附一句短解释，例如“远端跟踪分支：你电脑里保存的远端状态副本”。界面不能仅靠颜色表达状态，必须同时使用文字、图标和状态词。

### 4.4 刷新、查询和状态变化

以下动作在名称、按钮位置、影响说明和权限提示上必须分开：

| 用户动作 | v1 是否执行 | 数据或状态影响 | UI 要求 |
| --- | --- | --- | --- |
| 重新读取本地状态 | 是 | 只生成新的本地快照 | 标为“读取本地”，显示完成时间 |
| 查询 GitHub 最新事实 | 是 | 发起只读联网查询，不改本地 refs | 标为“查询 GitHub”，显示目标 host/repository 和观察时间 |
| Fetch | 否 | 会下载对象并更新 remote-tracking refs | 只解释和建议，不显示成普通刷新按钮 |
| 将远端变化整合进当前分支 | 否 | 可能改变当前分支、index 和工作树 | 明确区分 Fast-forward、Merge、Rebase |
| Push 本地 Commit | 否 | 改变远端分支 | 显示远端写入和授权要求 |
| 创建或更新 PR | 否 | 改变 GitHub 协作状态 | 显示目标 Head/Base 和授权要求 |
| 合并 PR | 否 | 改变目标分支和 PR 状态 | 显示保护规则、Checks、Review 和授权要求 |

每个来源单独显示 `observed_at` 和 `freshness`。本地快照、remote-tracking refs、GitHub 查询不能共用一个时间戳。系统不声称 GitHub 结果在查询完成后仍保持不变，也不声称知道从未记录的“最后 Fetch 时间”。

文件系统事件只能作为失效提示，不能作为唯一正确性边界：事件到达时立即把快照标记为过期并停用建议；窗口重新获得焦点、用户选择目标或准备展开建议时，再轻量复核 HEAD、refs、index 和工作区指纹。指纹不一致就停用旧建议，用户重新读取本地状态后才能恢复。后台不得因此自动 Fetch、查询 GitHub 或执行任何写操作。采集期间仓库变化时按 6.2 的一致性规则处理。

### 4.5 首次启动与仓库选择

第一次启动只完成必要检查，不展示长教程：

1. 检查应用版本、WebView 运行环境和系统 Git；
2. Git 缺失时说明用途和安装入口，停止仓库分析；
3. `gh` 缺失或未登录时允许进入本地模式，GitHub 层标为不可用；
4. 用户通过系统目录选择器打开仓库或 worktree；
5. 验证路径是否为可读 Git 仓库，并识别普通仓库、worktree、bare repository 和 shallow clone；
6. 存在多个 worktree、remote、fork 或 GitHub Host 时要求显式选择，不默认猜测 `origin`；
7. 生成首个快照，进入首页主流程。

bare repository 和 shallow clone 可以有限展示，但必须说明哪些拓扑或工作区判断不可用。仓库损坏、对象缺失或 Git 命令异常时进入诊断状态，不输出下一步建议。

最近仓库记录属于便利功能，不是分析前提。v1 默认不保存最近仓库；用户显式开启后，只保存在操作系统的当前用户应用数据目录，并提供查看和一键清除。记录不存在、仓库已移动或无权限时从列表移除记录，不修改原仓库。

### 4.6 情境教学

教学内容跟随当前对象和动作出现，不做与当前状态无关的长教程。例如：

- 工作区文件尚未 Commit，因此还没有进入分支历史；
- Commit 当前只存在于本地，Push 后远端分支才能看到；
- PR 是请求把 Head 合入 Base，不等于已经合并；
- 远端跟踪引用是本机缓存，不等于 GitHub 查询时观察到的状态；
- Fetch 更新本地 Git 对象和引用，不会自动把当前工作树更新为远端版本；
- 技术上可以执行，不等于团队规则或用户已经授权执行。

每条建议显示“为什么”和“什么变化会让它失效”。

## 5. 按动作能力矩阵

工具不得输出单一的“可以继续开发”绿灯。不同动作需要分别判断。

最少动作包括：

1. 继续本地编辑；
2. 建立本地 Commit；
3. 查询 GitHub 最新观察事实；
4. 刷新本地远端跟踪引用；
5. 把 Base 变化整合进当前分支；
6. Push；
7. 创建 PR；
8. 更新 PR；
9. 合并 PR；
10. 删除本地分支；
11. 删除远端分支。

每一行至少包含：

| 字段 | 含义 |
| --- | --- |
| `action_id` | 稳定的动作标识 |
| `target` | 该判断针对哪个 worktree、分支、remote 或 PR |
| `technical_state` | `READY / NEEDS_CHECK / BLOCKED / UNAVAILABLE` |
| `authorization_state` | `NOT_APPLICABLE / REQUIRED / CONFIRMED / UNKNOWN` |
| `facts` | 支持判断的当前快照事实 |
| `risks` | 已知风险和未知项 |
| `next_step` | 建议的最小下一步，不等同于自动执行 |
| `invalidated_by` | 哪些变化会使结论失效 |

技术状态与授权状态必须分开。即使 v1 不执行写操作，用户也可能照着建议手动操作，因此不能把“技术上可行”写成“已经允许”。

### 5.1 状态示例

- 未解决冲突或 Git 操作进行中：相关集成、Push 和合并动作 `BLOCKED`；不相关文件是否可继续编辑另行判断。
- 当前分支已被他人依赖或共享：可以继续建立新 Commit，但 Rebase 候选应 `NEEDS_CHECK` 或 `BLOCKED`。
- 远端事实陈旧或未知：本地编辑未必需要停止，PR/合并相关判断为 `NEEDS_CHECK`。
- detached HEAD：可以检查和保存现场，但创建正常分支历史前不能把它当作普通功能分支。
- 默认分支上存在未提交修改：不自动判定数据丢失，但切换、整合和发布相关动作需要先核对成果归属。

### 5.2 确定性下一步建议引擎

这项能力可以在不依赖大模型的情况下实现。它不是自然语言 AI，而是“用户目标 + 仓库快照 + 决策表”的规则引擎。第一版不解析开放式提问，用户从固定目标中选择：

- 继续开发；
- 建立 Commit；
- 提交 PR；
- 更新现有 PR；
- 合并 PR；
- 查询 GitHub 最新事实；
- 将远端变化更新到本地；
- 将本地成果推送到远端；
- 排查合并后运行效果不一致。

规则引擎输入必须包括有效的 `RepoSnapshot`、用户选择的目标、明确的目标分支/remote/PR、仓库规则和 GitHub 分支保护。处理顺序固定：

1. 检查快照是否完整、新鲜，目标对象是否唯一；
2. 先匹配冲突、未完成 Git 操作、脏工作区保护等硬阻断；
3. 再应用仓库规则、分支保护和已确认的团队约束；
4. 按用户目标进入对应决策表；
5. 使用 Git/GitHub 事实匹配规则，必要时才使用明确标记的受限推断；
6. 只输出一条首要下一步，可以附带不会混淆主建议的备选路径；
7. 同时显示依据、风险、权限要求和失效条件；
8. 证据不足、规则冲突或目标不明确时输出 `NEEDS_CHECK`，不得猜测。

规则优先级从高到低为：硬阻断 > 仓库规则和分支保护 > Git/GitHub 已确认事实 > 用户明确配置 > 受限启发式 > 未知时停止判断。规则至少包含：

| 字段 | 含义 |
| --- | --- |
| `rule_id` | 稳定、可测试的规则编号 |
| `intent` | 用户明确选择的目标 |
| `preconditions` | 规则适用的必要事实 |
| `guards` | 必须先通过的安全条件 |
| `matched_facts` | 本次实际命中的快照证据 |
| `technical_state` | `READY / NEEDS_CHECK / BLOCKED / UNAVAILABLE` |
| `authorization_state` | 是否需要且是否已有操作授权 |
| `next_step` | 唯一的首要下一步，使用操作描述而非默认执行命令 |
| `reason` | 面向新手的简短原因 |
| `alternatives` | 有条件的备选路径，不得伪装成同等首选 |
| `invalidated_by` | 会使建议失效的状态变化 |
| `confidence` | `confirmed / inferred / unknown`，不得用虚假百分比 |

#### 提交 PR

- 有未提交修改：先核对修改归属并形成 Commit；
- 当前位于默认分支：先确认成果是否本应位于功能分支，不直接建议从默认分支提 PR；
- 有本地 Commit 但没有对应远端分支：将 Push 作为候选下一步，同时单独提示远端写入授权；
- 同一 Head 已有开放 PR：建议更新现有 PR，不重复创建；
- 当前分支依赖另一条未合并分支：展示堆叠关系，先核对 PR 的 Base 是否正确。

#### 合并 PR

- PR 为 Draft，存在冲突，或 Checks/Review/分支保护未满足：阻断合并，只指出当前优先级最高的缺口；
- 堆叠 PR：按实际 Head/Base 和依赖关系解释顺序，不按分支名猜测；
- Merge commit、Squash merge、Rebase merge 只能依据仓库允许方式和明确策略给出候选；
- 没有明确策略时比较影响并输出 `NEEDS_CHECK`，不宣称存在唯一最佳方式；
- 合并属于远端写操作，技术可行和操作授权必须分开显示。

#### 将远端变化更新到本地

- target remote/upstream 不明确：先让用户选择目标，不建议 Pull；
- 工作区脏或存在未完成 Git 操作：先保护现场并解决当前状态；
- 本地可以 Fast-forward：说明这是候选整合方式，但 v1 不执行；
- 本地已经包含目标远端提交：说明无需重复整合；
- 本地与远端双方分叉：依据共享状态和仓库规则解释 Merge/Rebase 选择；证据不足时输出 `NEEDS_CHECK`。

建议卡片必须把“建议做什么”“为什么”“会改变什么”“是否需要权限”“何时失效”放在同一视图。v1 只给建议，不提供 Fetch、Pull、Commit、Push、Merge、Rebase 或 PR 操作按钮。

### 5.3 建议卡片显示契约

建议卡片是首页的主要结果区，字段顺序固定：

1. 当前目标和目标对象；
2. 当前技术状态；
3. 唯一的首要下一步；
4. 原因和命中的事实；
5. 该步骤会影响本地还是远端；
6. 是否属于远端写操作、是否需要授权；
7. 已知风险和未知信息；
8. 建议失效条件；
9. 各数据源的观察时间。

`READY` 只表示当前证据支持该动作，不代表其他动作安全，也不代表已经获得团队或平台授权。`BLOCKED` 必须说明第一个应处理的阻断项；`NEEDS_CHECK` 必须说明缺少什么，不能只显示灰色状态。

“查看对应 Git 命令”可以作为 v1 可选功能，但必须放在第四级技术详情中，并满足以下条件：

- 只从固定模板和已验证参数生成单条命令，不拼接 shell；
- 目标 branch、remote 或 PR 不唯一时不生成；
- 状态为 `BLOCKED` 或快照已过期时不生成；
- 命令旁明确写出“仅供核对，显示命令不等于建议执行或已经授权”；
- 可以提供复制按钮，但不提供运行按钮，不自动打开终端；
- v1 不展示 Reset、Clean 或其他破坏性命令。

## 6. 快照与一致性模型

### 6.1 RepoSnapshot

规则引擎只能消费一个版本化的完整快照。建议最小字段：

- `schema_version`
- `snapshot_id`
- `started_at`
- `completed_at`
- 仓库内部身份与展示用脱敏身份
- worktree 路径、HEAD OID、当前分支或 detached 状态
- index、工作区和未跟踪状态
- 进行中的 Git 操作
- 本地 refs 与 OID
- upstream 配置
- worktree 列表
- 远端跟踪 refs 与 OID
- 远端/GitHub查询的 `query_method`、`observed_at`、目标 OID、PR 数据、错误和权限状态
- 各来源的 `fresh / stale / unknown / unavailable`
- 快照和各结论的失效条件

`completed_at` 只表示采集完成，不表示本地与外部来源在该时刻被原子冻结。界面必须保留各来源自己的 `observed_at`。

### 6.2 采集期间变化

采集完成后重新读取本地 HEAD、refs 和工作区状态：

- 没有变化：快照可交给规则引擎；
- 发生变化：快照标记为 invalid，不输出动作结论；
- 可以有界重试一次；
- 再次变化：提示用户停止修改后手动刷新。

所有建议绑定 `snapshot_id`、`rule_id` 和输入事实。同一 JSON 快照必须产生稳定结果。

## 7. Merge、Squash 与 Rebase 教学

界面必须拆开两个常被混淆的问题。

### 7.1 把最新 Base 带入功能分支

候选可能包括：

- Fast-forward；
- 把 Base merge 到 feature；
- 把私有 feature rebase 到 Base。

判断时读取当前拓扑、分支是否共享/已推送、是否被下游分支或 PR 依赖、仓库规则和冲突风险。共享或被依赖的历史不得自动建议改写。

### 7.2 把 PR 合入 Base

候选可能包括：

- Merge commit：保留分支合并结构；
- Squash merge：把 PR 内容压成新的提交，原提交身份不会直接进入 Base；
- Rebase merge：把提交重新应用到 Base，形成新的提交身份和线性历史。

工具必须先读取仓库实际允许的合并方式、分支保护、PR 状态和团队规则。信息不足时显示 `NEEDS_CHECK`，不提供“唯一最佳方式”。本地 Rebase 与 GitHub 的 Rebase merge 不能共用一个含混按钮或解释。

v1 只做解释、候选比较和风险提示，不执行任何合并或历史改写。

## 8. 本地与远端状态教学

界面应把典型流向画成有方向的步骤：

```text
工作区修改
  -> 暂存区
  -> 本地 Commit
  -> 本地分支
  -> Push 后的远端分支
  -> PR（Head -> Base）
  -> 实际合并结果
  -> 本地重新查询/获取/整合后的状态
```

反向同步必须区分：

```text
查询远端事实
  != Fetch 到本地远端跟踪引用
  != 把远端变化整合进本地分支
  != 本地工作树已经验证可运行
```

工具不得用一个“同步”按钮隐藏这些不同动作。

## 9. 合并后运行效果不一致

代码已经合并，不代表两台机器运行的是同一套系统。差异可能来自：

- 实际 Commit 或 tree 不同；
- 工作区存在未提交修改；
- 依赖锁文件或安装结果不同；
- 运行时、编译器或工具链版本不同；
- 非秘密配置、profile 或 feature flag 不同；
- 模型、资产、LFS 或 submodule 状态不同；
- 构建命令、构建产物或缓存不同；
- 启动入口、服务进程或输入不同。

### 9.1 v1 复现身份面板

v1 只检查本机复现身份和缺口，建议包含：

- Commit/tree 与工作区脏状态；
- 依赖锁文件及其指纹；
- 工具链版本；
- 非秘密 profile 名称；
- 外置资产清单和允许公开的指纹；
- 构建、启动命令与实际入口；
- Git submodule/LFS 的受限状态。

每个字段分别标记：存在、已采集、一致性未知、实际运行未验证。不读取、记录或导出 Secret 值。

后续版本可以让两台机器分别生成脱敏快照并做结构化比较，但快照仍不能代替接收者实际运行验证。v1 不做自动环境修复，也不声称两台机器效果一致。

## 10. 技术架构

### 10.1 候选桌面形态

核心分析、规则引擎、Git 进程调用和 `RepoSnapshot` 必须与 UI 壳分离。这样更换桌面壳不会重写领域逻辑，也不会把 Windows API 带入未来的 macOS 构建。

以下体积和启动速度只是相对判断，实际数值必须由同一功能样机测量：

| 方案 | 交付与依赖 | Git/gh 能力 | 安全与维护 | 结论 |
| --- | --- | --- | --- | --- |
| Wails + 系统 WebView | 前端资产可编入原生程序；Windows 依赖 WebView2，macOS 复用系统渲染组件 | Go 直接调用受控进程 | 正式版不必向普通浏览器暴露本地 API；Go 与 Web 前端契合 | 首选候选，须通过 v0 技术门禁 |
| Go 本地服务 + 系统浏览器 | 实现快、跨平台；需要端口和浏览器窗口管理 | Go 直接调用受控进程 | 必须保护 loopback、Host、Origin 和会话令牌；产品感较弱 | v0、开发和诊断使用，不作为 v1 默认降级入口 |
| Electron | 自带 Chromium，跨平台一致 | 可通过 Node/子进程实现 | 包体、内存和依赖维护相对更重 | 与轻量目标不符，暂不采用 |
| Tauri + 系统 WebView | 体积通常较小，支持 Windows/macOS | 需要 Rust 或额外 Go 进程边界 | 引入第二套后端语言和 IPC 设计 | 仅在 Wails 门禁失败且愿意调整后端时重评 |

### 10.2 推荐路线与决策门禁

当前推荐是 Go 领域核心 + Web 前端 + Wails 原生窗口。Wails 官方文档说明其复用平台 WebView、支持 Windows/macOS，并可把前端资产编入单个可执行程序；这不等于 Windows 上没有 WebView2 运行时依赖。

v0 可以使用浏览器模式快速验证信息架构，也应制作最小 Wails 样机。只有同时满足以下条件，Wails 才成为 v1 的确定技术路线：

- 支持的 Windows 环境能稳定启动、退出和再次打开；
- 能在启动前检测 WebView2 缺失并给出可恢复提示；
- 正式构建不向普通浏览器暴露可调用 Git 的 loopback API；
- Unicode、长路径、目录选择、多窗口误开和进程取消得到验证；
- Git/gh 超时、取消和异常退出不会留下失控子进程；
- 实测包体、冷启动和内存开销符合“轻量”目标；
- Go 核心和前端不依赖 Windows 专属业务接口；有 macOS 环境时执行最小构建冒烟测试，没有环境则明确保留为未验证项，不阻塞 Windows v1。

门禁失败时重新比较 Wails、浏览器模式和其他壳层，不把开发期浏览器入口自动升级为正式降级方案。具体 Wails 版本、前端框架和最低系统版本均为「待确认」。优先使用原生 JavaScript/TypeScript 或轻量框架，除非交互复杂度证明需要更重方案。

### 10.3 Windows 运行时与发布形态

Windows 正式构建优先使用系统的 WebView2 Evergreen Runtime。应用启动前检测运行时；缺失时由安装说明或 Installer 引导用户从微软官方渠道安装，不静默下载。Fixed Version Runtime 会显著增加包体，和轻量目标冲突，v1 不采用，除非后续出现明确的离线企业场景。

v1 最小发布链包括：

- 带版本信息的 Windows x64 便携构建；
- SHA-256 校验值、变更说明和支持范围；
- 应用内“关于”页面，显示应用版本、规则版本和快照 schema 版本；
- WebView2、Git 和可选 `gh` 的环境检测。

Installer 是否进入 v1，由新手测试决定：如果便携版的环境预检和说明仍不能让目标用户在不运行手工命令的情况下进入主界面，Installer 升为 v1 必须项。代码签名涉及证书和费用，当前为「待确认」；未签名构建必须明确标注，不能写成已签名。v1 不做自动更新，也不在启动时后台检查版本；以后可先增加用户主动触发的版本查询，再单独评估自动更新和供应链风险。

### 10.4 配置、日志与调试导出

- 配置写入操作系统提供的当前用户应用数据目录，不硬编码机器路径；
- 配置带 schema 版本，只保存界面偏好、用户显式选择的目标和可撤销的最近仓库记录；
- 最近仓库默认关闭，启用后显示保存内容和清除入口；
- 默认日志只记录应用版本、事件码、阶段耗时、错误类别和每次启动随机生成的会话标识；
- 默认日志不记录完整路径、用户名、remote URL、Commit/PR 正文、文件内容、环境变量或凭据；
- 不接入遥测或自动崩溃上报；
- 调试包使用字段白名单生成，先展示脱敏预览，再由用户主动保存；
- 调试包不得包含 `gh` 凭据、Token、Cookie、Secret、原始 Git 配置或未经筛选的命令输出。

### 10.5 GitHub 联网

- 优先复用 `gh` 的登录和权限管理，不保存第二套 GitHub Token；
- 只有用户触发“查询 GitHub”时联网，界面提前显示目标 host 和 repository；
- 请求必须有超时、取消和错误分类；
- 断网、未安装、未登录或权限不足时，GitHub 层显示 `UNAVAILABLE/UNKNOWN`，本地分析仍可使用；
- v1 的查询只读取远端事实，不执行 Fetch，不修改本地远端跟踪引用；
- 不建立自有云后端，不上传仓库快照、路径、日志或调试包。

## 11. 只读与安全契约

### 11.1 命令执行

- 使用参数数组调用 Git，不经过 shell，不拼接命令字符串；
- 只允许固定的 Git 子命令和参数；
- 在适用位置使用 `--` 区分选项和不可信值；
- 禁止 pager、颜色和 ANSI 控制序列；
- 优先使用 NUL 分隔或经过验证的无歧义格式；
- 分支名、Commit 文本、路径、remote 和 PR 文本全部按不可信输入处理；
- 使用 `GIT_OPTIONAL_LOCKS=0` 或等价方式抑制可选索引刷新；
- 采集前后验证 HEAD、refs、index 和工作区状态。

产品只能声明“设计目标是不改变 HEAD、refs、index 和工作树，并在已验证场景中只读”，不能承诺未经验证的文件系统字节级零写入。

### 11.2 本地界面

- Wails 正式构建通过受控绑定调用 Go，不向普通浏览器公开通用 Git API；
- v0 或开发期浏览器模式只监听 `127.0.0.1`/`::1`，使用随机高位端口和随机会话令牌；
- 浏览器模式校验 Host 和 Origin，且关闭后立即释放端口和令牌；
- CSP 允许本机 UI 所需的 self 资源和 API，禁止外部来源；
- 不使用 `innerHTML` 插入仓库数据，统一按上下文转义；
- 正式 WebView 禁止任意导航和远端脚本，外部文档链接交给系统浏览器并提示目标域名；
- 发布构建默认关闭开发者工具和调试端口；
- 临时目录只能位于本工具自有目录；清理失败必须显示，下次启动只识别并安全处理自己的目录。

### 11.3 展示与导出隐私

- v1 本机界面默认隐藏完整绝对路径、用户名和私有 remote；
- 本地用户可显式展开，但不因此获得外发许可；
- 最近仓库、配置和日志只保存在本机当前用户目录，能够在设置中查看并清除；
- v1 不提供可分享 HTML 或快照；
- v1.x 分享导出需要字段白名单、脱敏预览、用户确认、Secret 扫描和独立 CSP。

## 12. 版本范围

### 12.1 v0：是否继续做的验证门禁

v0 不追求正式 UI，先完成：

- 版本化 RepoSnapshot schema；
- rule_id 与确定性规则引擎；
- 动作能力矩阵；
- 九类固定用户目标和三类核心决策表；
- 固定仓库夹具；
- 首页主流程和四级渐进披露的可用性原型；
- 浏览器开发入口与最小 Wails 样机；
- WebView2 检测、受控 Git/gh 子进程和正式构建安全边界验证；
- 与 GitButler、lazygit、gh-pr-graph 的任务级对照；
- 证明核心价值不是 PR 图。

Go/no-go 问题：

> 它是否能比现有工具更清楚地说明成果在哪一层、每个动作是否安全、为什么，并针对用户目标给出稳定、可解释的最小下一步？

答案不能被证据支持时，不进入 v1 完整开发。

### 12.2 v1 必须：Windows 单机只读桌面客户端

包含：

- 首次启动环境检查和系统目录选择器；
- 普通仓库、worktree、bare repository、shallow clone 和损坏状态识别；
- 多 worktree、remote、fork 或 GitHub Host 的显式选择；
- 固定顶部状态栏和“位置、风险、目标、下一步”主流程；
- 四层状态视图；
- 四级渐进披露和情境教学；
- 版本化一致快照；
- 仓库变化后立即使旧建议失效；
- 按动作能力矩阵；
- 固定目标选择器和确定性下一步建议卡片；
- 分开的“读取本地”和“查询 GitHub”只读操作；
- 本地与远端状态教学；
- PR Head/Base 和堆叠关系视图；
- Merge/Rebase 情境教学；
- 本机复现身份面板；
- 明确的数据来源、观察时间、未知项和失效条件；
- Git、可选 `gh` 和 WebView2 缺失时的可恢复提示；
- 关于页面、版本信息、便携构建和 SHA-256 校验值；
- 本地配置、日志和调试导出的隐私边界。

正式 UI 优先使用通过 10.2 门禁的 Wails 原生窗口。门禁未通过时必须先重新决策技术形态，不能带着未关闭的运行时或安全问题进入 v1。

明确排除：

- Fetch、Pull、Commit、Merge、Rebase、Cherry-pick、Push；
- Reset、Clean、Stash；
- 创建、更新、评论、Review 或合并 PR；
- 删除本地或远端分支；
- 完整 Git 客户端和完整提交图；
- Issue 拓扑、GitLab、插件系统；
- 环境自动修复；
- 分享 HTML/快照；
- macOS 正式发布；
- 业务依赖、分支出生史和唯一最佳合并方式推断。

### 12.3 v1 可选

以下能力只有在不拖延核心验收且通过对应安全检查时加入：

- 用户显式启用的最近仓库列表；
- 高级区“查看对应 Git 命令”和复制按钮；
- Windows Installer；
- 用户主动触发的版本查询；
- 更完整的键盘操作和无障碍优化。

缺少这些能力不影响 v1 核心价值验证。代码签名方案在公开稳定版前必须裁定，但当前不能假定证书和费用已经解决。

### 12.4 v1.x 以后再评估

- 显式 Fetch 与合并前检查；
- Review/Checks 的更完整解释；
- 自动更新及其签名、回滚和供应链保护；
- 经过脱敏门禁的分享快照；
- 双机复现身份对比；
- macOS 构建、签名和发布；
- Issue 关联、GitLab 或其他平台。

后续功能仍需单独设计和授权，不能从本方案自动推导为必做。

## 13. 测试与验收

### 13.1 基础夹具

- 普通功能分支；
- 堆叠 PR；
- Merge commit、Squash merge、Rebase 后 SHA 变化；
- detached HEAD；
- 无 upstream 或 upstream 已消失；
- 多 worktree；
- 脏工作区；
- Git 冲突或未完成操作；
- 远端跟踪引用陈旧；
- 断网、缺少 `gh`、未登录或权限不足；
- 多 remote、多 GitHub Host 和 fork PR。

### 13.2 边界与安全夹具

- 以 `-` 开头或包含特殊字符的分支名；
- 恶意 Commit/PR 文本、HTML 和 ANSI 控制序列；
- Unicode、换行和特殊路径；
- 浅克隆和 bare repository；
- submodule 与 Git LFS；
- 采集过程中 HEAD、refs 或工作区发生变化；
- 临时目录清理失败；
- Host/Origin 和本地会话令牌异常。

### 13.3 桌面状态与可用性测试

- 首次启动、重复启动、窗口关闭和异常退出恢复；
- WebView2、Git、`gh` 分别缺失，以及 `gh` 未登录、无权限、超时和断网；
- 仓库已移动、路径无权限、对象损坏和分析期间仓库变化；
- 多 worktree、remote、fork 和 GitHub Host 的选择不得自动落到 `origin`；
- Unicode、空格、长路径和特殊仓库名的目录选择与显示；
- 本地状态变化后，旧建议立即失效且不会自动联网；
- 启动时不自动查询版本、GitHub、Fetch 或执行其他隐藏操作；
- 配置、日志和调试包中不存在未授权的路径、remote、正文或凭据；
- 新手不打开关系图或技术详情，也能指出当前仓库、worktree/branch、成果所在层、事实新鲜度和首要下一步；
- 专业用户能够从建议追溯到规则、快照和原始证据。

### 13.4 建议引擎黄金测试

- 为每类支持目标建立固定 JSON 快照和期望输出；
- 同一快照、目标和规则版本必须产生相同的首要建议；
- 硬阻断必须覆盖低优先级启发式，不得同时显示相互冲突的首要建议；
- 缺少目标 branch、remote、PR、权限或最新查询事实时必须得到 `NEEDS_CHECK/UNAVAILABLE`；
- 快照失效后不得继续沿用旧建议；
- Squash/Rebase 导致 SHA 改变时，不得只凭 SHA 宣称内容未合入；
- 每条黄金输出核对建议、证据、权限、风险和失效条件；
- 不在支持列表内的目标必须明确说明暂不支持，不生成泛化建议。

### 13.5 v1 验收标准

- 相同快照产生稳定、可解释的动作结论；
- 每条结论都能追溯到 snapshot_id、rule_id 和输入事实；
- 用户选择目标后只出现一条首要建议，证据不足时不猜测；
- 技术状态与授权状态不混淆；
- 本地、远端跟踪和 GitHub 查询事实不混淆；
- 读取本地、查询 GitHub、Fetch、整合、Push 和 PR 操作在 UI 中不会混名；
- 未知或不可用不会显示成空白绿灯；
- 快照过期后建议不可继续使用，多 remote/fork 场景不猜目标；
- 在已覆盖场景中不改变 HEAD、refs、index 或工作树；
- 启动和只读刷新不会发起未声明的远端写入或后台更新；
- 恶意仓库文本不能形成命令、HTML 或 ANSI 注入；
- 发布物能显示自身版本并提供可核对的 SHA-256；
- 核心任务对照能够证明相对现有产品的差异价值。

## 14. 已接受风险

- GitHub 状态在查询后仍可能变化，所有结论只能绑定观察时间和失效条件；
- Git 无法恢复未记录的业务语义、分支出生史或队友未推送成果；
- 多数据源无法形成真正的跨系统原子快照；
- 用户选择的目标可能不完整或选错，目标对象不唯一时只能要求确认；
- 规则可能与仓库临时约定冲突，未采集到的团队规则不能由工具补猜；
- 新手可能把建议误当成命令，因此建议必须显示影响、权限和失效条件，v1 保持只读；
- Wails、WebView2 和系统更新可能引入兼容性变化，正式选型前必须完成样机和支持范围验证；
- Portable 构建不能消除 WebView2 运行时依赖，缺失时只能停止并提示安装；
- 最近仓库和调试信息可能暴露项目名称或路径，因此默认不保存最近记录，导出前必须预览；
- 代码签名和 Installer 尚未确定，未签名构建可能触发系统信誉提示；
- “已验证范围内只读”不等于未经证明的字节级零写入；
- `gh` 缺失、断网或无权限时，GitHub 层只能降级，不能补猜；
- Star 数量不可预测，不作为产品验收条件。

## 15. 开源和求职价值

这个项目的价值不应靠“图画得更漂亮”证明，而应来自：

- 对 Git 本地状态和 GitHub 协作状态的正确分层；
- 明确区分事实、声明、推断和未知；
- 可复现的规则引擎与边界夹具；
- 不依赖大模型、无需 Token 的确定性下一步建议；
- 低安装成本的 Windows 桌面体验和不锁死 macOS 的分层架构；
- 只读、安全、隐私和权限模型；
- 新手能理解、专业用户也能核查的界面。

Star 可以作为采用信号观察，不能作为是否完成、是否专业或是否值得求职展示的唯一依据。

## 17. 审查结论与当前停止点

本方案此前经过两轮独立审查，本轮又针对桌面客户端方案进行了一次结构化对抗式审查：

- 第 1 轮发现三个阻断问题：动作范围被单一绿灯掩盖、跨来源快照不一致、只读与 HTML 安全契约不足；
- 修订后，第 2 轮确认三个阻断问题均已关闭，未发现新阻断；
- 最终结论为 `PASS_WITH_ACCEPTED_RISKS`；
- 独立远端仓库的归属裁定保持有效；
- 此前新增建议引擎后完成了结构化对抗式审查：重点检查陈旧快照、目标歧义、规则冲突、权限混淆、SHA 变化、业务依赖不可见和建议被误当命令等风险；
- 上述风险已通过快照失效、固定目标、规则优先级、`NEEDS_CHECK` 降级、证据与权限分栏、黄金测试和 v1 只读边界降低；Git 无法观察的业务事实仍是已接受风险；
- 桌面端审查发现四项需要直接修订的问题：浏览器开发入口与正式产品形态混淆、单 EXE 掩盖 WebView2 依赖、桌面配置和日志隐私缺口、`Repo Compass` 近似名称较多；这些问题已分别通过条件式 Wails 决策、运行时门禁、最小本地持久化和更名关闭；
- 首页已从“图和数据层”改为“位置、风险、目标、下一步”，单一绿灯、多 remote 猜测、旧快照继续建议和含糊同步按钮均被列入验收阻断条件；
- 仍需通过 v0 实测或后续环境验证的事项是 Wails 版本与兼容性、包体/启动/内存、WebView2 缺失流程、macOS 最小构建、Installer、代码签名和更新策略；这些项目没有被写成已完成事实；
- 当前只完成方案与审查，没有实现代码、创建远端仓库或执行远端写操作。

下一步必须由操作者另行下达命令。建议先制作 v0 任务流原型、Wails 技术样机、RepoSnapshot schema、三类核心决策表和黄金测试夹具，不直接进入完整桌面界面开发。
