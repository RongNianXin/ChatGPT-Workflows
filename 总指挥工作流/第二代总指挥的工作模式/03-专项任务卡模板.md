# 专项任务卡模板

修订：2026-09-19.1（区分成果运输、授权请求与租约转移）

专项接收多项请求时沿用 `02-总指挥核心规则.md`“多项请求覆盖与复杂度分流”，只在自身角色和有效授权内处理；未完成项写入自己的既有短状态并回报，不另建中央记录。该约定不自动扩大任务范围或加载到尚未读取新版的窗口。

专项任务不重新裁定母项目的主场景。任务卡已经绑定场景时，第一次实质回复用一行说明 `执行入口：沿用母任务场景 X / 专项任务卡；依据：本卡目标。` 使用者直接向专项任务提出新的独立目标，且当前角色有权按正式场景路由时，才按 `02` 输出“场景判断”；没有正式场景或只是同一工作项的连续反馈时不强制重复。该说明不扩大任务卡、角色、通信或授权边界，也不构成完成凭证。

本卡只在 `02-总指挥核心规则.md` 的专项任务总 Token 净收益门禁通过后，由总指挥自动生成，不是人工表单，也不是普通代码工作的必经步骤。字段从当前指令、事实源和已确认批量执行卡取值；无法核验时写“待确认”。状态枚举以 `04-状态、目标变更与交接规范.md` 为主来源，本卡只镜像例外专项任务独立执行所需的最小集合。简单只读或局部低风险工作默认留在总指挥主窗口，不创建本卡。

## 执行与独立审查角色卡

命中不同 Agent 实例分别执行和独立审查时，完整读取 [执行与独立审查协作规范](docs/EXECUTION_AND_INDEPENDENT_REVIEW.md)。执行者和独立审查者是工作项逻辑角色；只有新建专项窗口或现有专项任务需要补齐契约时，才在下方通用卡补充：原身份、逻辑角色、共同契约、成果版本、审查范围、问题编号、本批轮次及上限、同问题累计尝试、返工政策、下一行动方、双方配对及收口方、实际通信授权和确认状态。角色阶段提示词复用该规范第 7 节，不维护第二份。

内部子 Agent 使用主规范的共同契约和短状态，不强制套用下方独立任务窗口的创建及握手字段；载体、执行环境、生命周期及回收责任按主规范登记。总指挥或普通任务承担逻辑角色时保留原身份，不强制套用专项任务卡；存在项目总指挥时，中央调度和单写权仍只属于登记中的唯一总指挥。已有任务换任只恢复联络，不创建重复任务；手册场景五是执行—独立审查协作入口，旧 2F 仅为兼容别名。

## 任务卡

### 工作区状态交接（必填）

- 开始基线：分支或 worktree、代码 Commit、允许修改路径、`git status` 摘要
- 结束/暂停回报：实际修改路径、验证结果、未提交/未跟踪文件、最新 `git status` 摘要
- 默认边界：不自行 Commit、Push、合并或覆盖他人未提交修改；需要时由总指挥另行制卡确认

生成卡片时只输出核心字段和实际触发的条件段；同一事实已有可靠记录时引用该记录，不重复填表。必要字段未知写“待确认”及受影响动作；没有 GitHub 对象的任务不生成空 PR、Issue、Assignee 或远端账。

```text
任务标识与标题：逻辑工作项、母任务和已确认决策版本；真实任务 ID 仅运行时使用
目标与验收：范围、排除项、逐项通过/失败标准
输入与基线：必要证据及缺口、文件/数据/代码身份、来源分类
角色与写入边界：执行者、唯一写者、负责路径、汇报对象及收口方
适用规则：当前场景、加载记录与适用标题/指纹；不继承旧任务已读状态
允许与禁止动作：当前授权来源、对象、动作、有效期、失效条件及硬禁止项
执行路径：最小方案、阶段依赖、可继续的独立分支及验证
预算与停止：修复、重型运行、独立审查分别累计；按 09 核对
当前状态与证据：完成边界、未完成项、实际验证/未验证及凭证
下一步与恢复：当前行动方、动作、阻断/恢复条件、既有短状态位置
```

条件段按下表触发，同名事实不在多个段落重复抄写。依据不足可能影响权限时，保留待确认字段，不以“未触发”隐藏风险。

| 条件 | 必须补齐的契约与主来源 |
| --- | --- |
| 独立专项窗口 | 创建方式、历史继承明确依据、创建净收益、主窗口保留边界、运行环境类别、稳定恢复位置；独立新任务用 `create_thread`，只有明确复制历史才 Fork。通信握手授权及状态必须分开，测试消息不带项目资料；失败由总指挥只读回收或最小人工转交，不自动重建。换任联络按 04，平台 ID 不写公开文件。 |
| 执行与独立审查配对 | 沿本文件“执行与独立审查角色卡”和 2F 共同契约，补成果版本、问题、轮次、同问题累计尝试、返工政策、配对及授权路由、确认状态；内部子 Agent 不填独立窗口创建/握手表。 |
| 协作对象、2A/3A/3B | 按 02/10 引用 Goal、轮次/增量截点、交付模式、场景分区及冲突、身份卡、目标命中与纳入证据、弱关联明确选择、发现事件及映射；同对象引用唯一执行记录。责任证据、候选负责人、实际实现者与 PR 作者分列，不自动设置 Assignee。 |
| PR、Issue 或远端动作 | 引用 09 精确授权卡和 PR 标准：对象/Base/Head、责任与分支隔离、可审查性、直接父项、Review 资格/绑定 Head、checks 与 Actions、最低批准与 Reviewer、动作必要性和交棒终点。分项核对 Assignee 等权限及回执、语言/格式、结果未知与有权纠错回退；checks 为零继续查 Actions。过时对象 Close 与 Comment 权限不能互代。 |
| 本地闭环实现 | 使用下方 2B 附加字段，已由核心或既有工作包记录的事实只引用。公共契约、复用/抽象、兼容性与可观测性按当前证据评估，不为假设未来扩展。 |
| 高资源、浏览器、服务或 Office | 按 05/09 和测试手册补负载、串行顺序、次数/总时限、运行身份、停止/释放方式及证据。先声明验证类型为流程／生成效果／两者：流程只验证正式入口、交互和运行状态；生成效果还须锁定素材清单或 manifest、原图哈希、模型/资产、参考边界或人工判据及效果阈值。生成效果缺素材、样本或判据时，自动降级为流程、运行身份或接口验证，不得声称效果已验收；提示补齐缺口，不猜测素材库。默认无头单 worker；前台控制须精确授权。Office 只处理明确对象与验收所需文件；依赖缺失按既定降级停止，不能随意换工具。服务须记录归属、端口、保留/关闭条件。 |
| 人工参与、专业或生产门禁 | 按本文件“人工参与判定与交棒”区分必须/建议、阻断范围、操作包、反馈版本与证据；外部责任及通信权限单列，AI 不代签专业验收。 |
| 模型调整确有依据 | 默认沿用当前配置，按 05 选择最低充分能力；只记录实际可用且可回读的模型/推理设置及调整理由，未知写待确认，不要求无依据手动调档。 |

委派须附 09“已有授权随委派传递”的最小可核验依据；卡片或另一个 AI 自述不产生权限。实质决策引用原记录中的可迁移决策回执：对象、问题、选择、证据、未采用方案、事实截点、失效条件和下一行动方。派生对象纳入原工作包核账，不再建立第二份账本。

## 跨任务写入协作事件包

专项没有目标目录写入租约时，先按 09 判定事件类型，不得把租约冲突写成“等待总指挥授权”。事件只写入本任务既有短状态或消息，不另建台账：

```text
事件类型：WRITE_HANDOFF / AUTH_REQUEST / LEASE_TRANSFER
事件 ID、逻辑工作项、状态修订与事实截点：
来源角色、目标角色、收口方与回执要求：
目标项目、资源范围和当前权威入口：
用户业务授权：依据、对象、动作、有效期、失效条件
写入租约：当前写者、世代、lease_revision、状态、允许写入类别、失效条件
成果与证据：内容摘要、目标文件/位置、验证、证据指针或哈希、未验证项
禁止项与结果未知动作：
唯一阻断类型：无 / AUTHORIZATION / LEASE / EVIDENCE / DELIVERY / OTHER
当前唯一动作、执行者、通过标准与完成回执：
```

- `WRITE_HANDOFF`：运输已核验成果给现任写者；不请求新授权、不改变租约。接收方只在既有业务授权与有效租约覆盖时写入，并回传实际落点和验证。
- `AUTH_REQUEST`：仅用于拟执行动作超出现有用户授权；列出差额对象、动作、风险和失效条件，不夹带租约转移。
- `LEASE_TRANSFER`：仅用于更换唯一写者；列出旧写者停止证据、在途/结果未知写入、目标世代和原子更新/回读。它不产生业务授权。

同一事项同时缺授权和租约时，分别列为两个事件或两个独立条件；先解决哪个由依赖决定。最终回复必须写明唯一阻断类型、证据、当前唯一动作、执行者和所需回执，不能只列候选清单。

## 场景 2B 本地闭环执行卡附加字段

场景 2B 只补充核心卡尚未覆盖且本工作包实际适用的字段；已有记录用指针引用。远端、人工验收、生成器、服务和 Commit 字段分别按实际对象及授权触发，必要未知不能省略。不要求使用者查询 Git ID、分支或历史记录。

```text
场景路由结果：A-新目标 / A-恢复已知本地工作 / B-本人负责对象续作 / B-他人负责对象推进 / 混合场景 / 不适用 / 恢复场景
用户场景提示：自动判断 / A / B
路由依据与置信度：高 / 中 / 低；列出 Git 状态、远端对象、责任和基线证据
自动纠正或暂停：无需 / 已由【原提示】纠正为【实际场景】 / 待确认【责任、历史、权限或基线问题】
本地工作包 ID 与边界：
需求与证据材料入口：自动发现 / 【文件、目录、链接或对象指针】
材料分级清单：正式需求或团队决定 / 已确认事实 / 项目候选规则 / 参考资料 / 反例或回归样例 / 过时或重复 / 冲突 / 待专业确认
使用者补充目标与人工关注点：无 / 【只记录增量，不要求复述资料】
需求—证据—验收矩阵：逐项记录目标、来源与强度、实现差距、拟达到程度、自动验证、人工样例/现象、核验时机、责任方、通过/失败标准、专业门禁和失效条件
材料冲突与缺口：无 / 【冲突内容、不能自动采信的原因、缺失材料及影响】
起始默认分支及提交：
隔离方式：现有安全分支 / 新任务分支 / 独立 worktree / 待确认
当前分支、上游与工作区状态：
来源不明或目标外修改：无 / 有【归属、保护方式、禁止操作】
信息不足恢复结果：不适用 / 【从任务记录、Git Diff、未提交/未跟踪、与任务有关的忽略项、依赖、配置、模型、资产和已有验证恢复的正式候选、无关修改、临时内容、待确认项、置信度与证据】
并存实现与选择器核账：不适用 / 【实现、入口、默认/回退、实际运行值、推荐处置、证据和未决项；不要求操作者填写】
关联远端对象：无 / 【Issue、PR、Base/Head、分支、作者和状态】
继承协作证据：无 / 【Review、Comment、CI、冲突、未闭环意见和当前行动方】
责任分类：使用者本人负责 / 他人负责 / 已明确共同负责 / 已正式交接 / 待确认
责任边界结论：可本地续作 / 只读分析与方案 / 等待交接 / 拆分工作包
允许的本地动作：明确文件、修改、测试、构建、截图、生成器、本地 Commit 及次数或阶段
本地禁止动作：至少包含 Push 和所有未精确授权的远端写入；按事实补充分支覆盖、清理未知修改等
低干扰运行计划：默认重型步骤串行、浏览器无头单 worker；能用 DOM、截图、日志、像素或结构化状态取得同等证据时禁止升级前台控制；确有缺口时只暂停受影响步骤，列明拟用工具、原因、范围、预计前台影响和关闭方式，取得当前精确授权后再运行；开发服务关闭或保留条件；出现卡顿后的断点与降载动作
公共契约与兼容性边界：无 / 【接口、数据、生成物、配置或团队共享行为】

人工验收运行身份：目标候选、代码基线、入口/命令、规范启动命令及自检输出、实际 profile/开关、依赖、模型/资产/配置指纹、端点/进程来源、页面可见版本和最近回读时间
本地 Commit 检查点：触发时机、提交范围、提交前验证和回退点
耐久 Commit 台账：记录位置、最后 `COMMIT-LEDGER`、`KEY_NODE` 标记与原提交到发布提交的映射
主线/依赖同步检查点：触发时机、只读检查、允许的本地集成方式和冲突处理
每轮继续条件：人工反馈未改变范围、契约、责任和禁止项
发布候选条件：自动验证、人工验收、工作区、基线和继承意见必须满足的状态
发布前回读：默认分支、远端对象、责任、Review、Base/Head、CI、冲突、隐私和未提交修改
远端发布卡状态：未到达 / 待生成 / 已生成待确认 / 已确认【卡 ID】 / 已执行并回读
本地闭环截点：基线 Commit、本地检查点 Commit、工作区状态、人工验收版本和事实时间
```

一个混合目标必须按工作包分别填写本节。`B-他人负责对象推进` 在没有可核验交接或明确授权时不得直接写入对方分支；但交付推进可以建议在经确认的本人独立修复分支上实现和验证。是否采用补丁 PR、交付 Commit、Cherry-pick 或更新原 PR 分支，留到精确远端发布卡决定。任何本地卡中的 `Commit` 都只指本地检查点，除非另有已确认的远端发布卡，否则不得解释为 `Push`。

## 场景 2B 远端发布执行卡附加字段

本节只定义执行卡结构；授权风险和终态动作门禁仍以 `09-自动化授权与风险分级.md` 为准。每个目标 PR 单独填写，不得用一行“自动提交并合并”合并多个动作。

```text
发布审查阶段：发布归属预审 / 正式发布候选审查 / 紧急发布豁免审查
紧急发布豁免：不适用 / 【原因、未完成人工验收、明确风险接受、回滚/停止条件和确认原文】
发布门禁状态：自动验证、人工表现验收、独立 Review 和其他外部门禁分别为 已满足 / 未满足 / 不适用 / 待确认；人工反馈为未执行、不确定或空白时不得写“已满足”
卡片可执行性：预审草案、不可执行 / 正式卡、待使用者确认 / 已确认【授权范围】
发布对象策略：只使用现有 Issue/PR，禁止新建 / 允许建议新建但本卡不创建
本地安全存档分支与完整检查点链：
本地候选范围：Commit 区间、已跟踪未提交修改；未跟踪目录及排除项
发布归属矩阵：本地 Commit/文件/代码块｜现有 Issue｜现有 PR Head｜匹配依据｜置信度｜重叠/冲突｜结论（进入目标 PR / 暂留本地）
未匹配或暂留本地项：无 / 【单元、原因、恢复条件】
目标 PR：编号、URL、作者、责任与当前状态
锁定远端事实：默认分支 Commit、PR Base/Head 名称与 SHA、最后实质事件时间
分支权限与责任依据：当前账号、维护者编辑、团队安排、并行修改和禁止项
目标本地载体：基于锁定 Head 的独立 worktree/分支；不得改写存档分支
移植方式：整颗 Cherry-pick / 按文件应用 / 按代码块应用 / 无；预期生成的新 Commit
冲突处理：允许范围、验证、失败回退和失效条件
验证：移植前后测试、构建、Diff 与目标 PR 范围核对
继承意见：未闭环 Review/Comment、绑定 Head、是否仍有效及拟回应方式
Checks/Actions/CODEOWNERS/最低批准数/Auto-merge：当前事实与门禁
```

## 专项任务执行规则

1. 先确认任务卡范围、母任务场景和基线；按本文件开头的规则给出一次执行入口说明，再读取局部代码、规则和事实。
2. 只做任务卡允许的工作，不自行扩展成全局重构。
3. 发现新问题时，先记录证据并回传总指挥；不能擅自把新问题并入当前目标。
4. 代码变更采用“生成—验证”闭环。
5. 低风险本地动作自动执行；已精确预授权的远端动作按授权包执行；高风险、禁止项和授权外动作必须停在人工门禁。
6. 修改后必须运行匹配影响范围的验证，并完成异常、兼容性、安全和误报自检。
7. 任务完成时回传短格式，不复制大段日志。
8. 任务卡按独立交付单元创建，不按编号机械拆分。共享同一根因、同一 PR、同一冲突域或严格依赖链的多个编号可以合并，但必须逐项记录状态。
9. 只有范围、验证和资源都可独立，且把固定规则载入、重复取证、派发、等待、回执和再汇总计入后仍有明确总 Token 或关键路径净收益时，才单开责任窗口。净收益不明、同一根因、同一 PR、同一 worktree、连续 UI 反馈或普通局部实现必须留在总指挥主窗口。
10. 单项受阻时回传阻断和恢复条件，不得要求总指挥暂停无依赖的其他任务。
11. 任务卡只保存本任务的对象、基线、边界、验收、授权引用和回传要求；通用执行算法不在此重复。范围、路由、Review 与停止条件以 `02` 为准，状态与恢复以 `04/10` 为准，资源以 `05` 为准，授权以 `09` 为准。
12. 任务卡必须绑定母任务和决策版本；组合卡按场景分区解释，弱关联对象未被明确纳入时保持排除。收到“请执行”等短指令时不得吸收未决、被否决或卡外方案。
13. 远端写入前核对对象、当前 Head、仓库规则和有效授权；提交后回读平台结果。调用报错或中断时先查是否已经落库，禁止盲目重试造成双写。
14. 长任务维护一份短恢复状态并在稳定里程碑更新；专项任务不修改中央索引、总指挥热快照或其他任务记录，只回传可合并的状态增量。
15. 专项任务因额度耗尽、程序异常或账号切换而在新窗口恢复时，先用当前目标、工作区摘要、现有产物和结果未知信号比较“直接重做”与“恢复”的成本；简单、确定、没有可复用成果或外部副作用的局部任务可以保留旧现场后直接重做，不得先通读全部历史来证明恢复。需要恢复时再从任务卡、专项短状态、负责路径、实际工作区和验证证据恢复自身断点。恢复提示词不改变本任务身份；除非使用者另行明确变更任务且满足总指挥单写者门禁，否则不得执行总指挥接管、中央世代登记、全项目 remote/账号核验或卡外队列重建。
16. 独立新任务必须使用 `create_thread`；只有使用者明确要求继承当前历史时才使用 Fork。Office 文件只有在任务对象或验收标准明确包含时才处理，结构验证已经满足验收或环境能力已明确缺失后停止切换工具。
17. 视觉观察任务只能写预先指定的本轮结果卡，不得取得代码、中央状态或远端权限；其观察结论不替代代码验证、独立 Review 或专业验收。

## 人工参与判定与交棒

本节是人工参与执行协议的唯一主维护位置。人工操作包只面向本轮身份卡中的【使用者本人】，即当前与 AI 交互并承担最终确认的人。专项任务在请求使用者本人参与前，必须先判断：AI 是否确实缺少必要权限、工具能力、人类观察、专业资格或业务决定；该人工步骤是否会产生继续执行所必需的新信息或授权。如果只是当前专项任务缺少工具或上下文，先回传总指挥判断能否改派给其他已授权能力。能由 AI 在现有规则和授权内完成的步骤不得转交给使用者本人，也不得要求其阅读原始日志、查找技术 ID 或代替 AI 做可自动完成的判断。

使用者本人的人工参与分为：授权确认、手动操作、试运行、人工测试、人工核验或专业验收、业务或技术决策。试运行用于在指定环境首次运行并采集事实；人工测试用于按步骤验证功能行为；人工核验或专业验收用于 AI 无法替代的感知、专业判断或正式签认。每项还要分为“必须”或“建议”：不执行会阻断对象、授权链或本轮继续推进的属于必须；不执行仍可继续、只会降低体验证据或纠错把握的属于建议。建议项不得进入阻断队列。每项都必须标记“是否阻断当前对象”和“不执行的影响”；单项待人工只暂停该对象中依赖反馈的部分，总指挥仍须继续其他无依赖任务。多个请求应按依赖和紧急程度排序，内容相同的请求合并，但不同对象的状态和反馈仍分别记录。

人工操作包采用“AI 预填、操作者处理例外”的方式，不把内部字段原样变成人类问卷。使用者不记得改动、没有验收记录、看不出结果或描述尚不完整时，均按有效的“不确定”信号处理：AI 先保护现有工作区并完成可自动读取、比较和验证的部分，再只询问机器无法替代的一个观察或决定。统一反馈状态为 `通过 / 失败 / 部分通过 / 未执行 / 不确定 / 不适用`；空白、沉默、`未执行`和`不确定`都不是通过，也不应阻断无依赖工作。

建议回答必须是可选示例而不是预设事实。默认提供 `符合预期，请按当前结果继续`、`不符合预期：【简短现象】`、`我不确定，请继续自动核对`，必要时增加 `我没有执行这项检查` 或互斥业务方案。AI 不得默认勾选“通过”，不得替人填写视觉感受、风险接受、隐私决定、专业结论或正式签认。已有人工反馈必须形成绑定版本或 Head、工作区指纹、输入、步骤、观察点、结论、证据和事实时间的回执；绑定事实未变时复用，实质变化时只重问受影响项。

需要本轮协作成员、其他团队成员、领域专家或管理员行动时，不生成面向他们的人工操作包；应记录对应外部责任状态、所需动作、恢复条件和交棒终点。需要平台传达时，只有内容能增加新证据、结论、阻断、交接或验收价值，且本轮授权精确包含相应 Comment、Review 或其他远端动作，AI 才可发送并核验回执。未授权时，把待发送内容纳入批量执行卡或最小补漏卡，并只向使用者本人生成授权确认操作包；现有记录已充分时不得重复评论。

每个需要使用者本人参与的事项必须生成以下操作包；不适用字段写“无”，不能省略到只剩“请确认”或“请测试”。字段用于完整记录，面向操作者先按下方“每次汇报的下一步说明”给出最小动作；不得要求先阅读全部内部字段，重要风险和授权范围仍须在确认前清楚展示：

每次请求授权确认前，AI 必须先用一段人话概览说明：准备做什么、为什么现在需要做、会改变什么、主要风险/资源占用和预计耗时、成功时会得到什么，以及异常时会如何停止或需要操作者反馈什么。概览用于让操作者判断是否同意，不替代下列精确对象、动作、有效期、失效条件、风险和禁止项，也不把普通进度告知变成新的授权请求。

```text
人工操作包：【序号】
级别：必须 / 建议
类型：授权确认 / 手动操作 / 试运行 / 人工测试 / 人工核验或专业验收 / 业务或技术决策
是否阻断当前对象：否 / 是
不执行的影响：说明会阻断什么；建议项明确写“不阻断主流程”及缺少的证据或纠错机会
当前需要：一句话说明需要使用者本人提供的授权、观察结果或决定
AI 已自动恢复和核对：用简明语言列出已确认事实、证据、置信度，以及无需操作者回答的技术项
仍需人工判断：只列机器无法替代的一个观察或决定；没有则写“无”并取消本操作包
推荐方案及原因：给出 AI 推荐；无唯一推荐时说明关键取舍
准备好的页面、输入与基线：AI 自动填写；不适用时写“无”
操作步骤：按顺序列出可直接执行的最少步骤
操作目的：说明该人工动作会补充什么证据、权限或判断
预期结果：说明成功时应看到的页面、输出、行为或文件变化
异常反馈：说明失败时应返回的截图、日志、报错或可观察现象
回答选项：AI 预填互斥的可直接复制选项，至少包含符合预期、不符合预期和不确定；按任务增加未执行或业务方案
默认状态：未执行；没有明确反馈不得自动变化为通过
反馈回执绑定：版本或 Head、工作区指纹、输入、步骤、观察点、事实时间和失效条件
AI 收到反馈后的下一动作：说明 AI 将继续执行、重新判断还是保持阻断
可复制的下一步提示词：根据当前对象和推荐方案预填；只为确实需要的人类观察结果或选择保留最少 `【】`
```

授权确认还必须按 `09-自动化授权与风险分级.md` 写明精确对象、动作、有效期、失效条件、风险和禁止项，并给出可直接复制的确认文本。手动操作、试运行、人工测试和人工核验必须写清前置条件与可观察结果；业务或技术决策必须给出候选方案、推荐项、主要代价以及不决定的影响。操作者回复“不确定”后，AI 必须先继续自动核对；仍然只能由人判断时，保留对应门禁并说明为什么，不得循环发送同一张空白卡。若无需继续对话，“可复制的下一步提示词”写“无”。

“可复制的下一步提示词”优先用于完成当前必需反馈或授权。用于提升操作者表达能力时，只能在当前任务已经安全处理后作为可选附注：同时保留一个日常语言最短说法，再给一个只增加一个关键概念的改进示例，并说明本次 AI 自动补齐了什么。不得要求操作者重新发送示例，不得用长提示词测验操作者，也不得把示例文本视为已经提供的观察、决定或授权。

### 每次汇报的下一步说明

本节是总指挥、普通任务及专项任务的共同汇报出口，不要求创建专项卡。普通进度简短说明即可；阶段结论和最终报告核对以下事项，不抄历史全表。

1. 给出出口前先回读 `02` 的活跃请求清单，核对实际完成、未完成、验证/未验证、阻断及恢复条件。父子关系和编号沿用原记录；子项实现或取消不自动算父项验收通过。当前任务展开剩余步骤，关联顶层任务概括状态，变化或受阻项不能藏在“其他”。例如任务1暂停且剩1.3，处理任务3后仍保留该断点。
2. 写明下一行动方和最先动作。已授权、前提满足的 AI 工作直接继续，阶段汇报不结束整项目标；无剩余则说明“无需操作”，不造新任务。顺序服从当前优先级、安全和依赖，不机械选最小编号；暂停不自动恢复。现在只给一个最先动作，不等于丢弃其余未完项。
3. 确需新授权时，收口方先准备可审阅结果，再给完整可复制文本：对象、动作、范围、有效/失效条件、风险、禁止项；资源动作补次数、耗时和停止条件。已知技术值由 AI 预填，用户只确认；模板、沉默和短确认不能扩大权限。
4. 确需人工操作时，按“人工参与判定与交棒”给当前最少步骤，明确在哪做什么、目的、预期及异常反馈，必要准备和安全条件不可省；只询问机器无法补齐的观察或决定。AI 与人交替时明确顺序及交棒条件，不把查询 ID、技术判断或获准内部记账交给人。
5. 等待或停止时写清谁在等什么、谁解除、恢复条件及操作者是否需要动作。需重新发起则给触发条件和预填文本；未设置并验证自动跟进，不承诺跨回合续跑。保存证据及受阻范围，不用新授权绕过次数或硬禁止。

下一步说明必须让操作者拿来就能做，不能只列“修改 README、重新打包、运行测试”等项目待办：

- AI 已获授权且前提满足时，AI 直接继续执行，不把内部待办改写成操作者的下一步，也不要求操作者再发“继续”。
- 需要操作者在软件、网页或命令行中操作时，只突出当前最先动作，并写清操作位置、可直接执行的步骤或命令、目的、成功时应看到的结果，以及异常时应反馈的截图、日志或报错。后续步骤可作为路径说明，但不能让操作者自行判断从哪一步开始。
- 需要操作者另发消息给当前 AI 或其他 AI 时，必须提供标题为“可直接发送”的独立 `text` 代码块；正文预填已知对象、范围、禁止项和验收标准，只给确实需要操作者补充的内容保留占位符。不得只写“让 AI 处理”“开一个新任务”或复述待办事项。
- 无需操作者动作时明确写“无需操作，AI 将继续执行”；已经完成且没有剩余事项时写“无需操作”。

跨窗口候选建议标明“候选、不可执行”；候选不得包装成可直接复制执行的提示词。阶段结束后按 2F 的唯一当前行动协议交收口方，非收口窗口不另签下一阶段。投递分别写“候选已由收口方确认接收”“候选已发送待确认”“候选尚未送达”，均说明现在不要执行、等待统一安排；发送成功不证明对方已收到。冲突只暂停冲突域，不按消息先后猜测。操作者直接发给本专项窗口的明确指令，阶段内有效且无冲突时照常执行，改变契约则交收口方更新，不要求重复授权。

下一步要发给其他窗口时，先按 [02 模板入口](02-总指挥核心规则.md#为其他任务窗口准备提示词)核对模板；用户保留手发权时不代发。换任、换聊天继续主线或归档前，按 04“换窗与归档前连续性门禁”先生成至少一种可续接材料，不能只给空模板或“新开窗口”。当前最小动作完成后回原请求清单核账，不把局部完成写成整轮完成。

## 状态含义

- 已完成：验收标准满足，有可复现证据。
- 待处理：已纳入本轮执行范围，但尚未开始。
- 处理中：已开始执行且存在可验证活动，不得与“等待外部”混用。
- 已完成部分写入“本地动作”或“远端动作及回执”；仍有后续门禁时，任务状态使用对应的待人工、待协作成员、待领域专家、待管理员、暂停或阻断，不另设模糊的“部分完成”。
- 待人工：需要使用者本人选择、授权、人工操作或验收。
- 待本轮协作成员：需要身份卡中指定的本轮协作成员继续处理。
- 待其他团队成员：需要本轮身份卡以外的已知团队成员继续处理。
- 待领域专家：需要领域专家或验收方判断。
- 待管理员：需要权限、仓库设置或平台操作。
- 暂停：因目标、排期或资源原因暂不继续，保留恢复条件。
- 阻断：当前继续执行不安全或缺少必要前置，必须写明原因和解除条件。
- 已取消/被替代：目标已取消或被新目标替代，保留原因。
- 待确认：事实或范围不足，不能安全继续。
- 已 Merge：远端已确认合并；记录合并后的必要验证状态。
- 已 Close：远端已确认关闭；记录关闭原因，不能仅因本地完成而使用。

`Comment`、`Changes Requested`、本地修改完成、已推送等是动作或阶段结果，不应替代当前状态。远端对象的 `已 Merge`、`已 Close` 必须以当前远端事实为依据。
