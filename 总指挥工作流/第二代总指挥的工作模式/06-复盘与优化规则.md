### 以后远端 Push 的固定策略（经本轮对抗式审查）

1. **先确认对象与权限：**回读仓库目录、当前分支、工作区、待推送提交范围、远端 URL 和远端基线；Push 授权必须来自当前操作者的明确授权，不能由网页可访问或 API 可访问推导。
2. **先测 Git 路径：**使用有界的 `git ls-remote` 探测目标分支。网页、API、`gh api`、DNS 或 TCP 成功只能说明对应路径可用，不能替代 Git smart HTTP 探测。
3. **单次执行与有限恢复：**探测成功后执行一次带连接/低速超时的 Push；失败按 `REMOTE_UNAVAILABLE`、`TIMEOUT`、`CONNECTION_RESET`、`EMPTY_REPLY`、`AUTHORIZATION` 或 `BASELINE_DRIFT` 分类。网络类失败只允许有限退避重试，达到上限立即停止，不留下挂起进程。
4. **成功必须双重回读：**Push 返回成功后回读远端 Head；优先用 Git 路径，若 Git 读取暂时失败，可用已认证 GitHub API 确认远端对象，但必须把 Git 读取链路记为残余风险，不能写成“所有远端检查均通过”。
5. **状态分层：**本地 Commit、远端分支可见、默认分支已包含、Checks/Actions、部署和正式入口分别登记；任何一层未验证，都不能用“已同步”概括全部结果。

**对抗式审查结论：**该策略没有把一次网络成功扩大成永久可用，也没有把 API 当作 Git Push 的替代证明；它仍保留了凭据、分支保护、Checks/Actions 和用户最终授权门禁。它的可接受限制是：规则只能限制重试和记录方式，不能修复运营商、代理或 GitHub 边缘网络。策略状态：`APPROVED_FOR_FUTURE_RUNS`。

## 跨对话身份指代歧义的复盘

## 普通规则刷新被维护清单阻断的复盘

验证覆盖旧预期摘要失配、精确模式拒绝降级、正文变化后恢复、连续漂移、结构损坏、缺文件及路径越界；均为确定性合成与本地文件证据，不代替来源窗口真实复测。未修改来源业务、未发送跨窗口消息、未执行远端写入。来源权限、文件范围、规则或宿主能力变化时重新核验。

## 故障复发性与永久修复门禁

每次出现阻断、工具错误、验证失败、提交格式错误或流程偏差时，收口前必须补做一次复发性判断：

1. **一次性环境因素**：只影响当前环境且无法由流程控制；记录环境证据、影响范围和下次识别信号。
2. **可复现的操作失误**：同一命令、输入或顺序可能再次触发；优先改用不易误用的命令、模板或自动校验，并增加回读门禁。
3. **系统性流程缺口**：规则没有要求必要检查、状态或责任；必须补入唯一职责文档和最小回归测试，不能只在本轮绕过。

若判断为第 2 或第 3 类，单次手工修补或口头提醒不能作为收口；至少要有一个永久措施（脚本/模板/规则门禁/测试）和一个可回读的验证信号。连续两次近似修补仍出现同类问题时，停止继续叠加补丁，重新检查根因、输入、工具调用方式和验收标准。

## 独立审查完成信号

独立审查不是“已派发”或“已返回一段意见”。只有审查者实际读取共同契约点名的必要正文，回报读取清单、证据指针、发现、未读项和状态，且收口方完成回读，才可登记 `REVIEW_COMPLETED`。只读到文件名、目录、摘要或平台完成标记时，登记 `UNKNOWN/INCOMPLETE_REVIEW`，暂停依赖该审查的收口动作。

### Goal 交接继续执行事故（已执行修订）

- **事实：**相关 Goal 窗口已经生成 `MATERIAL_PREPARED / GENERATED_NOT_DELIVERED` 交接材料，并同时记录平台 Goal 仍为 `active`；随后又出现“交接后的 Goal 继续从已登记断点推进”的执行和工具调用。记录不能证明操作者当时是否已点击 Pause，因此不把责任归给某一方。
- **根因判断：**“交接材料状态”“平台 Goal 状态”和“旧 Goal 是否仍有业务执行权限”没有硬性互相约束。已有文字规则要求先暂停平台 Goal，但没有把缺少平台暂停证据定义为不可继续的状态闸门。

- **边界：**这些规则只能让 AI 停止继续发起业务动作并提示操作者完成平台 Pause，不能替客户端点击暂停；真实平台状态读取和未来 Goal 行为仍需后续实战验证。

复盘不是重新规划项目，也不是增加新的管理文档；它只回答一个问题：

> 最近一批任务中，哪些流程可以在不降低执行质量和安全性的前提下变得更短、更准、更自动化？

## 1.1 工作流结论的本轮持久化规则

只要本轮对话涉及总指挥工作流、规则反馈、交接事故、广播接收、流程建议或可复用经验，且本轮没有决定立即实施工作流相关修改，必须在本轮结束前把本轮已确认的结论、待确认事项、真实阻断、下一行动方和失效条件写入主记录。不得把这类结论只留在聊天上下文，也不得等下一次复盘才补记。

操作者使用“相关文档”“记录一下”“写进计划”“保存这个结论”等自然语言时，不要求其知道文件名或位置。总指挥先按 [相关文档定位索引](../相关文档定位索引.md) 判断内容属于规则、变更履历、当前计划、故障案例、项目状态或交接材料，再选择唯一主记录；其他位置只写短指针。写入后必须重新读取主记录，并向操作者说明实际路径、状态、断点、下一步和证据入口。

如果本轮决定立即实施修改，仍须把任务契约、实际改动、验证结果和未验证风险写入对应主记录；“立即实施”只改变记录时机和内容，不取消记录义务。没有适用主记录、没有写权、写入失败或回读失败时，登记 `NOT_RECORDED` 或 `BLOCKED`，列出具体恢复条件，不得把聊天中的说明当成已保存。

记录采用最小充分形式：事实或结论、当前决定、状态、行动方、证据入口和失效条件。不得复制完整聊天、完整日志或在多个文件建立互相竞争的同义记录。

状态语义必须区分：`OPEN`（已决定要做但尚未完成）、`BLOCKED`（目标仍有效但当前无法继续）、`EXCLUDED`（本轮明确不做，且不是遗漏）、`CANCELLED`（原要求已取消）和 `SUPERSEDED`（被后续方案替代）。“未生成”“未配置”“尚未完成”等表述只能用于 `OPEN` 或实际缺口；对于 `EXCLUDED` 必须写“明确不做/不纳入本轮”，不得把它列入未完成项或待办清单。收口前逐项检查：计划项、未完成项、排除项和已取消项分别列出，避免把架构选择误报为施工欠账。

### 交接复杂度复盘（已实施，本地验证通过）

本次案例显示，交接失败的主要根因不是缺少更多手续，而是把三类不同生命周期的事实绑在同一条失效链上：不可变交接证明、持续变化的中央状态、以及交接期间使用的规则基线。现行修订将候选材料的 `rule_baseline` 快照与公共规则源 `live_rule_epoch` 分开；冻结期间规则根变化先分类并只暂停受影响阶段，兼容更新不要求操作者选择版本，重基线完成后才生成新候选。正式接管后，普通进度更新只写中央 CURRENT/状态索引，不自动追加 `CURRENT_ATTESTATION` 或撤销已完成接管；只有身份、授权、规则根、单写者或控制面结构等高影响变化才追加证明并重核受影响动作。

验证器同时把“调用缺少外部控制面根目录”报告为 `INPUT_REQUIRED`，不再伪装成来源损坏；封条允许早于事实截点的真实来源观察，只拒绝未来观察；正式附件回读实时 Git HEAD、树、分支和工作区计数，避免旧草稿通过。仓库级契约、封条、附件生成和质量检查均已通过；真实跨窗口交接和宿主自动遵循行为仍待后续任务观察。证据入口：`.github/scripts/Test-HandoffSeal.mjs`、`.github/scripts/Test-Prepare-Handoff.mjs`、`Test-WorkflowRefreshContract.mjs`、`Test-Repository.ps1`。失效条件：规则基线、验证器接口、中央写者或真实交接证据再次变化。

### 诊断入口与连续执行

2E 的人工反馈入口与 2C 的系统诊断方法职责不同；错误数量不能证明根因或复杂度。内部阶段帮助 AI 保证取证顺序，不应自动变成操作者审批轮次。采用[诊断标准 2.1](docs/PIPELINE_DIAGNOSIS_AND_ALGORITHM_TUNING_STANDARD.md#21-2e-分流与-2c-连续执行)统一按证据分流、绑定已有授权和总资源边界；只在真实缺口处局部停止。算法效果审查需检查方法适用假设、目标判据和分组误差，不能以无报错或一次样本改善代签效果。规则与静态检查通过不证明未来 AI 行为或实际识别率改善。

实战复核（待验证）：一次算法人工测试前，运行身份与恢复材料不一致，暂停交付测试入口有实际门禁依据；后续本地修复使电脑入口可核验，但手机通道仍受外部连接状态限制，算法错误的根因也尚未建立。过程中已获同一方案执行授权的本地步骤曾停在只读结论，之后又为可收敛的本地范围重复索取确认。当时先按 01 的 2C 连续执行和 09 的差额授权纠正执行；后续操作者澄清了结果优先、逐节点查因并推进修复的目标，已按下段修订默认交付。证据入口：本地私有任务对话回读；失效条件：出现新的项目硬门禁、授权范围证据或可复现算法归因，足以改变上述判断。

## 2. 建议的三视角审查

使用者本人、本轮协作成员和其他 AI 的建议均作为候选方案处理。总指挥从工程、程序实现和 AI 执行三个视角做一次合并审查，区分事实、推断、偏好和待确认事项。审查深度与影响相称：简单建议静默检查，不建立三个重复任务或输出三份报告；只有发现会影响结论、范围、风险或执行的问题时才说明。没有证据支持的问题不得为了“对抗式”形式而虚构。

操作者提供另一份 AI 分析并要求交叉审查时，在尚未阅读该分析且不延误必要风险处置的前提下，先按原始需求、当前代码或规则及可靠来源形成独立的简短判断，再阅读候选材料，逐项核对一致、冲突与证据缺口。已经读过材料时如实说明，不把事后反驳冒充盲审；两个 AI 意见相同也不代替原始证据、实际测试或独立实例审查。

工作流规则的新增、删除或修改默认执行下列闭环，但审查深度和复审次数按风险与证据决定：

先区分执行失误、输入/证据不足与规则缺口：已有规则能正确处理时优先纠正执行或补证，不把一次失误自动变成永久规则；明确的系统性、安全或权限缺口无需等待重复发生。新增规则须说明触发范围、可观察收益，以及读取、判断、维护和人工成本，优先替换、合并或澄清原规则。验证通过即停止；实际使用出现无收益、误触发或额外负担时，在下一次相关复盘调整或撤回，不另建评分表或周期记录。

1. 拟定最小修改方案，明确唯一主维护文档、需要保留的安全摘要和验收方式；区分正文调整与状态字段、路径、校验、恢复契约变更。后者须在既有[项目配置迁移清单](项目配置迁移清单.md)说明旧状态识别、最小迁移、责任与权限、验证及历史保留方式；不新增同义账本；
2. 修改前做与风险相称的审查：简单措辞和局部低风险修正静默快速检查；结构、权限、跨文档契约或执行行为变化时，对抗式审查目标、团队规范、权限、安全、可执行性、Token、耦合和规则冲突；
3. 根据审查结果修正方案，不把未解决的阻断问题带入文档；
4. 正式修改规则，并记录版本与实际改动；分别报告规则/工具交付、旧状态兼容验证、当前项目迁移及真实使用预检。未执行的项目迁移或实际预检不得由合成测试PASS代替，也不要求所有项目同时迁移；
5. 修改后必须做最小一致性检查和相称验证；只有形成了非平凡实际产物、影响重要、验证出现新事实、范围/基线变化，或前置假设尚未闭环时，才进行第二次对抗式复审。复审绑定实际 Diff 和验证证据，检查跨文档一致性、旧规则残留、授权扩大、正常流程误伤和复杂度，只复核变化及受影响范围；没有触发条件时不得为了凑轮次重复第一次审查。

引入 Skill 或大改路由、权限、交接等行为时，复用本次验证记录做少量合成案例：覆盖正常命中、能力缺失、不适用、输入不确定及权限受限的路径，并写明预期行为、实际检查结果和证据类型。静态文本/结构检查只能证明文档或脚本一致，不能证明模型在真实任务中会正确选用 Skill、质量已提升或 Token 已节省；没有可靠自动判据的主观效果保持未验证，等待实际故障反馈再修正。案例只针对本次变化及其直接边界，不建立常驻全场景测试或要求操作者做对照实验。

状态或校验升级的旧样例先验证“可读取、识别需迁移”，迁移后再验证正式门禁；新样例验证当前要求通过，不为兼容旧样例降低新门禁。0A/0B只加载规则，不自动跨项目改登记；实际动作依赖新要求时才按清单适配。宣布当前项目“可交接”前，必须对当前真实来源运行 `Prepare-Handoff.mjs` 的 `preflight_only` 完整预检并核对内容，单项扫描或模拟测试不能替代。中央来源或不兼容规则改变后，旧候选标为 `SUPERSEDED` 并保留；兼容规则前进建立 `RULE_REBASE_PENDING` 并定点重读，重新回读实时基线和预检，不复用未重核的旧 READY。

使用者本人简述“修改规则”“修改后对抗式审查”等同于授权完成上述低风险本地闭环，不要求其逐步重复确认。操作者点名的审查与当前阶段原定审查合并，不另加一轮；只有新证据、范围变化或产物形成后的独立风险需要时，才按第 5 步定向复审。若不同修改方向会显著改变目标、远端/生产/不可逆权限、安全边界或团队硬规则，必须在正式修改前暂停并请求决定。简单措辞修正可以静默完成，但不得跳过修改后的最小一致性检查；不得先把有争议的方案落地，再用事后审查为既成事实背书。

### 经验分层与执行落点

跨项目发现公共工作流问题时，默认由来源窗口就地总结，经已授权通信交给公共工作流的指定维护窗口统一审查、去重、修改、验证和 Commit。来源窗口最了解触发条件，应提供最小脱敏事实、预期与实际差异、已适用条款、失败机制、建议修订及反例；可以提供候选补丁，但不得据此直接修改或提交公共文件。维护窗口不得要求复制整个项目或聊天记录，资料不足只追问影响判断的缺口。投递成功不等于维护完成，是否采纳以维护窗口实际变更和验证结果为准。

来源窗口仍可在本项目已有授权内纠正执行失误、采取必要的安全暂停，或维护本项目独有规则，不必等公共规则更新。相同问题已有适用规则时优先修正派发入口、模板或执行，不机械新增规则。公共维护窗口不接管来源项目的业务结论，也不把来源窗口的经验直接当成跨项目事实。

例外直接修改仅在操作者明确指定来源窗口负责具体公共文件和提交职责、当前维护者确认释放该范围、团队规则允许且写入互不冲突时启用；否则仍提交建议，由维护窗口落地。例外完成后由维护窗口核对实际 Diff、检查结果和版本，再恢复维护责任。不要为了落实此分工新增任务、审批层或固定长表单；公开维护与通信、远端写入分别按原授权门禁执行。

1. 通用工作流只保存可跨项目复用的失败机制、触发条件和验收方式；项目特有的算法选择、入口、测试素材、设备组合与领域指标放入该项目实际生效的规则文件或既有专项记录。先识别已有规则入口，不因用户口语中的文件名另建一份不被加载的同义文件。公开工作流不保存来源项目身份、路径、数据或事故原文。
2. 已有规则却仍然返工时，先找执行入口为何绕过它：运行身份对应启动和交付检查，测试可信度对应输入预检和结果分类，恢复对应既有短状态与证据指针。只有当前任务包含实现授权时才改脚本或产品；只改规则时明确“规则已更新、自动检查待实现”。不要以增加必读文档替代执行修正。
3. 操作者负责目标、优先级、体验取舍与必要专业确认；AI 负责可自动核验的版本、输入、状态和测试事实。把“更准确、大小差不多、更快”等要求转成可观察标准，先提出最小充分定义；不同定义显著改变结果时再请操作者决定。不得让操作者猜根因、填写可自动获取的内部标识，或把其理解反馈当技术验收。
4. 对计算、实验、数据分析及其他课题研发，同样区分输入是否可信、处理是否运行、结果是否满足参考、结论是否可推广；按实际对象使用数据版本、方法、参数、仪器/软件环境和参考标准，不强制填写无关的网页、Git 或模型字段。不适用项明确省略；这不扩大平台能力、权限或专业签认范围。
5. 每项流程改进只记录所针对的返工、最小改动、可观察收益和返回主任务的停止条件，复用既有任务记录。演示或生成器先核对少量代表产物及缺失状态再扩展；达到当前交付标准即收口。响应更快是体验证据，不直接证明质量或端到端研发效率提高；没有数据不报节省比例。

运行与测试细则沿用 [自动化测试专项标准](docs/AUTOMATED_TESTING_LESSONS.md)，因果诊断与阶段演示沿用 [链路排查专项标准](docs/PIPELINE_DIAGNOSIS_AND_ALGORITHM_TUNING_STANDARD.md)，当前视图与历史分层沿用 `04/10`。本节不增加日常必填表、默认后台任务或第二个操作者提示词入口。

以下事件只触发一次 `EXPERIENCE_REVIEW_CANDIDATE` 待审事件：总指挥交接、同类故障连续两次失败、规则实质变更、稳定阶段截点，以及操作者明确要求“总结经验/沉淀经验/以后避免”。自然语言关键词不是自动发布命令；未命中明确触发时，不为“经验”全文扫描历史。

候选至少标明来源项目类别（脱敏）、适用范围、前置条件、不适用范围或反例、证据类型、脱敏状态、失效条件和审核状态。无法证明跨项目可复用时留在项目本地；审核通过只产生公共候选，不自动改变任何项目权限、规则或任务授权。

共享候选允许多项目追加，但公共索引只能由动态状态中登记的唯一维护者更新。维护者写入前回读世代、写者、租约、索引修订和文件指纹，使用预期前序做乐观校验；冲突、租约失效或来源不明时停止写入，不自动覆盖。其他项目候选或索引变化默认是外部更新，不阻断当前项目；只有当前任务依赖的条目或规则发生冲突时才暂停受影响动作。

经验加载遵循“索引先行、按需读取”：先核对索引版本/修订/指纹和项目适用性，再读取匹配条目；索引缺失、陈旧、权限不明或条目状态不是 `已采纳` 时返回 `UNKNOWN/BLOCKED` 或继续不依赖该经验的工作。公共索引 Commit、远端 Push/PR 和项目本地经验写入分别记录、分别授权。

## 3. 触发时机

- 一个 Goal 完成或暂停后；
- 集中接管一批 Issue/PR 收口后；
- 连续出现两次以上重复读取、重复任务或无效重试；
- 目标发生重大变化后；
- 交接前；
- 使用者本人主动要求复盘时。

不需要每轮微小操作都复盘。

### 按需时效核验与退役

维护由使用和变化触发，不默认创建定时任务、后台监控、自动联网或独立状态系统：

- 使用时核验：当前动作依赖模型档位、价格、产品界面、API、安装步骤或临时绕过方案时，核对适用版本、官方来源和当前环境；只检查即将使用的内容及其直接依赖。
- 变化时复盘：操作者报告升级、官方更新已进入当前任务，或旧说明实际失效、误触发、与新能力重复时，检查受影响规则。仅知道“有新模型”不触发全仓扫描，也不证明旧方案应被淘汰。
- 维护或发布前核对：对本次修改及 README 中相关时效声明检查来源和依赖；无变化且已有有效证据的不重复联网。用户明确要求一次性全面清查时另定范围，不把轻量交接变成版本审计。

按“声明/规则 → 原用途和依赖 → 当前证据 → 最小处置”判断：仍有效则保留；局部失效则更新；已由现有能力可靠覆盖则合并；确已不适用才退役。官方资料用于核实能力，必要时以当前环境小范围复现判断替代是否成立；链接仍可打开不等于内容仍有效，来源暂不可得只标待确认并暂停依赖动作。新模型的成绩不能替代单写者、授权、安全或专业验收。

退役先核对入站引用、模板、脚本、兼容路径与现有用户依赖。证据不足则保留并标明适用版本；有替代时更新入口并保留必要迁移说明。停用执行规则不等于删除历史证据；不自动删除数据、撤销权限、改远端对象或重写历史。确需破坏性迁移仍走原授权门禁。

复用本次任务记录和已有 CHANGELOG 保存有实质变化的依据、核对日期/适用版本、替代关系、验证与未验证项；公开记录只保留脱敏结论。没有变化不新增记录，不新建全仓时效台账。该机制减少重复检查，但未被使用或触发的内容仍可能过时，不能声称持续监测或始终最新。

### 外部材料的原始证据定位规则

凡是外部网页、代码仓库、公开文档、附件、第三方报告或其他非本项目材料参与了复盘、规则建议、架构比较或优化结论，记录必须同时保留以下最小证据指针：

1. **原始来源**：完整 URL、精确仓库/文件路径或操作者提供的原始附件路径；不能只写来源名称或 AI 对来源的概括。
2. **取得信息**：访问/读取日期，必要时记录版本、提交、标签、页面章节、行号、锚点或附件页码；动态网页没有稳定版本时明确标注“可回源但无快照”。
3. **支持范围**：原材料具体支持了哪条事实或候选判断；同时写明没有支持什么，不能把上游宣传、基准、推断或相关性扩大成当前项目效果。
4. **保存状态**：明确是“原始定位指针”“最小脱敏摘录”还是“经过授权的离线快照”。没有保存原文时，不得声称以后无需回源；保存外部材料仍须遵守隐私、版权、仓库范围和外发门禁。
5. **结论分离**：AI 的总结、推断和本项目实测必须与原始证据分栏或分段记录。新总指挥接手时，先回源核对仍有效的事实，再读取派生结论；来源失效、内容漂移或无法回源时，将受影响结论标为 `待确认`，不得沿用旧结论冒充当前事实。

该规则不要求为每条普通常识建立来源卡，也不要求复制完整网页；只要外部材料实质影响了当前复盘或优化决策，就必须能让后续总指挥从记录回到原始材料，并看出证据边界和失效条件。

### Goal 额度口径与操作者参数（入口与规则已落地，长期行为待验证）

操作者补充了当前使用者的额度证据：桌面客户端头像菜单中的“使用情况”和网页版设置中的“使用情况”均指向同一个每周限额，界面显示“剩余百分比”，并说明 Codex、Work、工作空间智能体和 ChatGPT for Excel 共享该额度；界面还提示大多数模式下的对话不计入此用量，因此不能把请求次数直接换算成额度消耗。本轮机器只读回执与操作者截图的剩余方向一致，支持“本环境存在可机器读取的同一额度信号”这一判断；具体动态数值只保留在本地私有状态或当前回合，不写入公开工作流文件。该工具回执不等于所有客户端、账号或未来环境都已具备同一接口。

外部能力边界依据：[Using Codex with your ChatGPT plan](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan)（核验日期：2026-09-29）。该页面支持共享额度池、周/五小时窗口和额度耗尽后的处理说明；它不支持把共享池差值归因到某一个 Goal，也不支持容量错误必然可自动切换模型。

Goal 额度配置应绑定“操作者的额度账户”，不能写死真实姓名，也不能默认套用到其他使用者。建议使用不含身份信息的本地配置键，并至少记录：额度范围为每周共享限额、单位为剩余百分比、重置周期为 7 天、可观察入口为桌面端、网页版和当前环境可用的只读用量接口。账号标签、计划名称和显示名称只作为可选观察字段；它们与额度统计口径不一致时，不得阻断读取或编造账号身份。

推荐采样策略：任务开始时建立基线；普通 Goal 在结束、平台预警或低频里程碑读取，高资源 Goal 在重型批次前后读取。只有平台接口、任务状态计数和计时器实际可观察时，才登记为自动采样；否则标记 `UNKNOWN/待确认`。额度保护只判断两个条件：当前剩余额度是否低于保留下限，以及本轮观测到的共享额度差值是否达到任务上限。保留下限默认 5 个百分点，可选 3 / 5 / 10 / 自定义；任务上限默认 `min(20 个百分点, R0-保留下限)`，也可自定义。任一条件触发后，先安全收口并保存断点、记录、未完成项和下一步，再停止；不再区分软停止和硬停止。共享额度池差值可能包含其他窗口或产品消耗，只能称为观测值，不能保证精确归因到本 Goal。读取失败、窗口重置或返回口径变化时废弃旧基线并保存断点，不根据会话长度、Token 或主观体感估算剩余额度。该策略是低频保护，不建立高频轮询或第二状态系统。

容量故障与额度故障分开处理：收到 `Selected model is at capacity. Please try a different model.` 时先保存断点，不把它写成额度耗尽或用户操作错误。Goal 入口可由操作者选择性预授权“模型故障切换”，并限定候选模型白名单、最多切换 1 次、切换后小型验收和失败回退；没有这项授权时不得自行切换。平台实际提供候选模型且授权有效时，切换后必须重新核对模型、工具、权限和一项小型验收；平台无法回读候选时暂停受影响动作并给出一次具体人工切换步骤。不得反复重试同一不可用模型，也不得把切换后的结果当成原模型结果。该故障属于平台可用性信号，当前规则只能降低中断损失，不能保证平台容量始终可用。

该条目只记录当前规则设计与证据边界，没有把操作者姓名、截图原件、账号标识或本轮动态百分比写入公开工作流文件。`01` 的 Goal 参数入口与 `05` 的采样/中止规则已经落地；当前环境和至少一个额度不可读取的环境的长期行为、模型容量故障切换和窗口重置路径仍待验证。失效条件：平台改动额度显示/接口、共享范围变化、工具回执与界面不再一致，或出现其他使用者的不同额度规则。

模型升级后的“找局限、解决旧难题、拓展功能”按当前目标处理：局限须绑定可复现差距和验收；旧难题保留失败证据与不变量后做最小对照；功能构思只形成有用户价值、代价与验证方式的候选。没有证据支持问题就明确无新增问题；构思不自动转成实现，模型升级也不扩大任务或权限。

- **对抗式复核：** “连续无改善”与“最大迭代次数”不能写成两个互相重复的硬停止；当前改为默认连续 2 轮后重新审查路线，确认无可行路径才收口。额度上限使用 `max(0, min(20, R0-保留下限))`，避免启动余额低于保留下限时产生负值或虚假的 20 个百分点预算。默认规则中的可删项不包括安全、权限和验证硬门禁。

### 操作者模板审阅与联动修改规则（2026-09-29）

1. Hindsight 只能作为可替换的记忆层，不能替代 `CURRENT`、唯一总指挥、单写者、交接封条、授权记录、工作区/远端核验或远端发布门禁。
2. 不自动摄取全部聊天、真实项目目录、私有画像、凭据、Token、Cookie、绝对路径、任务 ID 或未脱敏报告；默认只使用虚构或明确选择的脱敏样本。
3. 记忆召回只能提供候选事实和证据指针，不能自动产生授权、改变角色、写入中央状态或决定删除/退役规则。
4. 任何 MCP、Docker、嵌入式数据库或外部模型调用都必须单独登记版本、数据边界、网络边界、费用和回滚方式；没有运行证据时标记 `NOT_RUN`，不把上游基准或 README 声明写成本项目效果。

**对抗式审查结论：**

- **可能收益：** 记忆类型分层、观察保留支持证据、项目 memory bank 隔离、Memory Defense、MCP 和编码 Agent 接入，可能减少重复查找并让长期经验更易回溯。
- **主要反例：** 自动摄取可能把旧授权、错误推断或私人资料带入新任务；召回结果可能看似相关却不再适用；多一套服务会增加部署、版本、费用和故障面；Hindsight 的长期记忆基准不能直接代表本工作流的交接可靠性。
- **不接受的捷径：** 不能因为上游声称 state-of-the-art、支持 Codex 或提供 MCP，就直接删除现有文档、自动接管中央状态或把记忆命中当作当前事实。
- **停止条件：** 任一阶段出现跨项目串记、敏感数据进入存储、证据无法回指、旧结论覆盖当前事实、成本/延迟无可接受解释、无法隔离网络或无法完整卸载回滚，立即停止受影响阶段并保留测试证据。

- 主窗口与例外专项任务合计的规则载入、证据重复、派发、回执、再汇总和人工转发成本；
- 测试、截图、日志和回执；
- 重型命令、浏览器 worker 数、前台窗口、GPU stall、超时、残留服务和进程归属；
- 人工确认次数；
- 被暂停、取消或替代的任务；
- 发生的状态漂移和重新扫描原因；
- `AI状态索引.md` 中的轮次、任务、授权卡、截点和失败记录。

没有数据时标记“待确认”，不要凭感觉给出精确节省比例。

## 4.1 可复用故障的外部资料与本地收口

当运行故障、错误、性能问题或处理建议可能导致工作流规则、测试契约、恢复流程或故障知识库发生变化时，先判断是否达到可复用门槛。命中以下任一项才触发一次有边界的公开资料检索：问题涉及外部产品、版本、协议或服务端行为；本地证据不足以区分多个原因；同类排查已连续失败；或预计会形成可供其他任务复用的规则/案例。普通一次性拼写、格式、环境噪声和已有案例可直接处理的问题不强制联网。

公开检索只收集候选线索和可核验来源。记录来源、访问日期、适用版本/环境、支持的具体事实和未证实部分；网友讨论、搜索摘要和无来源推测不得直接升级为根因、修复结论或专业验收。检索前先做脱敏检查，不发送真实账号、绝对路径、任务 ID、完整日志、内部链接、凭据或其他私有材料。一次检索没有新增证据时停止，不为“曝光”重复搜索；发帖、评论、提交 Issue、上传材料或其他远端写入另行取得精确授权。

达到故障库收口门槛后，回读 `故障排查与解决经验` 及其命名约定，按以下顺序处理：

1. 已有案例：追加可回读的新证据，修订状态、适用范围、失效条件或恢复入口；不新建重复条目。
2. 新且可复用的问题：按现行 `TRB`、`HTTP`、`ERR` 或 `SYS` 命名规则建立记录，区分已确认事实、合理推断、外部参考、未验证项和验证结果。
3. 一次性或不可复用的小问题：留在当前任务记录或变更日志，不强行建案例。
4. 只有外部猜测、没有本地证据的问题：写入待确认/参考区，不能写成根因或已解决。

故障记录可以在“调查中”状态建立，但必须写明证据边界、当前阻断、恢复条件和下一行动方。记录更新、Commit、Push、发帖和其他远端发布分别核对授权；本地知识库收口不产生远端发布授权。

## 5. 检查清单

复盘只检查本轮实际发生或险些发生的问题；未触发的场景不逐项展开。详细执行标准回到对应主文档：

1. **范围与事实（`02`）**：目标、候选、依赖和排除能否核账；建议、索引和历史是否已回源；是否误纳入弱关联或重复对象。
2. **调度与资源（`02/05`）**：是否坚持单窗口主执行；例外任务是否有净收益；重型步骤是否串行、最小化且可恢复。
3. **工程质量（`02`）**：方案是否满足验收并保持简单；契约、兼容、异常输入、测试和真实根因是否有证据。
4. **授权与安全（`09`）**：本地与远端是否分开；对象、动作、有效期和回执是否精确；是否继承旧授权或绕过硬门禁。
5. **协作交付（`02/09`）**：Review、责任、分支、CI 和交棒是否基于当前 Head 与仓库规则；是否制造无价值 Comment、空提交或重复 Push。
6. **状态与恢复（`04/07/10`）**：唯一事实源、当前行动方、稳定截点、耐久 Commit 台账、`KEY_NODE`、运行身份、决策回执和恢复条件是否可回查；索引是否仍是短指针而非第二套事实库。
7. **效率与材料（`04/05`）**：是否重复读取规则、日志或附件；视觉隔离、会话切换和高成本材料处理是否有净收益，是否把冷存储误写成删除。
8. **收口与简明回执（`02/03/09`）**：计划、执行和平台回执是否分清；遗漏差集是否闭环；必须/建议人工操作是否附步骤、目的、预期结果和异常反馈方式。
9. **协作适配（`11`，仅在已启用时）**：是否只记录跨任务仍有效的抽象协作信息；一次口误、人格评价、身份、项目事实或敏感属性是否被错误写入；易错模式是否有防护动作、过期时间和反例入口。
10. **故障知识收口**：本轮是否达到可复用门槛；是否按需完成一次公开资料检索并区分来源强度；是否优先增量更新已有案例；新建案例是否具备证据边界、验证结果、失效条件和恢复入口；是否误把外部猜测写成事实。

新建独立任务必须使用 `create_thread`，并在正式工作前完成已授权的最小通信握手；若主动回传失败，开工前改为总指挥只读回收；重建须另获操作者明确授权，不得等任务完成后才发现无法交接。Office 文件只有在当前对象范围或验收标准明确包含时才处理。任务创建与通信语义以 `04` 为主来源，专项字段以 `03` 为准。

### 高 Token 架构防复发红线

以下任一现象出现即视为流程回归，必须优先简化，而不是继续在其上增加补丁：

1. 总指挥被再次禁止普通实现，导致所有代码、测试、Commit 或远端授权动作都必须经过专项窗口。
2. 默认建立事件 FIFO、Heartbeat、标题同步、收件箱和多份中央视图，并对每个微动作逐层传播同一事实。
3. 使用者需要向总指挥和专项窗口重复描述，或需要人工转发专项结果才能更新项目进度。
4. 为同一根因、同一 PR、同一 worktree、连续 UI 返工或普通局部任务建立多个责任窗口。
5. 只展示总指挥窗口 Token 下降，却不统计专项任务的固定提示、重复取证、等待、回执和再汇总。
6. 为维持调度体系而频繁加载长提示词、全量历史、完整日志或未变化附件。

安全边界不属于可删除的“管理开销”：精确 Base/Head、远端写入确认、未知修改保护、单写者中央状态、完成证据和可靠截点必须保留，但只能在风险和状态真正变化时更新。

修改规则时遵守：

1. 先确定唯一主维护文档；其他文档只保留链接、入口或一句必要安全摘要。修改公共规则、模板或检查工具时，执行下方“工作流改动与原有功能保留”；测试细节按该节指针加载。
2. 新规则优先并入现有职责，不因内容增加就创建新文件；只有出现独立读者、独立生命周期和独立加载价值时才拆分。
   按需执行手册可以在同时满足这三项时放入 `docs/`，但不得取得新的正式规则编号、产生授权或复制正式门禁；其触发入口、主规则归属和索引方式必须由 00/02/09/10 明确。
3. 操作手册不复制执行算法；任务与交接模板只维护各自契约，不定义新权限；索引不保存第二套项目事实。
4. 安全硬门禁允许简短重复，但详细条件仍回到主维护文档。
5. 默认复杂度预算不得增加。升级前比较行数、字节数、跨文件重复、必读文档、状态/字段和人工步骤；新机制先删除、替换或合并旧机制。只有不可降低的安全/权限边界，或已有证据证明净收益且没有更简单方案时，才允许增加复杂度；新增机制同时退出被替代机制，收益不能证明就撤销或缩小。等量删字不能替代收益证据，迁往支持文件的依赖仍计入成本；不能删除安全义务伪造下降。同类问题连续两次采用相近补丁仍未改善时，停止继续叠加，回到复现条件、根因、输入输出契约和最小流程；复核完成前不得新增同类字段、状态、提示词步骤或兼容分支。
6. 操作手册面向人类，只保留 AI 无法可靠读取或不能替人决定的输入，并优先使用日常语言；内部状态、算法、ID 和可自动读取的门禁不得转嫁为人工填表。
7. `【】` 只保留操作者实际要选择或填写的规则，不能混入行动规则。开放式作答、多值账号、路径或自然语言限制确实需要帮助理解时，紧跟一个半角括号示例：`【占位符填写规则】(示例：简单、抽象、脱敏的例子)`；纯选择题不加示例。行动规则另起一句。多个同类值默认用逗号分隔；AI 可以兼容顿号或分号并自动规范化。AI 输出模板中的 `【】` 是结构，不要求机械补示例。
8. 面向使用者本人的文档和回答使用日常语言。使用者按编号提出多个问题时，至少提供相同数量的一一对应小节；可以增加必要补充，但不得通过合并问题造成漏答，也不得为了凑小节机械扩写。
9. 私聊中的临时示例、评价性表述和真实项目细节只作为需求输入。公开可复制提示词应抽象为中性、专业、完整、可执行的表达，不逐字引用私聊措辞，不暴露真实人员、项目、路径或内部讨论。AI 仍须接受任意详略的自然语言入口，但不得为了展示容错能力而故意降低公开模板的专业度。
10. 文档质量检查并入现有生成、验证和审查流程，不新增审批层。新增或修改可复制提示词时，逐句确认“谁执行、执行什么、针对什么对象、在什么条件下执行”；补足省略的主语或宾语，代词须有唯一指向，首次出现的内部简称须解释或换成日常表达。作者从操作者角度完整读一遍实际复制块，确认不用猜测就能理解；按原有风险规则需要独立审查时，审查者同时核对语言及原规则语义，尤其确认润色没有改变权限、停止条件和验证义务。脚本只检测已知旧句、重复词、结构和引用，不能证明语言正确。发现问题只暂停受影响段落的交付，修订、回读并同步相关入口和摘要；不承诺永不出错，也不为语言检查另建递归规则或自动化。

### 工作流改动与原有功能保留

维护者在既有任务契约、验证和收口记录中按以下顺序落实，不新增审批层或平行账本：

1. 修改前列明允许改变的行为、必须保留的行为、实际共享依赖和上下游入口。新增或替换入口核对原入口的参数、默认值、返回状态和安全门禁。沿操作者实际入口检查“提示词→负责方→状态/文件→下一动作”，尤其确认停旧、归档或权限切换前的准备都有负责方和可观察完成条件；必要相邻修改说明因果和授权。
2. 有证据且可复现的行为故障，先把原失败变成能失败的回归，再修复；不能机械复现的人机流程保留原观察、失败判据与可核验步骤，不为凑红测伪造故障。按实际影响验证原正常路径、配置分支、边界及拒绝路径；代表性正常路径实际调用组合入口和底层状态转换，底层测试或文档关键词不能代替入口兼容与流程完成。
3. 将本轮适用的自动回归接入现有质量入口，同步实际受影响的唯一规范及轻量配置、手册、矩阵等消费者。按风险执行不同实例审查；纯文风、链接等非行为修改用对应静态检查与回读，不要求新增脚本、固定审查轮或每次全库重测。测试执行与证据复用见[测试手册2.5](docs/AUTOMATED_TESTING_LESSONS.md#25-验证时机与证据复用)。
4. 收口按实际差异核对授权与范围、受影响的保留行为及未覆盖项。范围外前后指纹只证明成果未改写，不证明共享依赖下的行为未变。发现回归只暂停依赖交付，修复或回退本轮增量，保留他人成果和安全门禁；分开报告本地验证、自然客户端观察与发布状态。缺少验证条件明确限制与恢复条件，不声称其他功能完好或绝无回归。

交接范围维护须分别验证控制面、断点必要成果和无关在途工作的生命周期，不能把全仓每次变化都当成身份变化。范围放宽须同时核工作区算法、封条sources、重基线和最终交付入口；范围外漂移拒绝与范围内允许两类回归都须实际运行。生成期间在临时附件落盘后再次核同范围工作区，采样中保护范围变化拒绝，不能只核sources。来源项目的一般修复授权不赋予公共控制面写权；非公共唯一总指挥只提交建议，公共写者统一审查、落盘和验证，历史越界不得通过改记录追认。

### 操作手册的读者与执行规则分层

操作手册只保留操作者选择场景、填写目标、复制发送、检查结果和处理异常所需的内容。供操作者复制的提示词保留在代码块中；纯 AI 内部执行规则迁入对应主规则，不靠特殊符号或折叠区继续堆在手册里。规则迁移必须同时更新读取入口、引用和检查，不能只删正文；手册提示词须能定位已分发规则，来源不可用时报告缺口。保持场景编号、角色、权限、前置条件、停止条件与验证要求不变；目标不明确的运行请求保留一个人类可填写的目标字段，不要求填写可自动核实的技术参数。

任何已经验证并可能重复使用的操作者动作，都必须沉淀到 `01-操作者操作手册.md` 或其明确引用的固定模板；聊天中的临时解释不能成为唯一长期依据。沉淀时优先复用现有入口，保留适用条件、复制边界、预期结果、异常处理和权限限制，不为同一动作制造多个互相竞争的提示词。

### 专业表达与低操作负担

文档修改、润色或评审的具体顺序、需改项、复制块和精简按[文档评审规范](docs/DOCUMENT_REVIEW_STANDARD.md)执行，本节保留通用表达原则。

公开文档以提高交付质量、减少重复操作、明确责任和支持复核为目标。以下是通用产品与文档质量标准，适用于不同领域和经验背景的操作者；公开工作流必须包含完整执行原则，不依赖未分发的私有指令才能保持一致行为。

1. 描述任务、所需输入和可观察结果，不评价操作者的智力、资历或能力；不因输入简短、口语化或表示不确定而降低技术核验标准，也不据此推断人格或专业水平。
2. 专业性来自事实准确、结构清晰、边界明确和可验证结果，不以术语密度、复杂步骤、夸张效果承诺或装饰性措辞代替质量。提供必要技术细节，不把成功率、专业正确性或用户感受写成未经验证的保证。
3. 文档与阶段汇报按“结论与下一步 → 必要操作 → 按需证据”组织；先说明检查对象做什么、实际发现、已证明范围和未证明部分。首次使用影响判断的内部节点、缩写或指标时，紧邻解释职责与含义，不能只给编号、日志链接或末尾笼统免责声明；不能把相关性写成根因、把运行成功写成修复通过。自动获取能够可靠读取的信息，预填能够确定的参数，保留用户的选择权和结果复核入口。
4. 人工步骤只保留必要决定或 AI 无法完成的观察，并包含操作、目的、成功表现和异常反馈方式。减少人工步骤不减少安全、权限、测试或领域专业验收；AI 的生成结果不得冒充这些验收。
5. 交付前检查：隐藏内部编号、代码名和日志链接后，正文是否仍交代实际发现、完成边界及下一动作；按 [03 的下一步出口](03-专项任务卡模板.md#每次汇报的下一步说明)能否分清 AI 的工作与操作者现在的确认、操作或等待，是否误把已有授权写成待授权；能否按说明操作、失败时恢复，必要证据与限制是否可查；是否含对操作者的标签、未核实承诺或来源私聊。AI检查不替代操作者是否看懂的反馈，不要求操作者复述考试；只修有依据的问题，不以猜测读者心理无限润色。

6. 当下一步确需操作者另发指令，且可减少重复表述时，默认在建议后附一个标为“可直接发送”的短文本块；这是按需便利入口，不是每次回复的固定附件。预填已确认的对象、目标、最小范围与验收，保留尚未作出的实质选择，缺失技术事实由 AI 核验，不要求操作者补全内部参数。已获授权且仍可继续的工作应直接执行；简单问答、任务已结束且无必要后续，或已有等价可复制入口时不重复附加。提示词本身不产生授权，不预置扩大范围、远端写入、费用、敏感数据处理或降低验证要求；确需授权时仍使用对应执行卡和确认门禁。多条路径只提供推荐路径的文本并简述可选替代，不用能力标签命名该入口，不为提供提示词制造新任务。

7. 所有期望操作者复制粘贴的内容都单独放入 Markdown 围栏代码块，块内只保留需要复制的正文，说明、选项差异和风险放在块外；每块对应一个完整用途。自然语言使用 `text`，命令使用对应语言，避免复制不完整的授权范围或把多个互斥动作合在一起。代码块用于提供清楚的复制边界，背景色由阅读器主题控制，不能承诺任意客户端的具体色值；自有页面可用浅色底和清晰文字实现。普通术语或检查结果的行内代码不表示要求执行。

公开规则记录可复用的行为要求、适用边界和验收方式；来源材料按已授权的隐私边界处理，仅保留必要内容。私有资料不作为公开工作流的必需依赖，不因文档整改而扩大资料收集或外发范围。

### 高增长文档健康检查

任务每次读取项目进度、当前状态、拓扑、长期任务记录或其他持续增长文档时，静默检查其是否仍适合下一次阅读和交接；不要求每次都改写。文档按性质处理：

- **当前视图**：允许由唯一维护者压缩，保留当前决策所需事实和历史指针。
- **灾难恢复热快照**：与当前视图是同一份活动文档，不另建平行事实库；优先保证空白账号能定位目标、队列、断点、验证、禁止项和下一动作。写入后回读关键字段，终态过程转为冷证据指针。
- **索引**：只保留短摘要、游标和位置，不吸收长正文。
- **人工核验轮次清单**：当前轮次可按问题最小读取；关闭后转冷并默认拒绝回读。中央索引每轮只保存一个清单指针，不展开逐张附件；清单本身不因 Token 优化自动删除。
- **视觉测试包与结果卡**：测试包只保存本轮文字步骤和基线；结果卡只保存逐步骤事实、证据 ID、冲突和最小回读入口。原图留在短寿命观察任务/轮次证据清单，不复制进总指挥热状态或交接正文。
- **唯一任务记录**：保留该任务的目标、关键判断、验证、阻断和交接；终态后可生成短终态摘要，但不能抹去必要证据位置。
- **规则、会议原文、审计账本和原始证据**：不得因变长而被普通任务自动删改；规则修改走本文件规定的闭环，原始材料保持可追溯。

任何带 `保留级别：KEY_NODE` 的提交节点都按 `04` 的耐久台账规则保护。文档精简可以迁移其过程细节，但必须在修改前后核对节点标识、提交映射、保留原因、证据指针和恢复/失效条件；缺一项就不得用精简结果替换旧可靠版本。

压缩触发和具体步骤由 `04-状态、目标变更与交接规范.md` 维护。人工核验每轮结束立即压缩并转冷；附件清理候选按 3 个关闭轮次或 30 天的软触发审查，但不得自动删除。其他文档没有过期、重复、矛盾、终态滞留或交接困难证据时，不做格式化重写；避免把节省下一次读取的收益变成每轮都要支付的维护成本。涉及移动、删除、覆盖历史文件或改变团队共享文档结构时，仍按项目规则取得单独权限。

## 7. 输出格式

本节工作流复盘最多给出 3 条改进；不限制操作者要求的文档评审数量，文档评审按[主规范](docs/DOCUMENT_REVIEW_STANDARD.md)处理：

```text
问题：
证据：
影响：
建议：
预期减少：
风险与验证：
```

优先顺序：先修复会影响正确性和安全性的流程，再减少 Token，最后提升自动化。
