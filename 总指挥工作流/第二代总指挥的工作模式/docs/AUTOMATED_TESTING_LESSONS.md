# 自动化测试经验与可信结果门禁

版本：2026-09-17.1

定位：本文件是按需加载的自动化测试执行手册，不是新的编号规则，不产生任何授权，也不代替项目测试规范、`02-总指挥核心规则.md`、`05-模型选择与资源策略.md` 或 `09-自动化授权与风险分级.md`。

目的：防止“命令确实运行了，但输入、页面、状态或结果分类错误”被误报成产品失败或成功。测试授权只回答“可不可以运行”；本文件回答“运行结果能不能作为结论”。两道门禁必须分别通过。

本手册负责证明测试装置、输入和结果分类可信；当目标进一步变为定位系统中第一处偏差、验证根因或调优算法时，同时按 `PIPELINE_DIAGNOSIS_AND_ALGORITHM_TUNING_STANDARD.md` 建立实际执行图和因果实验。测试的首个失败阶段是定位证据，不自动等于产品根因。

## 1. 何时必须读取

总指挥自己执行或指挥其他 AI 执行以下任一测试前，完整读取本文件：

1. 浏览器 UI、真实图片、音视频、摄像头、模型推理或 Web Worker 测试；
2. 新旧版本、不同 Commit、不同路由、不同算法或不同配置的对照测试；
3. 无头测试与人工结果冲突，或测试曾出现不稳定、偶发失败、难以复现；
4. 测试会改变镜像、视口、上传媒体、功能开关、缓存、模型状态等产品运行状态；
5. 批量测试、高资源测试或测试结果将用于回滚、替换算法、发布、关闭问题等重要决策。

普通、确定性的单元测试、类型检查和构建不必默认读取；一旦结果冲突、依赖真实运行状态或需要解释有效样本数，立即转入本手册。

## 2. 测试开始前的最小契约

执行者先用短表锁定以下内容；任何关键项无法确认时，先标记 `TEST_INVALID`，不得用测试结果评价产品：

| 项目 | 必须说明 |
|---|---|
| 要回答的问题 | 每个验收项只写一个可判定问题和成功/失败标准；同一授权卡可以包含多个分别判定的验收项 |
| 对照类型 | 完整产品对完整产品 / 同一产品的核心隔离；不得混用 |
| 版本与入口 | worktree、分支、完整 Head、未提交状态、路由、构建或服务指纹 |
| 运行与存储环境 | 操作系统、运行时或 shell、普通本地/同步/网络文件系统、实际路径长度及已知平台限制；无法确认时只限制依赖它的结论 |
| 输入 | 文件名、SHA-256、尺寸；必要时记录点击点、裁剪框、参数、镜像、视口和功能开关 |
| 就绪条件 | 页面、事件监听、模型、Worker、接口或媒体状态真正可用的可观察信号 |
| 实际系统输入 | 能证明产品实际收到什么的 Worker 请求、裁剪图、结构化诊断或等价证据 |
| 结果来源 | 结构化状态、返回值和页面事实；不得只匹配一条提示文字 |
| 有效分母 | 哪些运行计入成功率，哪些因测试装置错误剔除 |
| 资源与授权 | 是否高资源、worker 数、无头/可见/Computer Use、预计耗时、停止方式和当前有效授权；前台控制必须另列授权 |
| 证据与清理 | 截图、清单、指纹、日志的保存位置，以及测试后关闭本轮进程的方法 |

对照测试还必须保证除待比较变量外，其余条件一致。无法做到时，把差异列为混杂因素，不能声称因果。

### 2.1 运行身份与结论边界

- 测试启动或复用已有服务/计算进程前，按 `02` 的运行身份门禁比对目标版本、实际选择器、数据/依赖/资产和入口。能访问端点、进程存活、代码含目标实现都不能代替实际身份；自动复用旧服务不得绕过该核验。换进程、换配置或部署后重新回读受影响字段；测试与交付身份不同，只使依赖这些差异的结论失效。
- 每项测试写明能证明什么：装置可用、交互正确、数值满足参考、业务效果或专业验收不能互相代签。科研与非图像任务按自身处理阶段、方法和参考标准映射本手册，不把后文检测器类别机械套到所有课题。
- 质量统计先约定参考来源、容差、统计单位与分母；同一原始样本的多个落点或重复运行不能冒充多个独立样本。用于调参、人工挑选或反复查看的样本不再声称是独立保留集。无正式真值时报告工程近似参考的局限及未标注范围，不把固定集成绩外推到总体。

### 2.2 最小回归包与断言修正

- 删除、隐藏、改名或迁移功能前，先从实际引用和调用链核对共享组件、公共接口、运行时选择器、状态/事件契约及测试消费者；不能只检查当前页面或直接调用点。只展开受影响链路，项目内部组件名、DOM 结构和测试框架写法留在项目规范，不上升为通用固定清单。
- 按改动影响选用原失败例、正常对照、邻近边界及确有必要的独立保留例；状态或界面修改补充进入、退出、取消、失败恢复和原有平台行为。绑定输入、环境、关键参数、预期输出与参考图/数据；没有变化且已有有效证据的项目不重复全量验证。
- 断言或 CI 失败先用实际输入、状态、日志和当前需求契约区分：真实产品回归、需求合法变化后过期的测试契约、测试装置/环境错误，以及证据支持的时序波动；无法分类时保持待确认，不得仅为变绿删除测试、改预期或扩大容差。需求合法变化时同步调整实现、运行时契约和测试，说明旧断言为何失效，以及新断言仍能检出哪种真实失败。
- 定向用例通过只证明已运行范围。提交前运行受影响测试文件或项目定义的等价测试单元；远端 CI 在同一文件暴露过期断言后，继续检索并执行该单元中的相关残留契约，除非能以依赖隔离和既有有效证据证明无需运行。若项目已提供可在本地复现的受影响 CI Job 命令，优先运行该等价 Job；无法等价时，说明浏览器、服务、权限或环境差异及其对结论的限制。该要求不自动扩大为整库、全设备或高资源测试。
- 验证被删除或隐藏的界面、接口或状态时，组合证明“目标确实不存在或不可达”与“保留的关键业务状态、输出或交互仍正确”；不能把测试弱化为只断言不存在。若需求只要求移除且没有相邻行为契约，明确说明后一项不适用及依据。
- 禁用与可操作状态分别验证：禁用控件不要求接收点击，但应核对禁用原因和禁止副作用；可操作控件核对命中与响应，布局遮挡/裁切按视觉边界另验。文案允许同义表达时优先读取业务状态；确有逐字文案要求则保留精确断言。
- 用户给出总时限时，在启动前落实能终止本次进程及所属子进程的超时机制，并说明计时起点和覆盖范围；同一授权批次的重试不自动重置总预算。单项超时和“AI 会留意”不能代替总墙钟上限。结束记录实际用时、退出原因和残留进程；机制不可用时不启动依赖硬限时的运行，先缩小任务或说明缺口。
- 发布候选验证绑定候选包 SHA-256 与文件清单，并从该精确包解压到全新、短路径、非同步目录建立基准；源码目录、旧解压副本或同名旧包不能代签。若产品声称支持同步目录或网络文件系统，再用同一候选、同一输入做单变量兼容性对照；非同步基准通过不能代签目标存储环境。

### 2.3 验收项、执行阶段与授权批次

通用合批、局部停止和三类累计额度以 09“授权内连续执行与局部停止”为主来源。下列保留测试特有条件：分别判定结果不等于分次授权，2F 唯一即时动作也不把执行卡限制成一条命令。

- **先盘点再制卡**：一次核对本轮全部剩余验收项、仍有效的证据、输入与就绪前提、依赖、实际运行身份、资源和写入冲突。能在已有权限内轻量核清的工具参数、版本兼容性与断言前提先核清；需实际运行才能确认的条件写成卡内预检，不把未验证写成已就绪。
- **预检触达真实输入**：在消耗浏览器/模型预算前，尽可能调用正式运行所用解析路径，核对样本来源、哈希、配置及本项目可加载依赖；语法、类型和列出测试不证明该路径已执行。人工认可绑定具体阶段，不把“可识别/可显示”当成“可批准/全链通过”，也不反写旧快照凑样本。
- **证据输出隔离**：原始运行报告使用独立、不覆盖的目标；枚举测试、配置检查及 AI 汇总另用输出位置，执行前核对写入目标，之后核对原证据身份。报告丢失须披露可恢复范围，存续日志不等于原报告完整恢复。
- **先读结构再汇总**：优先直接读取原报告的必要字段；重复复杂计算才新增汇总工具，先核对实际 schema，并区分配置重试数与结果尝试序号。可选工具失败只限制该工具；原证据足够时继续核账，不把修工具强加为交付前置或隐瞒失败。
- **满足条件才合批**：动作权限可明确覆盖或分阶段限定、各阶段基线可锁定、输入齐全、切换及结果可隔离、资源与总时限可控时，优先同卡有序执行；否则说明具体拆分原因。预检通过后再批量、不同配置分阶段执行都可以列在同一卡中，但每阶段分别核验身份、保留结果，不互相代签，不因合批增加 worker 或扩大全部测试组合。
- **事前明确停止范围**：卡内区分全批停止与仅停止依赖分支。操作者明确要求首败全停时必须全停；身份、基线、共享资源或隐私异常按实际影响暂停，影响范围不清时暂停整个受影响批次。普通断言失败后，只有后续项独立、状态及资源隔离可信，且现有授权明确允许继续时，才执行独立项；依赖失败前提的后项不得继续，不得追认历史失败后的继续权限。
- **可选修订额度不自动生效**：仅在工具问题可预见且确有需要时，制卡可建议精确文件、修订种类、检查和次数范围，获得明确授权后使用。额度不涵盖产品算法修改、放宽验收断言、更换基线或改变测试语义；越界需另行授权，修订与重试不重置原总时限和累计失败次数。
- **范围内连续完成**：已授权且不受阻的阶段直接推进，不逐阶段重复询问。新缺口集中说明剩余差额，复用仍有效的结果，分别报告失败、未运行和未覆盖；近似修补连续两次未改善时回查前提与根因，不靠换卡继续叠加补丁。授权仍以 `09` 和当前项目规则为准。

## 3. 固定执行顺序

1. **冻结事实**：核对版本、入口、输入哈希和对照类型。完整旧版本验收与“把旧核心接进当前页面”是两个不同问题，必须分开测试。
2. **等待真正就绪**：不能把 DOM 元素出现、文件输入挂载或页面能打开当作模型、监听器和 Worker 已就绪。优先等待产品提供的稳定状态；没有稳定信号时先补充只读诊断或标记限制。
3. **单样本输入保真预检（默认无头）**：批量前只跑一个样本，检查上传内容、点击位置、镜像/坐标、实际裁剪、请求阶段和页面结果。优先用无头截图、DOM、日志、网络请求、像素或结构化状态留下足以还原输入链的证据。若这些证据仍无法覆盖原生桌面、系统权限、真实设备或操作者主观视觉判断，只暂停依赖该证据的步骤，并按 `09` 申请限定的前台控制；不能把“看得见”本身当作正确。
4. **通过输入保真门禁**：预期输入与产品实际输入的哈希、尺寸、坐标、裁剪或关键参数一致后，才允许批量。预检与通过后的批量均已获同卡授权且未触发停止条件时，直接进入下一阶段，无需再次人工确认。镜像切换、缩放、滚动和覆盖层出现后必须重新核对坐标系。
5. **顺序批量执行**：按项目资源规则使用最低充分并发；高资源默认单进程、单 worker、串行。每轮记录样本、重复次数、开始/结束时间和失败阶段。
6. **结构化分类**：同时读取状态、诊断和用户可见结果，按第 4 节分类；同义成功文案不能被漏计，错误提示也不能被误判成算法已运行。
7. **核对分母与证据**：只用有效运行计算成功率。逐样本清单、输入指纹、阶段、结果和截图数量必须能互相核账。
8. **处理人工冲突**：自动化与人工观察冲突时，先审计测试装置、入口、输入和状态机，再讨论算法。不能先假定人工错，也不能仅凭一次人工成功否定全部自动化证据。操作者看不出结果时记录为 `不确定`，先继续客观核对，不得强迫猜测或把空白当作通过。
9. **结束与清理**：关闭本轮创建且归属明确、无需保留的服务、浏览器和模型进程；保留最小证据与复现入口，不清理他人进程或未归属成果。使用前台控制或浏览器调试连接时，按 [09 释放与验收](../09-自动化授权与风险分级.md#前台控制结束后的释放与验收)解除本任务控制并核验，保留展示页面不等于保留控制连接；未能解除时如实报告并提供最小人工操作。

## 4. 统一结果分类

每次运行只进入一个主类别：

| 类别 | 含义 | 是否计入产品成功率 |
|---|---|---|
| `TEST_INVALID` | 测试装置、入口、输入、坐标、就绪或证据不可信 | 否，必须剔除并说明原因 |
| `PRECONDITION_REJECTED` | 产品在算法/Worker 前按规则拒绝输入 | 是，但单独统计，不能写成“检测算法失败” |
| `SYSTEM_ERROR` | 页面、服务、模型、Worker 或接口异常中断 | 是，单独统计 |
| `DETECTOR_FAILED` | 已确认进入目标算法，但没有得到有效识别 | 是 |
| `DETECTED_REVIEW_REQUIRED` | 已识别到结果，但需要人工确认或未生成后续产物 | 是 |
| `DETECTED_CANDIDATE` | 已识别并生成预期后续产物 | 是 |

报告必须同时给出：总尝试数、无效测试数、有效运行数、各主类别数和产品成功率口径。不得把 `TEST_INVALID` 纳入失败率，也不得把前置拒绝冒充算法漏检。

## 5. 已发生过的失败模式与教训

1. **比较对象不等价**：把当前完整页面与旧核心兼容模式比较，随后把结果当成新旧完整版本结论。教训：先锁定“完整产品对照”或“核心隔离实验”，不能混写。
2. **就绪竞态改变输入**：文件输入刚出现就切换镜像或状态，事件监听尚未接管，实际点击被换算到相反位置。教训：记录产品实际收到的坐标和裁剪，单靠自动化脚本中的预期坐标不算证据。
3. **无效批量放大错误**：在输入保真未通过时重复几十次，数量增加却没有增加可信度。教训：一个样本的输入链没通过，禁止放大批量。
4. **按单一文案统计**：解析器只识别一种成功提示，漏掉语义相同的另一种成功状态。教训：优先读取结构化状态；使用文字时必须覆盖状态全集并用人工样本校验分类器。
5. **把前置拒绝算成算法失败**：页面在调用 Worker 前已因区域规则拒绝，却被汇总成检测器漏检。教训：必须记录首个失败阶段和是否实际调用目标算法。
6. **有头模式被误当作可信保证**：能看到页面只提高可观察性，不能证明入口、版本、输入或状态正确。教训：可信度来自完整证据链，不来自浏览器是否可见。
7. **把可见工具当作默认测试器**：为了方便观察直接打开可见浏览器或 Computer Use，虽然可能得到结果，却打断操作者办公并扩大了控制面。教训：先列出必须回答的问题及等价证据；只有无头证据确实不足时，才为受影响步骤申请最小前台授权。
8. **把存储环境故障当成产品故障**：同步目录的瞬时文件占用与过深路径可以分别制造写入竞争和路径失败。教训：先在全新短路径非同步沙箱建立可信基准，再用同一候选单变量回放目标环境；不写死某个同步软件或固定路径阈值。

## 6. 停止和升级条件

命中以下任一项，暂停受影响测试，不继续增加样本或调整产品代码：

1. 版本、路由、Head、未提交状态或输入哈希无法锁定；
2. 实际系统输入与预期不一致；
3. 同一脚本重复两次仍出现相同测试装置错误；
4. 结果分类无法区分前置拒绝、系统异常和算法失败；
5. 自动化与人工结论冲突且无法通过现有证据定位差异；
6. 资源消耗超过授权、发生卡顿或出现不归属于本轮的进程；
7. 测试需要新增产品诊断、改变算法、上传外部服务或执行远端写入，但当前授权未覆盖。
8. 测试需要可见浏览器、Chrome 控制或 Computer Use 才能取得关键证据，但尚未获得当前精确前台授权。

停止后只报告：已确认事实、无效原因、受影响结论、最小补救动作和需要的授权，不用无效结果推动回滚、替换或发布。

同一测试装置错误连续两次后，按 `PIPELINE_DIAGNOSIS_AND_ALGORITHM_TUNING_STANDARD.md` 区分路径限制、文件系统竞争、测试装置与产品行为，找到第一处可靠偏差后再修；不得把未经同包、同输入对照的换目录后通过当成故障已解决，也不得用延长超时或重复全量测试掩盖未分类故障。
