# 状态、目标变更与交接规范

<!-- SCENARIO_REFS: {} -->
## 场景路由与旧任务兼容过渡

场景提示词包是入口层，不是新的事实源。新版读取旧任务时，必须保留旧 `scenario_id`、任务卡、断点、证据指针和授权边界，并生成带 `migration_status` 的新版当前视图。迁移只允许扩大可观察性和补充映射，不得扩大动作范围、恢复旧高风险授权或改变唯一写者。

兼容状态至少区分：`LEGACY_READABLE`（可按旧格式读取）、`MIGRATION_REQUIRED`（可读取但下一项实质动作前需生成新版投影）、`MIGRATED`（新版投影已回读）、`MIGRATION_BLOCKED`（缺少映射或存在冲突）。旧任务在 `MIGRATION_BLOCKED` 时可以继续做不依赖冲突字段的只读核对，不得被静默重启。

版本升级采用“双读、单写”：新版本可读旧版本和新版状态；每个对象只允许一个当前写者；完成兼容映射并回读前，不把旧记录改写为新版完成事实。升级后的路由只影响尚未开始或受规则变化直接影响的动作，已取得可靠完成证据的动作保持终态。

## 1. 唯一事实源原则

第二代抽象层只定义状态格式，不保存具体项目的实时状态。


> **场景编号迁移**：本规范历史文字中的 <!-- SCENARIO_HISTORY:BEGIN -->6/6A/6B<!-- SCENARIO_HISTORY:END --> 分别按当前手册解释为 1C/1D/1G；普通任务续接使用 1E/1F，无上下文故障接管使用 1H。旧编号只保留兼容定位，不改变身份、授权或恢复门禁。


每个具体项目按 `10-自动状态索引规范.md` 在既有管理目录维护唯一 `AI状态索引.md`。索引只保存控制面 ID、指针、摘要和证据位置，用于自动检索；当前代码、Git/平台状态、测试和人工确认仍是事实来源。

交接、续接或恢复时，按[10 对话定位与身份消歧](10-自动状态索引规范.md#对话定位与身份消歧)分别定位接收指令的对话、中央登记的现任总指挥和原/旧对话。操作者对现有记录的指代确认不自动构成正式切换，不继承旧授权；无需因单纯消歧重做交接。

具体项目的实时事实应由项目实例入口定位，至少包括：

- 当前目标和版本；
- 工作项清单与依赖；
- 总指挥主执行断点及例外专项任务断点；
- Git/GitHub 当前状态；
- 测试、截图、日志和人工确认；
- 未提交修改、分支、worktree 和恢复条件。

任务标题、聊天内容、旧截图或单份 AI 总结只能作为索引，不能单独作为当前事实源。

## 2. 最小状态记录

本节是字段目录。按 10 只记录核心状态和实际触发的条件段：目标/未完成项、行动方与下一动作、写者、当前权限与失效条件、验证和证据指针。已有记录引用不复制，必要未知写缺口及影响；无 GitHub 对象不填空远端账。累计修复/运行/审查额度沿原工作包保留，换任不清零。

### Goal 交接的硬状态链

交接载荷保留当前工作周期起点、时间口径、已用时间/总迭代数及专项累计限制，恢复不清零；明确批准新周期的预算规则仅由[05第5.3.2节](05-模型选择与资源策略.md#532-工作周期预算与累计限制)维护，交接或新平台对象不自动授予新周期预算。

平台 Goal 的持久状态与 AI 的业务收口是两个不同事实，必须分开记录，不能用“已生成交接文档”推导“Goal 已暂停”。适用 Goal 时，状态索引和交接快照至少记录：

```text
Goal 平台状态：NOT_APPLICABLE / ACTIVE / PAUSE_REQUIRED / PAUSED / UNKNOWN / CLEARED
Goal 交接权限：BUSINESS_ALLOWED / CLOSEOUT_ONLY / NONE
最后平台状态回读：来源 / 时间 / 结果 / 失效条件
平台原始状态：保留客户端或工具实际返回值；未纳入上列状态链的值不得直接解释为业务阻断、操作者 Pause 或已暂停
```

状态转换固定为：

```text
平台状态：ACTIVE → PAUSE_REQUIRED → PAUSED → CLEARED
业务权限：BUSINESS_ALLOWED → CLOSEOUT_ONLY → NONE
```

操作者提出交接、换窗、存档或终止时，AI 只能把业务权限降为 `CLOSEOUT_ONLY` 并提示操作者完成平台 Pause；平台仍为 `ACTIVE` 或无法观察时，不得开始新的业务批次，也不得把材料标成可继续。平台明确为 `PAUSED` 后，AI 可以完成已开始且可安全收口的原子步骤；交接材料生成并回读成功后必须写 `Goal 交接权限=NONE`，旧 Goal 进入禁止继续业务的终态。新窗口只有在操作者明确要求恢复时才能恢复 `BUSINESS_ALLOWED`。平台完成标记、`MATERIAL_PREPARED`、`GENERATED_NOT_DELIVERED`、`READY_WITH_RESTRICTIONS` 或 AI 自述都不能替代平台状态回读。

模型容量故障、额度触发或平台异常时，同样先写 `PAUSE_REQUIRED`，保存断点并停止新工作；没有可靠的平台暂停证据时不得声称已经自动暂停。该链只约束工作流记录和 AI 行为，不提供宿主级强制拦截。

### 2.1 高成本证据与附件摘要

WPS/Office、PDF、图片、音视频、长日志或大段聊天等材料首次被用于任务结论后，总指挥必须在现有任务记录或项目个人管理层中保存一份轻量证据摘要；优先并入既有记录，不为每个附件新建文档。只在没有合适记录载体且项目规则允许时才新建摘要文件。

摘要由 AI 自动生成，至少记录：

```text
证据摘要 ID：
来源位置与材料类型：
来源指纹：本地文件优先记录大小、修改时间和 SHA-256；超大媒体哈希成本明显过高时记录降级依据；平台材料记录版本 ID、ETag 或等价游标
首次分析时间：
关键结论与不确定项：
适用对象和代码/任务基线：
人工核验轮次与阶段/问题 ID：不适用时写“无”
原文、页码、图片或时间点定位：
敏感性与可共享范围：
存储稳定性：稳定本地路径 / 系统临时路径 / 平台附件 / 待确认
访问状态：active/hot / closed/cold / minimum-retained / deletion-candidate / deleted
默认读取：true / false
原件回读触发条件：
摘要记录位置：
```

后续任务按“状态索引 → 当前轮次清单/证据摘要 → 当前受影响事实 → 必要的原始材料局部”顺序读取。全量推进只要求工作对象和状态覆盖完整，不要求历史证据原件全部重读。`default_read=false` 的已关闭轮次不得因路径仍可见、文件名再次出现或需要全局总结就自动展开。满足以下任一条件时才回读原件，并只读取解决问题所需的最小页、图、片段或日志区间：

- 来源指纹变化，或无法证明当前材料与摘要对应；
- 摘要缺失、关键字段不足或与代码、平台、测试、人工反馈冲突；
- 当前任务必须核对像素、排版、原句、OCR、时间线或其他摘要无法承载的细节；
- 使用者本人明确要求复核原件，或安全、专业、合规、审计门禁要求原始证据。

原始材料仍是证据来源，摘要只保存已经完成的提取结论和定位，不替代当前代码、平台或重新测试。复用摘要时只核验其来源指纹和适用基线；基线变化只触发受影响结论复核，不自动触发整份附件重读。聊天中已经分析但未持久化、且预计会被后续任务复用的材料，必须在本轮结束前补写摘要，避免下一轮只能重新读取原件。

使用者本人主动提供或 AI 执行中发现的附件先分类，不因“附件存在”就默认全部读取：

- **必要证据**：缺失会显著改变安全、专业或合规边界、实现方向、验收或授权。只暂停依赖该证据的对象，并向使用者本人说明缺少的具体材料、用途、最低需要内容和提供方式；其他独立对象继续推进。
- **辅助材料**：可以提高质量但不改变当前安全执行边界。继续推进并记录证据不足，不向使用者本人索要全部历史材料。
- **重复材料**：已有可靠摘要、来源指纹未变化且当前任务不需要原文细节。只复用摘要和定位，不重新读取原件。

无法访问的团队聊天、私有文档或线下资料只有在属于必要证据时才请求使用者本人提供。请求必须精确到文档类型、相关时间段或所需结论，不能笼统要求“把全部附件发来”。专业或受监管资料缺失可以形成取证、讨论或待领域确认 Issue，但不得据此生成未经验证的专业实现规则。附件包含个人数据、受监管数据、账号、密钥或其他敏感信息时按项目隐私规则处理，不上传到 Issue、PR、仓库或公开日志。

### 2.1.1 人工核验轮次迁移与清理

人工核验材料按轮次而不是按聊天窗口管理；聊天窗口是上下文隔离载体，不是轮次事实源。规则可以阻止以后重新读取本地附件，但不能从当前聊天中删除已经上传的图片。每个图片密集的大轮次结束并准备下一轮时，执行以下固定顺序：

只有图片密集大轮次会显著膨胀长寿命总指挥上下文、结构化结果足以支撑后续工作，且隔离收益明确大于新建任务和交接成本时，才采用两类记录：总指挥持有纯文字“视觉测试包”，只读视觉观察任务持有当前轮证据清单并生成一张“视觉结果卡”。少量图片、需要与代码连续对照或摘要无法替代视觉细节时继续留在主窗口。观察任务只对其唯一指定记录有写权；中央状态仍由总指挥单写。总指挥默认只摄入结果卡，原件按证据 ID 保持冷路径可回查。

视觉测试包至少记录：`轮次 ID | 绑定母任务/基线 | 页面/设备/URL/工作区 | 步骤 ID | 操作 | 预期现象 | 失败现象 | 禁止项 | 结果卡位置`。视觉结果卡至少记录：`结果卡 ID | 轮次/基线/事实时间 | 逐步骤状态与可观察事实 | 证据 ID/原件定位/敏感性/存储稳定性 | 冲突与不确定项 | 建议最小回读 | 未解决项 | 失效条件 | 权限回执`。结果卡不得嵌入图片二进制、重复逐图长描述或整段聊天；原始视觉细节无法由摘要替代时，记录最小回读目的和所需局部，不把不确定项压缩成确定结论。

1. 当前轮次建立唯一轮次证据清单，逐阶段映射 `证据 ID | 问题/步骤 | 观察结论 | 路径/平台定位 | 指纹 | 敏感性 | 存储稳定性 | 摘要 | 访问状态`。中央索引只登记该清单，不复制每张图片的条目。
2. 冻结上一轮的轮次 ID、基线、问题总数、证据总数和最终结论；本轮结束后不再直接追加到旧轮次正文。生成结构化结案摘要，使后续任务不打开原图也能知道已确认事实、未解决项、适用基线和失效条件。
3. 建立迁移表：`旧问题 ID | 新问题 ID/材料入口 | 状态 | 结论变化 | 证据指针 | 是否可删除原件`。已解决问题进入结案摘要；未解决问题必须完整并入下一轮；重复或被替代问题记录替代关系。
4. 将上一轮清单设为 `closed/cold` 和 `default_read=false`。进入下一轮后只加载新轮次清单；旧轮次只加载文字摘要和迁移结果。回归、冲突、摘要不足、安全/专业/合规/审计要求或使用者明确要求时，记录触发原因和证据 ID，再最小回读旧原件。
5. 图片密集轮次形成可靠断点后，先执行专项净收益门禁；只有继续当前任务会显著增加后续成本时，下一大轮次才使用新 Codex 任务承接。同一轮的连续小阶段留在原任务。交接只携带当前目标、未解决项、结案摘要、轮次清单指针、回读触发条件和禁止项，不携带旧原图或逐图分析正文。
6. 对每个原始材料建立清理判定：`保留最小必要副本`、`迁移后删除候选`、`重复删除候选` 或 `待确认`。含可识别人脸的图片/视频默认优先列入删除或隔离候选，但安全、专业、责任或审计所必需时改为最小必要保留；不得自动复制到仓库或远端。系统临时路径标记为易失，不保证原件长期可恢复。
7. 新轮次主记录、问题摘要、迁移表和轮次清单写入后立即回读；至少检查问题数量、未解决项逐项存在、证据指针可定位、访问状态正确、源文件指纹未漂移。
8. 每轮结束立即完成文档压缩和转冷。每累计 3 个已关闭轮次或距上次清理审查达到 30 天，任一先到即生成清理候选审查；这是软触发，只生成清单，不产生删除授权。使用者可以提前发起，项目也可以在实例规则中收紧周期。
9. 清理执行使用明确文件列表，不使用根目录级递归删除；执行前后记录文件数、总字节数、失败路径和回收结果。任何一项不一致都使本轮清理状态变为 `待修复`，不得宣称完成。
10. 清理完成后，索引只登记轮次结案摘要、迁移表、轮次清单状态和清理回执；当前视图移除旧轮次的过程性细节。原轮次目录可以保留清理说明，但不得继续作为当前证据入口。

视觉观察任务结束后，其用户可见聊天是否归档由使用者决定；规则不要求删除任务。下一大轮次不得复用旧观察任务继续上传新图，否则隔离窗口会再次长期膨胀。已经进入总指挥聊天的历史图片不能通过结果卡、索引或本地文件清理追溯移除；应先在当前稳定断点保存其结论，再从下一大轮次改用视觉观察任务。

最小轮次收口记录：

```text
人工核验轮次 ID：
上一轮/下一轮：
```

### 2.1.2 中央工作项清单与保存语义

采用总指挥控制面的具体项目应由项目入口定位一份“中央工作项清单”或等价唯一入口。它负责保存所有仍影响后续决策的待实施、进行中、阻断、暂缓、待验收事项，以及需要保留恢复责任的最近完成成果。每项至少包含稳定 ID、状态、优先级、已确认成果、缺口、精确断点、下一动作、责任对象、恢复或启动条件、失效条件和详细证据指针；必要但不可核验的字段写“待确认”。

使用者以“写进计划、记录成果、保存进度、存档、留档”或同义自然语言要求保存时，先按目的分流：中央工作项清单保存状态与恢复入口；当前进度视图保存聚合；会议、专项、测试或阶段包保存完整证据；CHANGELOG 只记录已发生的版本变化；正式工程 TODO/Issue 只在事项进入对应排期且符合项目规则时同步。任一详细材料的落盘都不能代替中央工作项清单更新，也不得为同一状态建立平行中央计划。

字段所有权固定为：中央工作项清单拥有非终态事项、断点、责任对象和恢复条件；当前进度视图拥有面向人的聚合目标、阻断和下一动作；`AI状态索引.md` 拥有控制面世代、写者、封条指针、规则加载记录和事件/回读指针；Git、平台和必要成果文件拥有各自原始事实。封条只保存这些来源在同一 `fact_cutoff` 的指针与摘要，不拥有业务状态。来源冲突、重复 current 块或事实截点不一致时，以原始事实回源并将受影响控制面标为 `BLOCKED`，不得按文件更新时间或检索顺序猜测。

中央清单不得复制完整聊天、长日志、全部证据或大段方案。计划、建议、已讨论、已实施、已验证和已验收必须分别记录；完成状态须有直接凭证。保存请求本身只授权当前项目内的状态整理与既有记录更新，不授权开始未来计划、修改产品、创建远端对象或执行其他受控动作。

更新后立即回读中央清单与受影响的当前进度视图，核对状态、优先级、断点、下一动作、恢复/失效条件和证据指针。中央记录与代码、Git/平台、工作区、专项记录或人工确认冲突时，登记差异及影响，不用较旧摘要覆盖当前事实。

### 2.2 当前进度视图与压缩

每个采用总指挥控制面的具体项目应由项目入口定位一份面向人类和总指挥的“当前进度视图”或等价文档。它只回答：当前目标与基线、已完成的阶段成果、中央工作项清单指针、活跃工作项、真实阻断、下一动作及责任人、人工/外部门禁和详细证据入口。它不是事件流水账，也不替代中央工作项清单、平台、代码、任务记录、拓扑或 `AI状态索引.md`。普通任务和专项任务不因收到中断恢复提示词而被要求创建或写入中央视图。

对总指挥项目，该文档同时是账号断联或无正式总指挥交接时唯一的“项目恢复热快照”（兼容旧称“灾难恢复热快照”）。项目不得再创建一个内容重叠的“总进度”“当前状态”“崩溃恢复记录”作为第二套热状态；若已有等价文件，项目入口必须明确唯一写入者和唯一活动指针。专项任务继续使用自己的唯一短状态，普通任务复用已有计划或记录；历史视图、批次记录、专项记录和证据摘要属于冷证据，只有命中恢复或审计条件时展开。

热快照推荐保持以下最小结构；无内容的字段写“无”，事实不可核验时写“待确认”，不得用猜测补齐：

### 2.2.1 低频持久化与崩溃一致性

以下时点由总指挥强制更新热快照；例外专项任务按 `03` 更新自己的短状态并直接向总指挥回传增量：

1. 长任务、无人值守执行或多批次队列开始前：记录目标、范围、起始基线、批次顺序、首个动作和禁止项。
2. 恢复路径发生变化时：分支/worktree/未提交修改、完成里程碑、验证、人工反馈、远端事实、责任、授权、阻断、暂停或目标优先级发生实质变化。
3. 每个独立长批次结束后：先写入完成凭证、剩余队列和下一断点，再向使用者本人汇报；不得等全部批次结束后统一补写。
4. 即将进入较长无人值守、外部等待、上下文迁移或使用者明确要求存档时。
5. 平台明确显示额度预警、使用者报告额度不足或任务因额度耗尽中断时：只记录可观察信号，不估算不可见余额；先在安全原子边界更新当前断点，并把结果未知的工具或远端动作单独标出。

不按固定时间、消息数、Token 数或工具调用数更新。无持久状态变化的问答、重复只读查询和微小中间命令不写热快照，避免状态维护本身造成 Token 与磁盘噪声。

总指挥同时承担主执行时，中央状态写入与产品代码修改按阶段隔离：先完成一个原子实现或验证步骤，再在稳定截点一次性登记恢复所需增量。不得为每个命令、文件保存、测试进度或临时假设同步热快照、任务标题、拓扑和多份状态视图；作者自检结论必须标明来源，不能写成独立审查已通过。

写入采用“先形成完整新内容，再替换当前视图，随后立即回读”的方式；不得先清空再逐段追加。回读至少核对版本/世代、事实截点、活动目标、队列顺序、当前断点、下一动作和证据入口。写入或回读失败时保留旧可靠截点，记录 `快照待修复`，不得宣称已经存档；能够在同一安全本地范围修复时重试一次，仍失败则停止依赖该快照的接管。

每次任务读取当前进度视图、拓扑、专项状态或其他持续增长的动态文档时，先做一次低成本健康检查：更新时间和事实截点是否可信；当前目标、阻断和下一动作能否快速定位；终态对象、重复叙述和被替代结论是否仍挤占当前视图；文档之间是否存在基线或状态矛盾；详细事实是否有稳定回查入口。检查本身不要求修改文件。

满足以下任一条件时才进入压缩：当前结论被历史过程淹没；同一事实重复出现；终态或被替代对象长期滞留；更新时间、基线或责任信息矛盾；交接时无法在短时间恢复当前状态；或超过项目自定的软阈值。不得用一个固定字数替代内容判断，也不得为了让文件变短删除仍影响决策的事实。

压缩遵守单写者原则：

1. 只有项目规则指定的总指挥或中央状态维护者可以修改当前视图；专项任务和临时协作 AI 只回传状态增量。
2. 修改前核对当前代码、平台、任务回执和并发写入，确认没有另一维护者正在改同一文件。
3. 保留当前目标、基线、活跃项、未核验远端动作、阻断、下一责任人、恢复/失效条件和证据入口；只合并重复表述，移出已终结过程和被替代结论。
4. 从当前视图移出的内容必须已存在于平台、唯一任务记录、状态索引或历史快照，并留下可回查指针；不覆盖或删除原始会议记录、证据、回执和审计账本。
5. 修改后更新视图时间与事实截点，核对活跃对象数量、状态、下一动作和链接，确认压缩前后的当前结论等价。

远端写操作取得可验证回执后，先更新对应任务事实；若它改变目标、基线、对象状态、阻断、下一动作或责任人，同轮更新受影响的当前进度视图、拓扑/专项状态和索引指针。纯读取、无状态变化的重复回执或不影响当前决策的历史细节，不为“每次操作都留一行”而写入总体进度。

### 2.2.2 耐久 Commit 台账与关键节点

每个项目在既有研发记录或项目个人/本地管理层维护一份唯一耐久 Commit 台账；没有独立研发记录时，由 `AI状态索引.md` 保存台账位置和短事件索引。台账默认不要求与目标代码 Commit 同时进入 Git，因此可以在 Commit 创建后直接回填精确标识；不得为回填 SHA 再创建只含台账更新的新 Commit。团队要求共享研发日志时，把映射并入下一次有实质内容的正常记录更新。台账记录代码状态演化，不复制完整 Diff、日志或聊天，也不把 Commit 当作验证、远端送达或业务通过。

每个项目相关 Commit 创建后追加一条记录：

```text
记录类型：COMMIT-LEDGER
提交标识、父节点与起始基线：
分支/worktree 与工作区状态：
目标、影响范围和关联对象：
实际验证、未验证和证据指针：
远端状态：仅本地 / 已 Push / 已进入 PR / 已合并 / 已被替代；附回执
保留级别：ROUTINE / KEY_NODE
KEY_NODE 保留原因：不适用 / 默认入口、运行选择器、配置、依赖、模型、资产、数据/公共契约、部署、发布、合并、回滚、人工确认基线或恢复路线变化
原提交到新提交/合并提交映射：无 / 可核验映射
恢复与失效条件、事实时间：
```

台账写入遵守以下规则：

1. 普通连续 Commit 可以在当前视图中聚合为一个提交区间，但台账必须保留区间边界、目标和详情指针。不得把“每个 Commit 都记录”实现为每次复制完整文件清单和 Diff。
2. 标记 `KEY_NODE` 的节点是文档精简保护对象。允许把过程细节迁往冷证据，但不得删除提交身份、父子/替代映射、保留原因、验证边界、证据位置和恢复/失效条件；压缩后必须能够从当前索引恢复到该节点。
3. Rebase、Squash、Cherry-pick、补丁移植或合并改变提交标识时，追加映射记录，不覆盖原记录。远端删除分支也不能删除已经用于决策或验证的节点映射。
4. 每个 Commit 都更新台账；只有它改变当前基线、运行身份、恢复路径、验证结论或队列时，才同步更新热快照。这样既保证可追溯，也避免总体进度退化为逐提交流水账。
5. 文档压缩前后核对 `KEY_NODE` 数量、标识集合、映射和证据指针。任何缺失都使压缩失败并保留旧可靠版本；不得以“已合并”“历史太长”或“已有最新 Commit”为由删减。

### 2.2.3 通用任务中断恢复与无正式总指挥交接

场景 1G 适用于任何普通、专项或总指挥任务窗口，但不是所有中断任务的必经步骤。原任务简单、完整目标可以直接重发、没有可复用中间成果、未提交修改或结果未知外部动作时，安全重做通常比恢复更短，操作者可以不使用场景 1G。其余情况由新窗口先恢复原任务身份，再决定读取哪些事实源；“恢复任务”不等于“接管项目”，仓库存在也不等于当前任务具有总指挥职责。

1. **锁定原身份与边界。** 只依据当前用户说明、任务创建信息、任务卡、项目登记或其他可验证记录，把原窗口识别为 `普通任务 / 专项任务 / 总指挥 / 待确认`。普通任务和专项任务不得因为场景 1G、额度耗尽或缺少交接而升级为总指挥；身份待确认时先保持原文件和状态不变。
2. **执行恢复收益门禁。** 在打开长对话、完整日志、全仓历史或中央状态前，只用当前消息、身份、现有产物/工作区摘要和结果未知信号比较恢复与安全重做成本，并选择 `直接重做 / 快速恢复 / 深度恢复 / 必须先核账`。简单、确定、当前目标完整、目标工作区洁净或旧产物已隔离、无可复用成果和外部副作用的任务默认直接重做；存在同文件未提交修改、昂贵计算/下载/人工结果、复杂需求演变、关键检查点或重复副作用风险时恢复。无法可靠比较时选快速恢复，不得为了判断是否值得恢复而先完成一次深度恢复，也不得编造精确 Token 或时长估计。
3. **按需选择恢复源。** 所有角色都先读当前可见消息、用户本轮明确上传并要求处理的精确附件、已有任务记录、实际产物和验证。普通任务到此已足够时停止扩展；专项任务再核对任务卡、短状态、负责路径、工作区和回传关系；只有总指挥分支才读取中央当前视图、`AI状态索引.md`、任务拓扑和单写者状态。Git/工作区只在任务实际位于仓库时读取，remote/账号/平台只在旧动作或下一步涉及远端时读取，规则目录只在可定位且与本轮执行有关时读取。
4. **恢复可验证任务契约。** 提取全部可见用户要求及其后续变更、目标、范围、排除项、验收、已完成且不可重复动作、结果未知动作、未开始步骤、实际文件/产物、验证、阻断、禁止项、旧授权状态和唯一下一步。聊天摘录可以恢复公开决策链，但不是事实豁免；不可见内部推理无法验证，也不得声称已经完整复原。
5. **保护中断现场。** 没有完成回执的命令、远端动作和文件写入先归入 `结果未知`，回读后再决定是否重试。选择直接重做也不能先清理或覆盖旧产物；当前代码、文件、Git/平台状态和测试证据优先于旧 AI 结论，后续排队消息不得覆盖原执行顺序。
6. **决定是否续跑。** 选择直接重做时，必须已经从当前消息或可靠材料取得完整目标，确认目标文件没有未提交修改，并先排除重复外部动作；否则转为快速恢复。直接重做只能避开或复用现有基线，不得先清理、回滚或覆盖旧现场。选择恢复时，置信度足够、身份/范围/并发没有冲突、结果未知项已经排除，且下一步属于用户在当前恢复消息中明确授权的低风险、可回滚本地工作时，可以从断点直接继续，不要求为了“恢复完成”再等一次确认。远端写入、删除、费用、凭据、生产环境、不可逆动作、专业签认或新范围必须重新取得当前授权。
7. **最小报告。** 继续前先回显原身份、所选路线及依据、置信度、已确认事实、缺口、精确断点、下一步和本轮可继续范围；能够立即重做或续跑时保持简短，不把恢复审计变成新的主要工作。恢复不可靠时保持现场，只扩大受影响部分或提出最少问题。

只有第 1 步确认原窗口为总指挥，且新账号看不到历史、旧总指挥无法继续或没有正式交接时，才进入“无正式总指挥交接恢复”（兼容旧称“无正式交接恢复”“空白账号灾难恢复”）：

1. 从项目规则定位中央入口、项目恢复热快照和 `AI状态索引.md`，再读取登记的适用规则。
2. 核对项目根目录、管理入口、分支/worktree/未提交修改、证据指针、当前 Git/平台事实、最近完成凭证、队列和单写者。
3. 快照完整且抽查一致时增量恢复；数量、基线、队列或工作区矛盾时升级受影响部分核账，无法恢复可靠边界时才全量重建。
4. 新总指挥写入新的世代、任务 ID/逻辑 ID、恢复依据、置信度和接管截点。旧总指挥标为 `不可继续/待确认`，保留历史；没有确认单写者前不得写中央状态。

总指挥热快照缺失或损坏时，依次回退到索引当前指针、匹配的专项状态/批次记录、Git/工作树、平台当前事实和必要冷证据。普通或专项任务不因缺少中央热快照而升级为全项目恢复，也不默认重读全部附件和聊天。

### 2.2.4 例外专项任务恢复记录

每个通过净收益门禁的跨阶段或长专项任务在其负责路径维护一份稳定短状态，优先复用已有唯一任务记录；没有合适载体且项目允许时，命名为 `00-专项任务当前状态.md`。普通主执行不为此另建专项状态。同一任务不得按每轮日期新建多个“当前状态”，也不得把总指挥热快照复制到专项目录。

专项状态只包含：任务目标/范围、创建净收益依据、负责人和隔离边界、起始/当前基线、实际变更范围、已完成与验证、当前断点、剩余步骤顺序、人工/外部门禁、禁止项、失效条件和证据入口。专项 AI 只能写自己负责的记录；结束或中断时直接回传这些字段的状态增量，由总指挥决定是否更新中央热快照和索引，使用者无需转发。

### 2.2.5 写入租约、成果运输与失效恢复

项目采用目录或资源单写者时，权威入口只维护一份租约记录；中央索引只保存指针和聚合状态，不复制第二套写者数据库。最小字段为：资源范围、`writer_task_id` 或角色、`writer_generation`、`lease_revision`、`writer_status`、允许写入类别、运输通道、最后核验时间和失效条件。真实任务 ID 只写允许保存的本地私有实例。

1. 用户业务授权决定“这项工作是否允许做”，租约决定“哪个任务可以写这个资源”，恢复责任决定“租约失效后由谁收口或转移”；三者分别判断。已有业务授权仍有效但发送方无租约时，使用 `WRITE_HANDOFF` 向现任写者运输成果，不重复请求同一授权。
2. 正常路径是：回读权威入口一次 → 发送一次结构化 `WRITE_HANDOFF` → 现任写者写入、验证并回执一次。只有缺少业务授权时用 `AUTH_REQUEST`；只有确需改变唯一写者时用 `LEASE_TRANSFER`。
3. 恢复时只读核对平台实际任务状态、入口修订、在途或结果未知写入。`active/inProgress` 不替换；`idle` 不等于失效；`archived/notFound` 也不等于文件或成果已删除。无法判断时只阻断租约转移，不影响独立只读工作。
4. 只有确认旧写者停止、没有在途或结果未知写入，且当前规则指定的有权角色可执行转移时，才原子递增世代与 `lease_revision`、更新权威入口并立即回读。迟到旧任务不得自动抢回租约，其结果按版本和副作用去重。
5. 允许写入类别只限制租约范围，不能扩大读取、业务、Git、远端、发布、费用或自动化权限。租约记录变化、权威入口漂移、写者状态冲突或出现第二写者时，当前租约及依赖动作按范围失效。

### 2.3 本地闭环状态与远端断点继承

场景 2 的本地进展不得只写“本地开发中”。默认责任窗口是总指挥主窗口；每个本地工作包使用以下状态之一：`场景路由中`、`推进路径决策中`、`待确认本地执行卡`、`本地实现中`、`待人工验收`、`本地返工中`、`待主线同步评估`、`发布归属预审中`、`发布候选审查中`、`紧急发布豁免审查中`、`待确认远端发布卡`、`待有效复审或批准`、`已转远端交付`、`暂停`、`阻断`、`已取消或被替代`。

核心状态必需；下列远端、人工验收和发布字段仅在对应用途实际存在时补齐，已有主记录只引用。必要未知写缺口及影响，不为无 GitHub 的本地工作包生成空远端账：

- 实际场景、用户提示、路由依据、置信度和自动纠正记录；
- 本地工作包 ID、起始默认分支 Commit、当前分支/worktree、上游和工作区脏净状态；
- 本地检查点 Commit、未提交变更范围、验证结果、人工验收版本与反馈；紧急豁免时还要记录原因、未完成验收项、风险接受、回滚/停止条件和确认原文；
- 关联 Issue/PR、冻结时 Base/Head、作者、责任模式、Review/Comment、CI、冲突和未闭环意见；
- 当前行动方、下一动作、完成凭证、恢复条件和后续行动方；
- 主线/依赖最近核对时间、事实漂移、发布候选条件和远端发布卡状态；
- 本地安全存档分支与完整检查点链、发布归属矩阵、各目标 PR 的锁定 Head/目标 worktree、移植方式、暂留本地项和失效条件；
- 明确区分 `仅本地完成`、`已准备远端卡`、`远端动作已确认`、`远端动作已回读`。

从远端协作切换到本地闭环时，不关闭、不改写、不删除原 Issue/PR，也不创建一个“重新开始”的空白状态。先保存远端断点：对象、Base/Head、分支、责任、最后实质事件、未闭环 Review、CI/冲突、当前行动方和截点时间；再建立引用该断点的本地工作包。返回远端时，从本地最终检查点和最新远端事实计算差异，旧 Review 是否有效必须重新判断。

状态转换约束：

1. `场景路由中 → 待确认本地执行卡`：只读事实足以冻结范围、责任和基线。
2. `待确认本地执行卡 → 本地实现中`：使用者本人已确认精确本地卡；不得同时把远端动作记为已授权。
3. `本地实现中/本地返工中 → 待人工验收`：已产生可运行或可观察版本，保存对应代码/资产版本和自动验证结果，并按 `02` 的运行身份门禁证明交付地址实际运行目标候选；无法证明时保持 `运行入口待确认`。
4. `待人工验收 → 本地返工中`：反馈未改变公共契约、责任和卡片范围；改变时转为补充制卡，不直接继续。
5. `待人工验收/本地实现中 → 发布归属预审中`：只读建立远端载体归属和执行卡草案；未满足的自动/人工/外部门禁必须显式保留，草案不可执行。
6. `待人工验收 → 发布候选审查中`：使用者本人明确接受当前可观察表现且自动验证满足要求；该接受不等于独立 Review 或远端发布授权。预审矩阵可复用，但须回读失效条件。
7. `待人工验收/发布归属预审中 → 紧急发布豁免审查中`：使用者本人明确记录紧急原因、未完成验收项、风险接受和拟执行终态动作；自动验证满足当前影响范围，且仓库/平台硬门禁仍保留。不得把这次转换记成“人工验收通过”。
8. `发布候选审查中/紧急发布豁免审查中 → 待确认远端发布卡`：最新主线、远端对象、责任、继承意见和验证均已回读；本地 Commit/文件/代码块到现有 Issue/PR Head 的发布归属矩阵完整，存档分支受保护，目标 worktree/移植方式和暂留本地项已明确，推荐发布路径稳定。紧急豁免路径还必须把豁免事实写入卡和目标 PR，并证明未覆盖 Required Checks、有效 Review、权限、安全或平台保护。
9. `待确认远端发布卡 → 已转远端交付`：卡内远端动作已实际执行并取得平台回执；只有本地 Commit 或草稿不能进入此状态。

来源不明修改、责任冲突、Base/Head 漂移、默认分支发生相关公共契约变化、验证失败或人工反馈改变范围时，只暂停受影响工作包并记录失效条件。不得通过 Reset、清理、覆盖分支或丢弃旧协作证据来伪造一个“干净状态”。

人工参与的详细判定和操作包格式以 `03-专项任务卡模板.md` 为唯一来源。本规范只记录使用者本人的参与类型、阻断性和操作包位置；其他成员的动作记录为外部责任与协作交接。不得用一个“待人工”状态代替可执行交棒，也不得把给其他成员的建议混入使用者本人的操作包。

“下一责任人”不能只保存一个账号。等待、暂停或阻断必须分别记录当前行动方和后续行动方，并附当前动作、是否已送达及回执、完成凭证和恢复条件。请求尚未送达时不得把状态写成“待对方”；“父链稳定后复审”等无主语表述必须改写为谁先稳定哪一项、凭什么算完成、完成后由谁对哪个 Head 复审。

GitHub 时间线最后一条事件的作者不能证明责任已交接或使用者本人已经完成本轮。正式 Review request 以请求状态、Review 绑定 Head、当前 Head、CI/冲突和直接父项为依据；Head 变化后必须重新判定既有 Review 是否有效。checks 为零时继续读取 Actions，不能把零检查写成成功或无需 CI。

PR 堆叠树和 Issue 依赖树是逐编号状态在当前截点的轻量投影，不是第二套事实库。PR 树只记录直接 Base/Head，Issue 树只记录有证据的父项、前置或阻断；普通 Related 关系不得升级为依赖。树的显示顺序不代替实际执行顺序、合并方向或授权。

动作结果与对象状态分开记录。例如“已提交 Changes Requested”只说明 Review 动作已发生，对象通常仍处于待修改或待本轮协作成员；“本地修复完成”也不等于 PR 已合并。`已 Merge`、`已 Close` 必须以远端当前事实为依据。

Review 动作、实现责任和分支载体也必须分开记录。交付推进中，Comment/Request Changes 不能把母目标改成“已完成”；若可安全直接修复，状态转为“待确认本地执行卡”或“本地实现中”。交回原作者必须记录为什么当前处理者不应直接修复、请求是否已送达和恢复条件；不得用“PR 作者默认负责修改”替代判断。

使用者本人或 AI 实现了实质改动后，必须重新核对当前 Head、PR 作者、当前处理者 Reviewer 资格、Required Reviews、CODEOWNERS、最后 Push 后批准规则、CI 和 Auto-merge。PR 作者不能批准自己创建的 PR；非 PR 作者的当前处理者参与修复后，若仓库和团队规则仍认可其 Review，可以在验证当前 Head 后进入有效 Approve，不得虚报为“独立于实现者的复审”，也不自动新增另一位 Reviewer。只有规则要求独立批准、当前处理者不具备资格或风险判断需要第二人复核时，状态才进入对应等待门禁。直接更新他人 PR 分支还必须保存团队规则、作者/责任安排、维护者编辑设置、并行修改检查和精确远端授权；仓库 write 权限本身不是责任交接证据。

实质交付与责任归属也必须分开。提交关联 PR、修复或验收证据后必须记录 Assignee 复核结论；只有责任依据、目标账号持续负责意愿或明确安排、团队规则、平台权限和精确远端授权同时成立时，才可设置对应 Assignee。临时推进和一次性交付不得伪装成长期负责；已有 Assignee 时不得自动替换或移除。

Issue 创建者、Assignee、计划实现账号、实际实现账号、PR 作者和 Reviewer 是不同事实，必须分别记录。实现责任策略只影响执行建议，不能覆盖已有责任证据；与现有 Assignee、活跃分支、关联 PR 或明确交办冲突时，先记录协调方案和结果，不能把“使用者本人优先”写成已经取得所有权。

协作可见性、技术完成度和远端动作必要性必须分开。`仅本地处理` 表示远端没有本轮新增痕迹；`汇总载体远端可见` 表示团队能在汇总处看到结论，但目标对象时间线没有本轮新事件；只有目标对象出现本轮直接动作或本轮新 Cross-reference/平台回链时，才能写 `对象级远端可见`。现有记录已完整表达事实、责任与恢复条件时，可以写“无需新增远端动作”及依据，但不能借此把仅本地处理写成远端可见。同一对象同时发生本地和对象级远端动作时，各栏分别记录，禁止用“已处理”合并概括。

候选集、本轮执行对象、上下文依赖和明确排除必须可按编号互相核对。每个正式候选必须记录命中目标、触发成员和正向纳入依据；已列协作成员创建且对象内容命中目标可以进入候选，但成员被列名、共同标签或无关创建行为本身不能成为纳入理由。使用者本人创建且内容命中目标、协作成员有新实质 Comment、Review、Commit/Push、关联交付或状态变化的对象进入候选；不命中目标时仍须满足目标外强参与信号。既定扫描入口发现的跨模块弱关联对象单列为观察项，并在明确确认前归入“明确排除”；记录间接证据、潜在价值、误纳入风险和确认结果。发现对象或协作事件不等于自动接管或必须远端发言，依赖项默认只作为上下文，弱关联信号不自动产生正式所有权、执行责任或远端写授权。

2A 与 3A 共存时分别维护队列状态和停止条件。同一对象在当前活动母任务内只允许一个规范执行记录，同一时刻只有一个有效责任窗口；明确交接时更新窗口、截点和下一责任人。其他队列保存引用及其影响，不复制状态正文；历史轮次记录继续保留。2A 已达到交棒终点时可独立收口；无关 3A 未完成只保留为后续队列，不得把 2A 写成未完成，也不得把 3A 写成已处理。

## 4. 项目状态变化

以下事件需要局部重算：

- 新增或关闭 Issue/PR；
- PR Base/Head、冲突、CI、Review 或负责人变化；
- Review request、Review 绑定 Head 或有效性变化，以及 checks 为零时对应 Actions 的触发、批准、运行、跳过或失败状态变化；
- 使用者本人创建的相关对象上出现本轮协作成员的新 Comment、Review、Review request、Commit/Push、关联交付或生命周期变化；
- 新增或撤销“建议 owner”、关联 PR Review request、直接点名、Assignee、明确交办、临时推进声明或认领关系；
- 新增关联 PR、修复或验收证据后触发的责任模式与 Assignee 复核变化；
- 实现与 PR 推进责任策略、计划实现账号、实际实现账号或 PR 作者变化；
- 实现责任与现有 Assignee、活跃分支、关联 PR 或明确交办发生冲突或完成协调；
- 新增或失效的 Cross-reference/平台回链；
- 本轮新建分支、PR、Review、Comment 或其他派生对象及其交棒状态变化；
- 新提交、合并、回滚或测试结论变化；
- `COMMIT-LEDGER` 或 `KEY_NODE` 新增、映射变化、证据失效或压缩核账失败；
- 实际入口、profile/feature flag、环境覆盖、依赖、模型/资产、缓存、服务进程或部署路线变化，导致运行身份或人工回执失效；
- 新增任务、任务失败、任务回执或任务停止；
- 依赖、权限、环境或验收方要求变化。
- 授权包新增、收窄、撤销、过期或与项目规则冲突。
- 母任务已确认结论、被否决方案、未决项或端到端交付模式变化。
- Issue 草案创建为正式编号、派生 PR 建立关联，或 Reviewer/最低批准门禁变化。

处理顺序：

1. 记录事件及来源；
2. 判断影响范围；
3. 暂停已失效或会浪费资源的任务；
4. 只重算受影响工作项和下游；
5. 把受阻对象移入阻断/等待队列，重新计算其他可执行对象；
6. 重新生成下一波次；
7. 保存恢复条件。

增量推进的基准检索和持久化按索引规范执行，候选范围和结束核账按总指挥核心规则执行。本文件只规定状态变化如何记录和局部重算，不重复两者的算法。仅扫描新增编号不能称为增量覆盖核账。

增量结束核账属于本轮任务的内置收尾，不单独建立固定的每日任务、重复任务卡或第二套状态记录。默认复用本轮候选、逐编号状态、动作账本和回执，只定向刷新本轮变化、未闭环旧账、派生对象及低成本入口元数据；核账通过后更新当前进度视图并写入下一可靠截点。任务中断、截点不可靠、编号或分类数量矛盾、范围/身份变化、怀疑遗漏、共享基线重大变化或正式交接时，记录升级原因并执行加强核账；仍不能恢复时转为全量推进。

只有以下情况才做全量重扫：范围不明、游标丢失、事实互相矛盾、默认分支重大变化、无法证明上一快照完整，或总指挥更换后无法可靠恢复交接截点。单纯更换总指挥不自动触发全量：交接快照完整、范围不变、增量游标有效且当前事实抽查一致时，新总指挥可以在完成规则与事实的首次只读加载后继续增量推进。

目标不直接覆盖或物理删除，使用版本化状态：

## 6. 交接协议

### 成果连续性与运行复现契约

本节是总指挥、普通任务和专项任务交接中的成果身份主来源。契约版本：1。只在接续代码、程序、算法或依赖本地产物的工作时按风险加载；普通答疑和无运行依赖的文档任务不强制核验全部五层。复用已有运行身份、PR 与链路证据，不新建第二套事实库。

“同一份成果”指相同的逻辑内容和约定运行身份，不要求不同电脑使用相同绝对路径、PID 或全目录原始字节。五层分别记录 `PASS / FAIL / NOT_RUN / UNKNOWN / NOT_APPLICABLE`、证据截点、适用范围和失效条件：未执行用 NOT_RUN，证据不足用 UNKNOWN，已证明不满足才用 FAIL。每层通过不能代签其他层；调度权切换、成果可续接、运行复现和人工效果验收分别报告。只阻断依赖缺失层的动作，无关工作不全局冻结。

| 层次 | 最小证据 | 不能据此推出 |
| --- | --- | --- |
| Git 基线 | 脱敏仓库标识/远端、分支、commit SHA、tree SHA、Git 对象格式；子模块 gitlink、实际 checkout 与脏状态；LFS pointer/OID 与实际对象可得性 | 分支或 HEAD 相同不证明工作区成果相同；LFS 指针存在不证明模型已下载 |
| 工作区增量 | 相对路径、类型/模式、staged 与 worktree 各自内容身份、tracked modified、deleted、rename 来源/目标、required untracked；规范化方案/版本、attributes 和过滤器依据、稳定指纹 | 新 worktree、GitHub、git pull 或新电脑不会自动取得未提交修改 |
| 依赖与构建 | 锁文件指纹、冻结安装命令、实际安装/解析结果证据、运行时/工具链；必要时构建来源、CI 产物或容器 digest | 锁文件相同或安装成功不证明实际依赖树相同；不强制新增容器或 CI |
| 运行身份 | 各端实际 worktree、规范启动及自检、非秘密环境字段、feature flag/profile、模型/权重/资产指纹、实际进程/服务来源；按影响核对客户端、worker、浏览器和计算后端 | HTTP 200、端口、profile 名、已安装浏览器版本不证明实际客户端载入版本或效果通过 |
| 输入与验收 | 输入文件和必要解码数据指纹、参数/options、seed、缩放/镜像、缓存、冷/热运行、并发、重复次数、同次 run_id 或等价绑定；参考环境和预先约定容差 | 相同 seed 不保证 ML/GPU/WebGL 跨硬件逐位一致；一次耗时差不能证明源码不同 |

清单按用途分开：**运行成果清单**只包含接续所必需的源码、脚本、配置和资产；**验证证据清单**绑定输入/输出、冻结日志时间片等必要证据；**现场连续性清单**可在本地记录范围更广的状态用于发现变化。缓存、临时构建文件、无关日志和秘密不得进入运行成果包；运行确实依赖生成产物时，记录可重建方式或把该产物明确列为必要交付。排除不等于删除历史。必要且被 Git 忽略的模型/资产仍须有合法可访问的获取方式和校验，不能因 ignored 就遗漏。

未提交成果是正常交接的默认对象，不以另发补充提示词或先 Commit 为前提。旧总指挥在已有受控记录中保存成果清单、修改目的、实现与关键决策、验证范围及精确断点；新候选实际回读接续必需的代码、配置、测试与证据，不能只检查 HEAD 或继承旧摘要中的完成声明。详细材料保留在获准来源，快照只带可靠指针；快照不是文件传输，也不自动授予创建任务或发送权限。

“未 Commit”与“编辑器未保存”分别判断。交接默认以磁盘上最后一次保存的内容为事实边界；编辑器缓冲区不可观察时登记 `NOT_OBSERVED`，不降低 `control_handoff_confidence`，也不阻断正式切换。只有操作者明确说明某段未保存内容是本次交接必需成果时，才局部标记待保存并暂停依赖它的动作；不得要求为普通交接取得前台控制。后续发现缓冲区变化时，按新的工作区增量重新登记，不追溯改写已经完成的交接。

#### 自然语言成果存档

操作者明确说“保存当前算法”“为当前算法存档”“存一下当前版本”或同义要求时，AI 直接复用本节成果包契约，不要求操作者填写版本号、名称或文件清单；否定、引用、假设或讨论中的同类措辞不触发存档，真实意图或对象仍歧义时只询问最小问题。AI 从当前目标、运行身份、调用链、工作区和项目单一登记恢复范围，按实际依赖纳入源码、默认选择器、行为配置、必要资产/依赖、测试和验收指针，并覆盖 staged、worktree、删除、重命名和必要未跟踪项；不能把最近修改时间或单一文件当作完整范围。

项目已有版本规则时，AI 按真实 Diff、兼容性、历史查重和验收状态自动生成严格递增且不复用的版本及人话名称；算法版本按算法族或组件分别维护，界面版本独立维护并绑定自己的源码指纹。联合恢复包拥有独立的包身份，只引用纳入范围内的算法、界面和运行时组件身份，不把包编号写成任一组件版本，也不因某一组件变化虚构其他组件升级。操作者保留实际效果评价、编辑器全部保存、产品取舍、风险接受和远端/生产授权。内容身份与适用范围未变化时复用已有存档，不递增版本；评价状态变化只更新绑定状态，不伪造代码变化。

成果包范围优先由项目已有范围配置、责任登记和实际调用链决定。范围配置必须区分 `复制内容`、`仅记录指纹/取得方式` 和 `排除`；媒体、模型、数据库、密钥或其他不适合复制的实体按项目契约只留非敏感身份或安全取得方式。秘密值和受保护输入不得进入包，也不得保存其内容哈希。范围外工作区变化先作为差异报告，不自动纳入；共享界面、运行时、渲染、数据流或其他跨责任文件的归属和影响仍不明确时，向操作者询问最小问题，并只阻断依赖这些文件的共享部署、PR Ready、合并或正式发布。采集前后核对工作区稳定性，先生成临时候选，回读清单、逐文件摘要、运行身份、恢复步骤和隐私排除后再原子确定。存档或恢复包存在不等于已 Commit、已上传、可跨机取得或已经恢复成功；恢复须在保护目标现有修改后重新计算身份并报告未验证项。

#### 指纹口径与稳定采集

1. 已提交源码以 Git tree/blob 为跨平台标准身份；原始 SHA-256 作为原始字节证据另列。工作区文本按照已审定的 `.gitattributes`、编码和 Git clean 内容规则形成规范身份；记录属性来源、算法/序列化版本及适用范围。不能默认把所有 CRLF 转 LF、任意重编码或去空白。属性未定义且原始字节不同、无法确认语义等价时标 UNKNOWN，不能假通过。
2. Git clean filter、working-tree-encoding、LFS 及外部转换可能执行代码或需要额外工具。先只读核对规则及可用性；未知或不可信过滤器不运行、不安装依赖、不静默绕过，仅将受影响规范化字段标 UNKNOWN。二进制、图片、模型按精确 SHA-256；需严格字节一致的场景保留 raw SHA-256。
3. 同一路径 index 和 worktree 内容可能不同，必须分别记录；稳定清单还包括删除、重命名、文件类型和执行位。跨平台大小写碰撞、符号链接或模式不支持时单列受影响路径，不用改路径掩盖差异。必要 untracked 使用显式范围清单，不把整个未跟踪目录自动打包。
4. 指纹必须绑定完整的适用清单。聚合时明确路径排序、分隔/长度编码、内容规范化、字符编码及序列化版本；机器路径不得混入跨端内容身份。区分“已独立复算”“由一致清单推定”“旧记录值”；聚合算法不可复现时，逐项零差异仍可作为对应范围的证据，但不能声称旧聚合值已复算。
5. 采集前后核对状态及内容稳定性，检查已知生成器、格式化器和其他实际写源。变化时只使受影响快照待重算；前后抽查不能证明不存在不可观察写者，证据不足保持 UNKNOWN。不得为稳定采集擅自停止其他进程。正式接管仍须独立满足单写者门禁。
6. 先审查清单再采集/打包。密钥、认证配置、秘密环境值不得写入交接材料，也不得用秘密值哈希冒充脱敏；只记录秘密字段是否配置及安全获取方式。发现误收先拒绝新清单/成果包，修正范围；不覆盖原证据、不擅自清理已存在文件。

#### 四种交接位置与交付情境

下列是同一五层契约的场景分支，不是第二套门禁。

- **同机、同一 worktree：**候选只读重算 HEAD/tree、状态与完整适用成果清单，精确匹配后可延续未提交成果；不要求为交接强制 Commit。运行进程须重新回读，旧服务存在不表示已接管。若当前仅做不依赖未验证运行层的工作，可限定范围续接，效果验收保持未验证。
- **同仓库、新 worktree：**新 worktree 不继承原 worktree 未提交修改。先在授权内用可回查补丁或成果包恢复 tracked 与 required untracked，覆盖二进制、删除、模式及必要资产，保护目标已有修改，再重算清单。仅 git diff 通常不包含 untracked；未完成恢复不得称交接成果恢复成功。
- **不同电脑：**已提交部分核对远端实际可取得的目标提交/tree；未提交成果通过获准渠道传递受控补丁/成果包，模型/资产另核获取权限和指纹。包绑定基线、路径、内容校验、恢复步骤及复核结果；不能靠 git pull 传递本地未提交成果。不同系统不用全目录 raw hash 作唯一判据。
- **PR 合并后复验：**核对目标分支实际最终提交/tree；squash/rebase 不一定生成 merge commit，保留原候选到最终对象的包含性/内容映射。再核依赖、配置、模型、输入和实际入口。性能按同条件、多次测量和分段日志比较；第一处分叉是定位线索，须因果证据才可归因于 PR、硬件或配置。细节沿用 [PR 标准](docs/PR_SUBMISSION_AND_REVIEW_STANDARD.md#432-跨机器复现证据) 与 [链路标准](docs/PIPELINE_DIAGNOSIS_AND_ALGORITHM_TUNING_STANDARD.md)。

完整路径清单保存在已有受控证据位置，交接正文只保留用途、指针、指纹口径、各层状态和异常摘要。计算程序可在明确范围内检查清单，默认不把全部路径输出给操作者；异常才展开。现有证据工具能满足要求时直接复用，不强制开发诊断导出功能。方案已形成、包已生成、目标已恢复、实际运行已回读和效果已验收分别登记，不互相冒充。

#### 交接对象分类与未跟踪对象判定

交接核验先给每个未提交、未跟踪或附加 worktree 对象归类，再决定它是否影响切换。统一使用以下四类：

| 类别 | 判定标准 | 交接处理 | 是否自动阻断 |
| --- | --- | --- | --- |
| 当前成果 | 本轮目标明确引用，或实际运行/恢复必须依赖 | 列入运行成果清单，记录路径、归属、指纹和恢复方式 | 仅在缺失、归属冲突或无法保护时阻断相关切换 |
| 历史资料 | 旧版本规则、停用脚本、迁移记录，当前运行不依赖 | 记录为历史只读材料，保留回查入口 | 否 |
| 外部/辅助载体 | 指针目录、独立项目链接、闲置或辅助 worktree，当前成果不依赖 | 记录对象、用途、HEAD/脏状态和排除理由；不纳入封条成果 | 否 |
| 待确认对象 | 现有证据无法判断是否属于当前成果，且可能影响恢复或安全 | 标为 `UNKNOWN`，只暂停依赖该对象的动作，给出最小核验项 | 不得升级为全局阻断 |

“未跟踪”只描述 Git 管理状态，不等于“当前成果”；“detached”只描述 worktree 的 HEAD 形态，不等于活动任务或重复写者。若对象已按“历史资料”或“外部/辅助载体”完成归类并有直接证据，交接可以继续，不能因为数量非零或目录名称陌生而拒绝切换。只有分类为“当前成果”或“待确认对象”且确实影响成果恢复、唯一写者、权限或验收时，才阻断对应动作。中央索引、当前进度视图和封条必须记录同一分类结果；旧记录中笼统的“未跟踪=阻断”表述视为被本节替代。

最小证据顺序固定为：读取目录/文件清单 → 回读项目边界或指针说明 → 核对 Git worktree、HEAD 和脏状态 → 查询当前工作项/任务关系 → 给出分类、证据来源、事实截点和失效条件。无法完成其中一步时，保留 `UNKNOWN`，不得凭目录名、最近修改时间或历史聊天猜测归属，也不得自动删除、移动、提交或吸收对象。

### 6.0 换窗与归档前连续性门禁

正式总指挥材料准备前，中央状态索引的 CURRENT 区必须写入 `规则清单摘要：<rule-manifest SHA-256>`，且必须与本轮实际规则 manifest 完全一致；仅有单个规则文件指纹或候选附件内的 manifest 不足以证明中央登记已同步。摘要不一致时先回到规则刷新和中央索引收敛，不生成正式候选附件。

正式交接材料只需闭合“生成状态”和“当前窗口是否收到主附件”两件事。生成工具的 `GENERATED_NOT_DELIVERED` 是正常内部状态，证明主附件已原子生成并完成哈希记录；不要求发送方再调用 `Mark-Handoff-Delivered.mjs`，也不要求旧总指挥与候选互发回执。操作者把唯一主附件发送到新窗口后，候选以当前消息中实际存在的附件作为送达事实；缺少机器回执不降低候选评分。
对平台 Goal，以上两件事仍不能代替 `Goal 平台状态=PAUSED/CLEARED` 和 `Goal 交接权限=NONE` 的旧任务终止门；平台状态未闭合时，`GENERATED_NOT_DELIVERED` 只能表示材料已生成，不能表示旧 Goal 已停止或可继续。

本门禁统一处理三种可观察意图：正式总指挥交接；因当前对话混入较多支线而把未完成主线移到新聊天；归档仍承担工作的当前任务。它只保证任务连续性，不自动授权创建、Fork、发送、归档、总指挥切换或原业务动作。使用者未通过消息表达而直接点击客户端归档，当前 AI 无法观察，不能登记为已触发。

1. **先确定原身份和交接类型。** 总指挥换任或归档仍在任的总指挥走场景 1C/1D；普通或专项任务换窗、非换任分支和归档走场景 1E/1F，按下方交接主快照契约交付，不产生总指挥世代。只读解释任务或新支线不接管原主线，原窗口仍负责的事项必须留在其活跃清单。
2. **形成稳定断点。** 在不会留下半写文件、半次提交、重复远端动作或无法判断的外部副作用的最小原子边界停止。回读当前目标、活跃请求和事件队列，分类为：已完成且不得重复、正在执行、结果未知、尚未开始、暂停/阻断、取消/替代。结果未知不能改写为失败或未执行。
3. **生成唯一主快照。** 有待续工作时，正式总指挥交接生成 07 定义的便携交接快照；普通/专项换窗、非换任分支或归档生成下方契约定义的主快照，并交付对应接手提示词。任务较长、有未提交成果、多个对象、昂贵验证或潜在副作用时，可同时更新原角色已有短状态；普通任务不为形式新建中央索引。
4. **主快照与精简续接提示词的最小字段。** 原窗口身份及依据、任务身份（普通任务 / 总指挥工作流下的专项任务）、工作流约束（启用 / 不启用）、当前总指挥（专项任务填写；普通任务可写无）、续接目标和范围、活跃请求逐项状态、已完成且不得重复的动作、正在执行或结果未知的动作、实际产物和验证、工作区/未提交修改/运行进程（仅适用时）、阻断与禁止项、旧授权不继承、精确断点、下一动作与行动方、必要证据入口、失效条件，以及新窗口第一次只读核对动作。总指挥工作流下的专项任务默认向填写的当前总指挥汇报；特殊汇报对象只在目标或细节中另行说明。AI 自动填入可核实字段，不要求操作者查 ID、复制完整聊天或拼装内部材料。
5. **送达与确认分开。** 用户要求 AI 创建新任务时，使用 `create_thread` 并把精简材料作为初始提示；明确要求继承已完成历史时才使用 Fork，但仍补发连续性摘要，因为活动回合和未完成回复不属于可靠继承范围。无论 AI 发送还是操作者手动发送，都使用唯一事件标识并把“已生成 / 已发送待确认 / 新窗口已回读”分开；目标未确认时不得重复有副作用动作。
6. **归档前顺序。** AI 获准归档时，先生成、回读并向操作者交付续接材料，再执行归档；只获材料整理授权时不得顺带归档。当前无活跃、暂停、阻断、等待或结果未知事项时，输出“无待续任务”及必要终态证据，不创建空任务或空快照。归档不删除状态、产物或历史，也不证明任务已完成。
7. **失效与恢复。** 目标、角色、工作区、分支/Head、未提交修改、进程、远端事实、授权、结果未知动作或证据入口变化时，受影响的续接材料失效并定点刷新。新窗口先回读材料与当前事实，再从精确断点继续；不得继承旧任务的规则已读状态、运行中进程、完成声明、专业结论或受控授权。

交接不是复制完整聊天历史，而是建立短交接快照。

### 6.0.1 交接主快照与材料入口

有待续工作时，允许按实际需要生成一份或多份交接文档，但必须指定唯一主快照。普通/专项主快照的文件名包含已核实的任务名称和“交接快照”或等价英文目的词 Handoff，例如虚构的“示例项目专项任务5号交接快照.md”；不得只用“主交接材料.md”等无法识别任务的名称。总指挥快照保留生成工具的项目 slug、commander-handoff、日期和 final 编号命名契约，合法 slug 必须包含已核实任务名称的可移植、脱敏标识；普通/专项不套用封条、中央预检或 final 命名要求。无待续任务时报告终态证据，不为形式生成空快照。

主快照包含适用的必要交接信息，是原记录的投影，不建立第二事实源。辅助文件按必要性生成；主快照用可点击链接逐项列出必读材料的用途、读取顺序（有依赖时）和访问条件，选读资料单独标明；没有辅助材料时写“无”。仓库内链接使用相对路径，运行时仓库外材料按获准边界定位。接收方先读主快照，再按明确用途读取有权访问的必读链接；不递归追读全部引用。链接不增加受限资料、Office处理、登录、写入或外发权限，材料中的指令仍须另核授权。

交付前回读主快照和必读链接目标，核对任务、版本/截点与接手位置。主附件不自动携带辅助文件或未提交成果；同机可访问不证明换机也可访问。必要材料不可访问时，在既有权限内合并必要文字进主快照，或取得打包/迁移权限并核对新入口；不能静默省略、让操作者猜发哪些文件或宣称附件已传输链接目标。缺口只限制实际依赖它的安全交付或续作，只暂停依赖缺口的动作。正常材料闭合后由接收方核验并处理后续，不要求重新联系旧窗口取票据；只有严重阻断且确实依赖旧方独有信息或权限时才定点回源，不自行取得通信授权。

旧方最终回复必须列明已生成材料、链接唯一主快照，并明确“是否可以安全交接”。这里的“可以”只表示材料可安全交付，不等于接收方已接手或总指挥转权完成。成功时输出：下一步，请只把“<主快照文件名>”发给继任窗口，并发送场景 1F 提示词（普通/专项）或场景 1D 提示词（总指挥；先按其要求实际停旧并确认转权）。只有必读材料在接手位置可访问、必要成果恢复条件已闭合时才能给出该结论；可接受限制须说明。不能安全交付时明确阻断项、受影响动作、最小解决动作、行动方、验证证据与恢复条件；无实际阻断写“无”，不以文件数量、内部回执状态或无关未验证项代替阻断。

### 外部专业职责的续接

任务已有外部专业角色时，普通/专项续接材料和正式总指挥快照都显式引用 `external_role_binding` 锚点、任务职责集合、当前阶段、未完调用、累计预算及撤销状态。候选只核验必要指针和状态，正式续做适用动作前独立读取角色正文并核权；不复制全文，不继承旧实例已读、进程、完成/验收声明或受控授权。开始前消费与同次恢复按[共同对接规范第5.1节](../../引用的外部工具/外部工具自动对接规范.md#51-开始前消费与同次恢复)，未完成/失败也占一次，恢复不新领次数。总指挥换任不撤销仍有效的专项本地职责，汇报路由按本规范另核；规则文档就绪与接收方实际加载确认分开，不假定所有窗口已迁移。阶段自主调用及终点门禁按共同规范第5.2节执行。

用户要求“新建任务”“新建对话”或“创建独立专项任务”时，总指挥必须使用 `create_thread` 创建不继承聊天历史的任务，再发送精简交接包；不得先用 `fork_thread` 复制当前任务，再通过改标题或角色提示把副本伪装成新任务。`fork_thread` 只适用于使用者明确要求继承当前任务已完成历史的分支讨论。平台无法创建同项目独立任务时，应保持现有任务与本地成果不变并报告阻断，不得以 Fork 降级替代。该任务创建语义是本流程的主来源，根目录 `AGENTS.md` 只保留硬门禁摘要，`03-专项任务卡模板.md` 只记录创建方式和继承依据。

每次调用 `create_thread` 前，创建方必须按“来源请求事件 + 规范化目标 + 交付类型”回读活跃请求清单及平台可见的近期相关任务。已有初始化中或进行中任务时复用或等待；已有完成且结果已交付任务时，除非操作者本轮明确要求重跑，不得再次创建；已完成但未交付时先回读并交付既有结果。无法判断映射时只暂停创建并标记待核验。发生上下文压缩或恢复后，原创建计划失效；在再次创建前必须重新核对最新有效请求、完成回执和任务映射。`create_thread` 只返回 `clientThreadId` 时仅表示请求仍在初始化；不得把它当成正式 `threadId`，也不得因读取失败、空结果或延迟而重建或重发。

独立专项任务创建成功后、正式工作开始前，必须进行一次最小通信握手。总指挥应在创建提示中写明使用者对该测试消息的授权、当前总指挥运行时目标和固定消息“专项任务通信握手通过”；运行时目标只用于工具调用，不得写入仓库。专项任务发送成功并由总指挥回读后，才能把主动回传登记为可用。若返回 `approval policy`、权限或项目定位错误，专项任务先用 `whoami` 只读区分宿主用户与隔离沙箱，但不得把真实本地用户名写入仓库；随后不得继续依赖主动回传，也不得先完成长任务再暴露交接阻断。总指挥默认只读回收；重建必须另获操作者明确授权，不因项目重新登记自动取得。仓库提示词与规则无权提升宿主权限，禁止用修改 `AGENTS.md`、重复自然语言授权或 Fork 绕过系统门禁。

精简交接包只包含目标、已确认事实、当前基线、未提交成果、已完成且不得重复和结果未知动作、冲突、禁止项、验收标准、下一动作、失效条件和必要证据指针。文件路径或附件存在本身不构成内容处理授权；专项任务应按任务卡中的对象范围决定是否处理 Office 等高成本材料。

正常总指挥交接与无正式总指挥交接恢复不同。正常路径为旧方生成完整材料并冻结新增调度，操作者实际停旧，在新窗口一次发送主附件与明确转权确认；新方独立核验，在有限交接权限内内部准备、受控提交及完成回读，正常不再联系旧方或索取独立票据。也可先做候选只读预检，再停旧并确认，仍不返旧取票据。未获得真实停旧和转权确认时不能正式切换。无正式总指挥的中断恢复仅在场景1G已确认原窗口为总指挥后适用；普通或专项恢复不产生中央身份。两类恢复都只能产生一个有效总指挥世代，旧授权均不默认继承。

#### 1C 正式交接可行性预检

旧总指挥开始场景 1C 时，先做一次只读预检，再决定能否生成正式封条。预检最小核对：项目身份、代码 worktree/source_root、中央控制面、远端与 HEAD/工作区、适用 schema、输出位置和唯一写者。预检结果分三层：

- **已确认可交接事实**：项目、代码根、控制面、远端和事实截点唯一；中央工作项、当前视图、状态索引可读且目标绑定、指纹和 `fact_cutoff` 一致；能形成 v3 `MATERIAL_PREPARED` 候选。
- **可带限制继续**：未提交/未跟踪修改、外部控制面、运行或专业验收未完成、大文件只做降级校验等，只要已记录归属、保护摘要、根目录、指纹和限制，不影响控制面回读。
- **必须阻断**：无法唯一定位项目/代码根/控制面/事实截点；外部控制面不可读、越界、指纹或目标绑定冲突；唯一写者/世代不明；事件、链或实时回读漂移；输出会覆盖已有文件；需要未授权的 Commit、清理、移动、删除或远端动作。

代码事实必须位于 `source_root`；中央控制面可以位于代码根外，但必须在来源中标记 `root_ref=external_control_plane`，由配置提供受控的 `external_control_plane_root`，并逐项核对路径边界、项目绑定、摘要和事实截点。外置控制面不是代码仓库接管，也不授权修改其源码。未提交成果保护摘要与正式封条来源分离：前者记录现场范围、归属和保护结论，后者只纳入接续必需且已核验的来源；不得把全部未跟踪目录自动纳入封条或 Git 盘点。

旧 v1/v2 链只读登记为 `LEGACY_UNVERIFIED`。旧链迁移与新交接候选是两个独立阶段：交接前只能在独立、空的 v3 候选封条目录中生成 `MATERIAL_PREPARED`；`CURRENT_MIGRATION` 只在旧总指挥已经停止、需要把旧链最后摘要迁入新的当前控制链时使用，且必须使用另一个独立、空的迁移封条目录。不得在同一目录同时追加旧序号和新的序号 1，也不得用 `CURRENT_MIGRATION` 代替候选准备；旧链不回写、不补造历史。

材料准备使用固定提交顺序：封条必须同时绑定冻结的 `rule_baseline`（rule_version + manifest 摘要）和 `workspace.worktree_fingerprint`（tracked diff + 未跟踪内容摘要）；候选生成后重新准备时必须重新计算两者。`冻结新增业务 -> 收敛并回读唯一 CURRENT -> 在索引登记封条目录、事件和预分配快照 ID -> 保存全部来源 -> 生成并实时验证 MATERIAL_PREPARED 封条 -> 生成正式便携附件 -> 计算并回读附件 SHA-256 -> 交付`。封条覆盖中央工作项清单、当前进度视图和状态索引，不覆盖随后生成的便携附件；附件必须引用已验证的封条摘要和同一事实截点。附件 SHA-256 只能写入不属于该封条来源的交付回执或外部清单，不能回写已封来源形成自引用。封条后中央 CURRENT、交接保护范围内工作区、远端或候选来源变化都使受影响阶段材料失效，须从受影响的 CURRENT 收敛步骤重做，不能只改附件正文；公共规则源变化按 `RULE_REBASE_PENDING` 与交接阶段矩阵分类，不把兼容规则前进误判为中央事实冲突。

交接快照必须先以项目入口定位的中央工作项清单作为全部非终态事项的主来源，再结合当前进度视图、工作项拓扑、专项任务状态、`AI状态索引.md` 和必要的当前代码/平台回源，生成便携投影；它不是新的独立事实源。快照须逐项投影中央清单中的待实施、进行中、阻断、暂缓和待验收事项，至少保留稳定 ID、状态、优先级、已确认成果、精确断点、下一动作、责任对象、恢复或启动条件、失效条件和证据指针；只保存聚合事实与指针，不复制详细材料。快照还至少包含：生成时间与事实截点、目标与范围、代码/远端基线、已完成阶段成果、相关对象的可迁移决策回执、人工/外部门禁、未提交成果、禁止项、第二代规则根目录、`总指挥轻量交接启动配置.md` 的路径/版本/SHA-256、02/04/07/09/10 的交接时来源指纹、第一次只读动作和快照失效条件。能够定位时还要记录旧总指挥任务/会话 ID、本地会话文件路径、最近字节数与 MiB、检查时间和 `正常 / 交接评估 / 优先交接` 软门禁状态；这些是机器相关的诊断字段，不是跨设备事实源，也不要求新任务读取旧 JSONL 正文。配置与规则指纹只帮助新任务建立自己的加载记录和定位变化，不能继承旧任务的“已读”状态。

机器可读封条必须遵守 [HANDOFF_STATE.schema.json](templates/HANDOFF_STATE.schema.json)。材料与原语义续链可使用schema v3/v4；接收方直接准备及完成使用schema v4；v1/v2 记录只能作为 `LEGACY_UNVERIFIED` 历史读取，不继续追加，也不追溯补证旧事件时序。项目实例只在已被 `.gitignore` 精确排除的私有目录保存 `handoff-state.<sequence>.<digest>.json` 链、`handoff-transition.<previous-sequence>.<digest>.json` 轮换意图及工具锁/临时文件；公开规则、便携快照和提交只保存相对目录指针、schema 版本、世代、序号、前序摘要、事件 ID、来源摘要、`source_digest_status`、候选核验状态、交接阶段、轮换意图摘要和链状态。`source_digest_status=PASS` 只能由同截点回源读取产生；校验 `HIGH / READY / READY_WITH_RESTRICTIONS / COMPLETED` 时必须向 `HandoffSeal.mjs verify <seal-dir> <source-root>` 提供可访问的代码来源根目录；若封条含 `external_control_plane` 来源，还必须提供同一控制面根目录并逐项实际回算 SHA-256。缺少任一根目录报INPUT_REQUIRED；路径越界、文件缺失或摘要不符只阻断依赖该来源的动作，不把调用缺参写成来源损坏。工具仍不能替代来源语义、远端权限或操作者确认。每个字段只由其 owner 回源，封条不拥有业务状态。

`source-root` 是代码事实和默认来源的可信根，不是封条工具所在仓库；封条工具则从当前已核验的工作流规则根按规范相对路径定位。`external_control_plane_root` 只承载已绑定的中央控制面来源，不改变代码仓库归属，也不允许工具修改其独立源码。必须分别核对工具路径、代码来源根和外部控制面根，再逐项解析真实来源文件。只在错误目录中未找到工具，不能记为“工具缺失”；任一根目录无法唯一确定、真实路径越界或工具指纹不明时，只阻断封条生成与依赖该封条的正式附件。

候选封条使用 `handoff_phase=MATERIAL_PREPARED` 且 `transition=null`；`READY / READY_WITH_RESTRICTIONS` 不要求旧写者已停止。接收方在真实停旧及转权确认有效、候选核验通过后，内部生成不可变直接准备意图，绑定旧摘要/序号、旧新世代、旧新写者、新事件与准备时间；已有v3意图按历史语义精确匹配消费。该内部证据不增加人工转交。受控提交中央current后，由 `handoff_phase=TAKEOVER_COMPLETED`、`switch_status=COMPLETED` 的新封条消费该意图。v3 链校验必须拒绝缺失、篡改、重复、错误前序或过期未消费意图，并拒绝跨序号 `fact_cutoff/sealed_at` 倒退、`sealed_at < fact_cutoff`、事件 ID 复用、`prepared_at` 位于前序封条之前或接管封条之后。同一 generation/writer 只有在身份、授权、规则根、单写者或控制面结构发生高影响变化时才追加 `CURRENT_ATTESTATION`；普通进度更新由中央 CURRENT、状态索引和耐久台账记录，不要求续签封条，也不撤销已经完成的接管。若候选尚未正式切换，中央来源变化仍使候选材料失效，必须从受影响的 CURRENT 重新准备。历史封条只验证结构、摘要链和意图关系；默认只回算最新封条的当前来源。`--history-only` 输出 `latest_source_status=NOT_CHECKED`，仅供历史诊断，不支持 READY/COMPLETED。首次从旧格式迁移只从当时唯一 current 建立序号 1 的 `CURRENT_MIGRATION` v3 链，并绑定旧链最后摘要、世代、写者和迁移时间；旧封条或 Markdown 留作历史来源，不得补造过去连续性。

写入使用expected previous digest、规范控制面锁再取同目录独占锁、同目录临时文件、flush/fsync和不可变改名；不提供宿主级强制锁。链校验必须拒绝残留锁/临时文件、重复或回退序号、前序摘要不匹配、跨世代无匹配轮换意图、时间回退、事件 ID 复用、无变化重复证明、来源摘要漂移、旧写者封条后事件和重复current块；远端不可达只按版本与下一步依赖处理，v3原语义不放宽。三个中央来源还必须各自只有一组非空 `CURRENT:BEGIN/END`，`HISTORY:BEGIN` 位于其后，`CURRENT:END` 与 `HISTORY:BEGIN` 之间不得夹有正文；全文哈希一致不能替代结构检查。无法完成链校验时，控制面不得标 HIGH 或 READY。

自动化交接清单：若存在已登记、待恢复、暂停或替代中的自动化，交接快照还必须逐项登记：用途、绑定的逻辑任务、执行世代、类型与名称、原始非秘密提示词、模型与推理设置、频率与时区、绑定对象、通知设置、授权范围、当前状态、最后可靠成功截点、平台核验结果、来源与核验时间、恢复条件及失效条件。平台任务 ID 仅作为获准运行时的定位线索，不作为永久地址或任务存在、执行成功的证明；无法核验的字段标为待确认，并只暂停依赖该字段的恢复动作。凭据、Cookie、API Key 和其他秘密值不得写入快照。

快照正文优先控制在约 6,000 个中文字符或 12 KB UTF-8 的软目标内，只保存当前结论、聚合计数、指纹和稳定证据指针；不得复制完整聊天、Git 路径清单、worktree 全表、Diff、日志、图片或历史流水。必要事实超过软目标时移动历史和大证据为指针，不得硬截断目标、断点、禁止项、恢复/失效条件或未核验动作。

候选首次只读必须按 `总指挥轻量交接启动配置.md` 的人话模板输出，先给四行结论：可切换置信度、是否建议现在交接、真正阻断、操作者下一步。默认不展示机器字段、计数、指纹、封条序号、内部状态码或完整检查清单；这些只保存在机器记录中。只有操作者明确要求技术细节，或确有异常需要定位时，才在四行结论后补充最小技术依据，并说明它影响哪个动作。没有实际阻断时不得把 `NOT_RUN`、`GENERATED_NOT_DELIVERED`、编辑器状态不可观察或旧总指挥未归档写成 WARN、阻断或“不能交接”。旧任务状态冲突时只读取其当前状态和最后一条控制权声明，不读取完整对话。

临时交给其他 AI 分担工作且不转移总指挥权限时，当前总指挥仍是中央状态唯一写入者。临时 AI 接收完成该工作项所需的最小任务包：任务尚未开始时提供目标、范围、验收标准和必要事实；已经部分推进时，再提供已完成与已验证事项、状态不明动作、未提交成果、当前断点和必要证据指针。新任务位于同一项目不等于已经掌握最新事实，临时 AI 应先核对实际项目、规则、工作区和可访问材料；能够自动定位的项目路径、remote 和当前状态不要求操作者重复填写。临时 AI 只处理明确范围，不得与总指挥或其他任务并行修改同一文件、同一 PR Head 或共享的未提交状态；冲突域不明时只暂停受影响的写入。结束后返回“实际完成、修改对象、验证、未验证项、未完成项、阻断、证据指针和建议写回的最小状态增量”，不得生成或更新总指挥交接快照，也不得直接覆盖中央进度、拓扑或索引。正常换任只有在候选只读核验通过、操作者已停止或归档旧总指挥并明确确认切换、候选完成切换前最小复核后，才能由候选在规范锁及可恢复日志下受控提交中央状态并完成回读后取得调度权；候选不得自行终止旧任务。

只读解释任务不是总指挥交接。它只读取目标对象的可迁移决策回执、证据指针和必要的当前 GitHub/代码事实，用于回答“做了什么、为什么、原结论是否仍有效”。原总指挥可以继续推进其他对象；解释任务不得实现、远端写入或修改中央状态。回执缺失时必须返回原总指挥补录，不能靠完整聊天或零散历史猜测；发现事实漂移时只报告失效范围和证据，由原总指挥核验后更新。

交接前旧总指挥必须确认：

- 没有未核验的远端写操作或不可逆动作；
- 当前状态已保存到稳定截点；
- 本地操作者协作画像为 `enabled` 时，已在主任务形成稳定截点后按 `11` 做一次触发式维护检查；当前总指挥作为默认唯一画像写者，同时核对是否有其他窗口回传的待合并候选。没有合格新证据时明确记录“不更新”，失败时只标记“未更新/待复核”，不得阻断交接；未执行核验与核验失败分开说明；漏查按 `11`“节点漏查的补做与结果说明”处理，按补查实际时间登记，不追写旧完成声明。
- 当前本地会话文件路径、大小、检查时间和软门禁状态已记录，或已明确标记无法定位；自动压缩次数未被当成交接依据；
- 每个活跃任务都有任务 ID、基线、断点、证据和恢复条件；
- 未提交修改、worktree 和后台进程有明确归属；
- 没有两个总指挥同时拥有调度权。
- 当前授权包的范围、剩余有效期和禁止项已明确记录。
- 每个等待对象已写明当前行动方、送达回执、完成凭证、恢复条件和后续行动方，不存在无主语交棒或双方互等。
- 上一可靠全量快照、增量游标、未闭环旧账和本轮派生对象已记录。
- 四类结束差集为空，或每个真实缺口已进入最小补漏卡/明确外部门禁；“无需新增远端动作”的对象均有依据。这里的“收口”是把执行中或结果未知的动作停在安全原子边界并逐项登记，不等于强行完成所有待办。普通未完成项只要有状态、责任对象、精确断点、下一行动和失效条件，可以进入快照的非终态队列；高风险动作未安全停止、结果未知且无可靠断点，或责任/恢复条件缺失时，必须 `BLOCKED`。
- 正式附件正文已逐项与中央 CURRENT、AI 状态索引、实际 Git/工作区/远端、规则来源和生成状态核对；世代、目标断点、HEAD、未提交数量、验证状态和交付状态没有旧值残留。生成后的主附件由操作者发送时，以候选当前消息实际收到附件作为送达事实，不要求独立机器回执。封条/哈希通过不能替代内容一致性核对；无法核对的字段已标为“待确认”并限制依赖动作。
- Goal、轮次、任务、授权卡、派生对象与可靠截点已写入项目状态索引；所有 ID 由 AI 或平台生成，不要求使用者本人提供。

交接完成前：

- 未停旧的可选预检期间，旧总指挥保持原唯一写权，候选只读；默认已真实停旧时旧方不再调度，新方完成交接回读前也不得调度；
- 旧总指挥生成候选封条后冻结新增业务；正常 `active → idle` 不单独使候选评分降级，只有新中央写入、重复调度、来源冲突或未解释漂移才使受影响结论失效；
- 候选身份在正式切换前失效（包括候选任务被归档、取消、替换或无法再次核验）时，旧候选的评分、封条、附件和“达到可切换”结论全部降为历史，不得继续正式确认或复用失效材料；旧方仍有效时由其登记并重新准备；已真实停旧时保留停旧状态，由接收方登记失效与恢复入口，重新核合法写者及授权，不自动恢复旧调度；
- 默认操作者实际停旧后一次发送附件与转权确认；可选候选预检核验仍有效基线及旧pending匹配后报告“可以停旧”，再由操作者停旧确认；无pending不要求返旧取票据，候选不得自行终止旧任务；
- 最终确认到达后，候选先复核配置/来源指纹、中央世代与单写者、候选截点失效条件、工作区聚合指纹和远端基线；通过后才更新中央登记并回读；
- 任一方不得在交接窗口启动新的全量推进、增量推进或专项调度。

操作者启动正常换任使用01场景1D。默认单段提示同时声明旧方已停止调度、接管断点相关写入已收敛，并把本项目调度权移交当前接收窗口；新方按轻量配置独立核验后，仅取得本次准备/提交权限，完成回读才取得业务调度权。自然语言完整表达同等门禁也有效，不要求操作者重复模板或填写技术参数。未停旧可先候选预检，材料通过报告可以停旧；不得要求正常返旧准备票据，也不能把附件、AI自称或末尾提醒代替操作者确认。

AI 为上述步骤生成发往另一窗口的文本前，须按 [02“为其他任务窗口准备提示词”](02-总指挥核心规则.md#为其他任务窗口准备提示词)核对场景 1D 模板；填参、补说明或等价自然语言不另立流程，准备文本本身不授权发送或切换。

自然语言不构成捷径：必须补齐 1C/1D 的预检、收口核账、快照交付、独立核验、真实停旧与直接转权确认；取消正常返旧不取消这些验收。

交接完成后：

- 使用者本人明确指定新总指挥；
- 操作者已停止或归档旧总指挥；旧历史保留；
- 新总指挥已完整读取轻量启动配置、建立本任务独立加载记录并完成来源指纹比对；异常规则已按需完整读取，后续具体动作所需规则仍按场景加载；
- 新总指挥完成切换前最小复核，在规范锁和可恢复日志下受控更新并回读中央入口、当前进度视图和状态索引，确认单写者唯一；
- 新总指挥只继承画像的五态、一次介绍状态、规则根级安全指针、schema、`profile_revision` 和待合并候选数：`enabled` 不重新询问，`paused / disabled / unavailable` 不读取正文，`unasked` 只在同一规则根没有可靠选择记录且正式接管后，于首个主回复末尾介绍一次；任何画像正文和旧外发授权都不继承；
- 新总指挥在从交接断点恢复前，必须先执行一次画像合并门：回读状态、`profile_revision`、Git 排除/未跟踪核验和待合并候选指针；按 11 的证据与隐私门逐项决定 `UPDATED / NO_UPDATE / PENDING_REVIEW / BLOCKED`。只有当前新总指挥可以写唯一本地画像；普通/专项窗口的候选不得直接改写。合并失败不撤销已完成的控制面切换，但必须在接管汇报中列出候选数量、实际写入、缺口和下一行动方；
- 新总指挥从交接记录中的第一次只读动作开始。

#### 接收方直接准备、受控提交与中断恢复

Prepare预检/正式生成、Candidate停旧建议与Takeover提交使用HandoffControl的同一只读存储检查；不合规索引/运行文件在停旧建议前拒绝，记录 `INPUT_REQUIRED / CONTROL_STORAGE`，保留原件，不以来源损坏概括。未停旧时不得建议停旧，已停旧时不得恢复旧调度。其他中央文档被Git跟踪时，新日志的 `workspace_projection.version=2` 仅容纳已核四目标plan的精确旧/新字节；原完整工作区先通过，再绑定非事务内容、索引、HEAD/tree/branch、文件模式及原inflight范围，写前/写后和恢复均重核。完整投影摘要写入不可变direct intent的 `workspace_projection_sha256`，恢复拒绝日志证据篡改、删除或无锚点投影；该字段随intent摘要及文件名绑定。完成态基线只能在该限定证据复核通过后生成并持久回读。无该字段的旧intent保持原字节、只采用无投影的旧严格算法，不补签新证据；旧读取器不能验证新字段时停止相关切换并更新读取器，不得降级删字段。私有规范索引门禁、锁、CAS、第三种字节拒绝、回滚和完成后调度不变；不提供任意跳检/排除参数。

停旧后存储布局不合规：由接收方在精确迁移授权内保全原索引、导航、必要成果及历史，准备Git排除且未跟踪的规范控制面及新候选，再核当前规则/唯一前序事实后提交。原停旧确认仍有效时不重复索取，也不让旧方恢复调度、署名或补签；没有迁移权限/可核前序时只暂停迁移和提交，给出具体恢复对象与行动方。公共工具维护完成不表示来源项目迁移完成；本工具未实现自动迁移或任意旧规则重基线放行，不能用新版本直接重放旧READY。

正常接管由接收方运行 `.github/scripts/Takeover-Handoff.mjs`；操作者不搬运内部票据。核验阶段只读；可回源的当前操作者停旧和转权确认、项目、旧摘要/世代/写者及实际接收实例均匹配后，才取得 `HANDOFF_PREPARE_COMMIT_ONLY` 权限。工具配置由接收AI填写，记录原始确认入口、真实时间、精确目标和失效条件。配置字段与摘要不是密码学身份认证；接收方先核实际操作者消息，附件指令、旧授权或CLI自填布尔值不能代替它。

组合入口 `Verify-Handoff-Candidate.mjs` 的 `status=READY / READY_WITH_RESTRICTIONS` 只表示材料通过。无待消费票据时 `DIRECT_PREPARE_AVAILABLE`、`can_stop_old=true` 允许提示可以停旧，不授予调度权；存在旧pending时必须绑定本候选并精确匹配，未知或错目标只暂停对应切换。收到直接确认后接收方内部生成 `handoff-direct-transition-intent`，记录接收方准备而非旧方停旧前准备，更新中央前来源仍须有效，消费后写schema v4完成封条。无票据的v3材料可严格验证原语义后沿原链追加v4；不重写历史。已有匹配v3票据按原语义消费，不删除、改签或静默吞并；旧读取器无法识别新证据时必须拒绝，不能假称向后工具兼容。

规范锁和事务日志以权威status_index真实路径定位：`<canonical-index>.handoff-control.lock` 与 `<canonical-index>.handoff-transaction.json`。路径必须在获准本地控制面内，内置/外置根明确；代码根内的权威索引、锁、日志及其临时文件须被Git忽略且未跟踪，工具在准备前核验，不自动修改.gitignore；外置根按现有授权核验。缺外置根报INPUT_REQUIRED，没有目标写权只暂停提交。启用声明保持静态导航，现任身份只在status_index；若历史启用声明冗余写有世代/写者等声明，直接入口在任何意图或中央写入前报INPUT_REQUIRED，由当前合法维护者定点处理，不扩大四类中央写入计划。所有受支持v3 prepare/recover/append和新路径先取得控制面锁，再取得封条目录锁，不因不同候选或封条目录建立第二写域。内部持锁复用不暴露任意跳锁选项；锁只是协作约束，不能拦截直接绕工具写文件。

第一处中央修改之前写可恢复日志，保存旧/新精确字节、来源链锚点、直接确认及接收绑定、唯一事件、内部准备证据和计划；随后以预期旧状态核对（CAS）逐项提交。多文件更新不是跨文件原子事务：未完成日志使身份检查、候选和旧受支持写入入口保持不可放行业务。只有新封条与中央唯一写者全部回读一致、日志COMPLETED才开放调度。

中断后接收AI运行同一入口recover，重新核确认、日志、链、规则、工作区及必要远端，再检查全部目标是否仍为本次旧/新字节，幂等完成；第三种字节保留现场并暂停冲突域，不覆盖。重复事件回读原结果，不递增第二世代；封条已存在不删除历史或盲目回滚。前向恢复因规则或保护工作区变化无法完成、且本事件尚无完成封条时，可由接收AI运行同一入口rollback：先核确认、原链与所有目标字节，只撤销本次精确匹配写入，保留其他变化、日志和不可变意图。回读后记录ROLLED_BACK_STOPPED，仍禁止ACTIVE及原事件前向恢复；重新生成受影响材料、处理旧pending和恢复调度须另核当前合法写者与授权，不自动唤醒旧方。已有完成封条、第三方控制字节或其他链事件时禁止回滚。残留锁不自动删除，须定位持有者及真实停止状态，必要恢复单独核权。

规则变化先登记RULE_REBASE_PENDING，接收方只保存受影响观察，不在旧写者名下重签。必须证明兼容及新基线足以支撑切换才能派生继续；来源不可核、重核失败或身份/权限/安全边界改变只暂停受影响切换。当前工具正常SAME路径可直接执行，无法证明漂移安全时给出具体恢复，不凭路径分类放行。无关远端不可观察可按v4显式REMOTE_UNOBSERVED完成控制面接管，仅限制远端依赖动作；v3的HIGH/COMPLETED仍要求远端PASS。运行/专业未测按下一动作依赖限制，不伪造通过。

来源严重冲突需旧方修复时，准备文本不自行授予跨任务发送权限，材料运输也不能代替修复后的新确认；不得恢复旧业务或继承旧授权。

#### 历史v3票据重基线恢复（仅适用于旧写者仍有效）

若旧总指挥仍有唯一写权、旧票据已准备而公共规则触发重基线，先确认唯一待消费票据、前序摘要、中央身份和全部控制面来源精确匹配。旧封条的非控制面来源允许已发生摘要漂移，但必须仍可读取，并在恢复记录中逐项登记实际摘要；缺失、不可读或控制面漂移不得绕过。调用 `HandoffSeal.mjs recover <seal-dir> <source-root> <previous-digest> <intent-digest> <recovery-event-id>` 追加不可变 `RULE_REBASE` 恢复记录。原票据保留，恢复记录绑定其摘要、旧世代/写者、时序和已观察漂移；旧候选立即失去停旧资格。随后旧写者按现场事实更新必要中央 CURRENT，在原链追加同世代同写者、来源已变化的 `CURRENT_ATTESTATION`，再以新规则与工作区基线生成新的 `MATERIAL_PREPARED` 附件及匹配票据。恢复记录缺失、重复、被篡改、旧票据已消费、旧写者已停止或身份冲突时，暂停受影响切换；不得移走旧票据、重置链序号、另起无前序链或先修改中央再倒填恢复证据。

#### 在途专项与交接保护范围

交接冻结旧总指挥的新调度、中央控制面和精确断点依赖的成果。已获授权且与该断点无关的专项普通开发可以继续；专项仍按自身授权、预算与停止条件执行。不得为了总指挥换窗一律冻结全部专项，也不能因目录叫“专项”就排除校验。

旧工作区算法 `git-diff-binary+untracked-content-sha256-v1` 保留全仓严格语义。新草稿可以显式采用 `git-scoped-index-worktree-sha256-v2`：旧唯一写者在 `workspace.inflight_scope.excluded_roots` 登记每个允许继续的目录及 `path_ref / owner / reason / ownership_source_ref`；最后一项必须指向同一草稿中已严格封存的归属证据；`ownership_root_ref` 默认 `source_root`，既有外置证据可显式绑定 `external_control_plane`，不复制成另一份中央账本。范围决议自身随封条绑定，候选不能临时扩大排除范围。默认未声明路径仍严格；中央五来源、规则、归属证据、必要未提交及忽略成果不得与排除目录重叠，共享盘点配置和控制面文件名仍严格。目录须真实存在，拒绝路径逃逸、符号链接、大小写或 Unicode 碰撞、范围重叠、跨边界重命名及未解决索引。外置控制面按实际物理位置核对，落在代码根内时仍不得与排除目录重叠；固定规则快照同样严格。当前范围算法只支持普通文件。

`readGitWorkspaceBaseline(sourceRoot, requiredRefs, inflightScope)` 生成新基线；准备、重基线和候选入口使用同一固定范围，并分别核验 Git 索引与工作树，不能仅过滤 diff。V2的 `index_sha256` 绑定保护路径索引；沿用字段名 `tracked_diff_sha256` 的槽位绑定保护路径工作树内容与文件状态，`untracked_digest` 绑定保护路径未跟踪及必要忽略内容。连续两次采集必须一致，附件临时文件落盘后再核同一范围；这不提供宿主级强制锁。范围外的暂存、未提交和未跟踪计数及内容变化仍使候选失效。已声明目录内普通未提交文件变化不使候选失效，但 `HEAD / tree / branch` 仍全仓严格；专项 Commit、远端变化及权限冲突不因范围排除而豁免。旧票据恢复只登记旧来源漂移，不代表新范围或必要成果已验收；旧封条、票据及恢复记录不改签，新算法仅用于合法续链的新草稿，读取工具至少采用包含本算法的版本，旧读取器不得静默降级。

正式 `sources` 只固定中央控制及精确断点确实依赖的成果。无关在途专项的活源码、测试和进度不作为实时硬来源；交接保存可靠阶段观察、下一行动方、失效条件与动态入口，必要冻结证据使用独立不可变时间片。已被旧封条收录的来源不能直接忽略；旧唯一写者须从合法链和真实当前事实重建新草稿，重新判断必要成果和范围。专项目标、责任、权限、预算停止、里程碑或中央下一动作发生变化时，重核受影响中央观察；后任在恢复相关业务前回读最新专项状态，不把旧观察代签当前验收。范围的业务独立性由合法写者举证，哈希工具不能代替依赖判断。

### 交接身份一致性与封条覆盖

正式交接的必读、准备和实时验证集合统一为状态索引、中央工作项清单、当前进度视图、实际项目中央入口和工作流启用声明。新准备的 `sources` 必须包含 `status_index / central_work_items / current_view / central_entry / workflow_enablement`；后两者可使用既有 `external_control_plane` 根，不新增控制面账本。项目入口不是公共规则00，必须按项目启用声明定位实际文件。启用声明只声明启用状态及导航，不保存独立的现任身份。

现任身份的唯一权威登记放在状态索引的 CURRENT 内。AI 自动写入下列结构化注释，实际平台标识只进入项目本地状态，不进入公共规则或日志；对话标题序号、世代、写者名称后缀与平台标识分别核验，不相互推导。实际世代或唯一写者的依据缺失、冲突时，只暂停依赖该身份的正式切换；平台映射未知不单独构成阻断，也不允许补造历史接管。

身份分流必须先确定唯一权威：状态索引 `CURRENT` 的身份和唯一写者是规范来源，中央入口、当前视图和工作项只保存导航或与该来源一致的派生视图。若只是派生视图残留旧世代、缺少新版导航字段，且状态索引、平台任务映射和唯一写者证据一致，登记 `CONTROL_PLANE_MIGRATION_REQUIRED`，由当前唯一写者在已授权范围内最小修复、逐份回读后再继续；操作者称呼或确认本身不能替代这些证据。若状态索引 `CURRENT`、平台映射或唯一写者彼此冲突，登记 `CONTROL_IDENTITY_CONFLICT`，只暂停正式切换和控制面写入，不覆盖旧记录、不生成新封条。

### 交接材料的交付说明

候选材料的判定必须同时报告 `chain_status`、`control_status` 和 `handoff_ready`；结构链 `PASS` 不得单独推出可切换。候选在正式切换前被归档、取消、替换或失联时，已有候选材料立即标为历史失效，不能继续使用或改名复活。

交付前须生成真实项目实例封条，并用实际来源根目录验证；合成测试通过、补写故障说明或候选再次评分均不能代替该步骤。同一已知阻断未解除时，不要求操作者重复转发旧材料。只有 `READY / READY_WITH_RESTRICTIONS` 表示候选材料就绪；`BLOCKED` 期间的诊断文本不是正式交接附件，不得使用 `final-*`、不得发送给候选评分，也不得作为候选截点。移交方尚未停止或归档不单独扣分；实际切换仍执行第二阶段操作者确认与世代/单写者门禁。封条目录、事件编号和预分配快照 ID 先写入索引，封条摘要与回算结果在仓库外便携快照中提供，避免回写被封条按全文哈希覆盖的来源。正式主附件文件名必须包含稳定项目标识和递增版本；诊断草稿如需落盘使用 `draft-*`，两者均不得只有通用前缀与日期。正式状态只允许 `READY / READY_WITH_RESTRICTIONS / BLOCKED / COMPLETED`；未注册颜色码、拼写近似或自定义缩写不得代替正式状态。

#### 交接失败后的分层诊断与一致性交付

- 分开核验“窗口能否发送并取得正文”“材料是否可读且一致”“身份是否可切换”。认证方式、供应商或模型切换与故障同时发生，只构成相关线索；没有错误原文或必要日志时，不宣称它导致上下文丢失、文件损坏或状态漂移。仅核对必要的非敏感环境信息，不读取或传播令牌。新建或分支窗口可以恢复通信，但不能证明成果和身份已经接续。
- 草稿恢复提示词和附件仅作为输入。核对其中项目、移交方、候选名称与当前任命；不一致时暂停身份切换并请求确认，继续无关的只读核验。恢复按相关性和授权逐层读取，不承诺恢复不可见思路或完整记忆，不以“资料足够”自行取得中央写权。
- 收到候选冲突报告后，先回读精确附件和实际文件；区分候选收到旧副本、生成时漏更新、生成后事实变化。未取得证据前不选择其中一种作为根因。一次只修正文而留下 JSON current 的旧字段，不能算材料已同步。
- 交付前以同一事实截点逐字段核对快照、清单 current、进度与索引：HEAD、远端基线、暂存/未提交/未跟踪成果、worktree 存续、阻断、行动方及规则指纹。历史保留在历史区；已删除对象的旧统计不得继续冒充 current。先保存受影响文件，再计算实际指纹，最后回读交付物；核验未通过不得声称可交付。指纹匹配不等于语义完整或测试通过。
- 区分更早的前任、当前移交方和新候选。更早前任归档不能证明当前移交方停止；候选只读核验期间允许移交方存在。正式切换时按已有门禁确认当前移交方停止调度；平台 idle/archived、操作者确认和不可观察的进程状态分别登记，不要求以平台未提供的进程证据无限阻断。
- **运行状态不可观察时采用两阶段判定。** 第一阶段由候选核对交接材料、实际工作区、规则指纹、平台任务可见状态、未提交成果及必要证据；平台任务列表只能证明平台可见状态，不能单独证明某个窗口的后台进程仍在运行。若平台没有进程级证据，将该字段记为“不可观察/UNKNOWN”，不得仅因缺少不存在的证据无限期阻断切换。运行状态确认可与附件在同条输入中到达，经材料核验后生效；独立核验操作者当前消息对旧窗口运行状态的明确人工确认，并独立记录确认原文的最小摘要、确认来源（操作者当前消息）、确认时间（含时区）、适用范围（旧窗口已停止、不再接收新业务消息或执行任务）和失效条件。
- 操作者明确确认“旧窗口已经停止、不再继续发送消息或执行任务、允许按当前材料继续交接”时，该确认可以解除“旧窗口是否已停止”的观察性阻断，但不能替代快照、文件内容、Git、工作区、规则指纹、未提交成果或其他基线核验，也不产生远端写入或旧授权继承权。两阶段均通过时，候选应明确报告“交接条件已满足”，不得继续要求平台提供其无法提供的进程证明。
- 默认操作者先停旧，再一次发送附件和正式转权确认；可选候选预检材料通过即可报告可以停旧，不要求旧方另取票据。确认停止后旧方不得接收新业务；再次唤醒旧方或观察到其新调度/中央写入时，只重核受影响运行状态、单写者、工作区与断点，不能继承旧授权或以提醒代替事实。
- 1D 的最小复核由 `.github/scripts/Verify-Handoff-Candidate.mjs` 统一执行：它在封条链和 CURRENT 身份通过后，重新验证 live 规则 manifest、工作区聚合指纹和下一步依赖的远端基线，并核验无pending的直接准备可用性或已有pending与本候选的精确匹配。`HandoffSeal.mjs verify` 的 PASS 不得单独写成候选通过。规则漂移返回`RULE_REBASE_PENDING`，由接收方定点分类并保留恢复入口；历史旧写者仍有效的v3重基线路径单独按本章处理，正常路径不要求返旧取票据。无法证明兼容时只暂停对应切换；远端暂不可观察与来源损坏分开登记；正式接管后旧候选只按历史链核验，不用切换后的 CURRENT 反向否定已完成接管。
- 附件应带可区分的版本、事实截点和文件摘要，接收方先报告实际读到的版本。原路径被改写不能证明已发送附件同步更新；内容变化时明确重新发送最新附件，或在同工作区按获准精确路径核验。仅继续解释且事实未变，不自动使快照失效；事实改变时只刷新受影响材料。所有必要修改完成后才生成最终快照。

旧总指挥完成场景 1C 后，最终回复必须明确给出唯一默认转交入口：项目化命名的正式人类可读交接快照 `.md` 文件链接，并直接写明“实际停旧后，只向新候选发送这个附件和场景1D提示词”。当前项目示例命名为 `ChatGPT-Workflows-commander-handoff-YYYYMMDD-final-N.md`；实际编号和完整路径以本轮工具回读为准。机器记录 `.json`、封条、manifest、校验回执和中央状态只供 AI 核验，默认不要求操作者转发，也不得把它们与主附件并列后让操作者猜选项。同一工作目录且候选有权读取时，由候选沿主附件指针读取实际文件；换目录、换电脑或必要材料不可访问时，必须单独列出缺失项和获准恢复方式，不能把主附件当成代码备份包。

下一步指向01场景1D单段标准模板，明确发往实际接收窗口：操作者先实际停旧，再一次发送主附件及转权确认；新方独立核验后内部准备、提交和回读，不正常返回旧方取票据。可选先做只读预检，通过后再停旧确认；自然语言完整表达同等目标与安全门禁也有效，不强迫重复模板或填技术参数。操作者自行新建和发送时不继续代建、代发；自动创建受阻只说明具体缺口，并提供同一模板和附件的人工路径。候选仍须能访问正确项目和必要成果，人工创建不绕过权限或完整性核验。

交付前核对主附件、补充材料条件、模板位置、接收窗口和当前阶段；候选核验或正式切换前，若规则基线、中央身份、工作区、远端或当前断点发生变化，须刷新受影响的清单指纹与快照，并明确使用最新版本。普通进度更新不要求重新生成候选附件；已完成接管后只按影响范围重核后续动作。该检查用于约束交付，不新增提示词、编号场景或独立状态台账，也不保证模型与平台永不遗漏。

面向操作者或接收窗口的正式交接快照不得使用孤立的 `handoff.md`、`snapshot.md`、`final.md` 等无法区分任务归属的默认名称；应使用稳定项目或任务 slug、日期、材料形态和递增编号，例如 `<project-slug>-commander-handoff-YYYYMMDD-final-2.md`。slug 不得包含真实用户名、凭据、完整任务 ID 或其他敏感信息。本条只约束人类可读附件；机器可验证的 `handoff-state.<sequence>.<digest>.json` 等封条文件名继续遵守其固定合同。

外部正式交接快照文件名必须使用同一事实截点下的递增编号，例如 `codex-handoff-YYYYMMDD-final-2.md`、`final-3.md`；只在对应 `MATERIAL_PREPARED` 封条实时验证通过且 `switch_status=READY / READY_WITH_RESTRICTIONS` 后生成。正式生成调用 `.github/scripts/Prepare-Handoff.mjs <config-json>`；配置与规则 manifest 格式分别参考 [HANDOFF_PREPARE.config.example.json](templates/HANDOFF_PREPARE.config.example.json) 和 [HANDOFF_RULE_MANIFEST.example.json](templates/HANDOFF_RULE_MANIFEST.example.json)，占位符必须替换为本轮实际路径与 SHA-256。需要提前判断可行性时，将配置中的 `preflight_only` 设为 `true`；它只读核验项目绑定、代码根、外部控制面、来源摘要、输出路径和工作区保护摘要，不创建封条、不生成 `final-*`。工具自动定位自身工作流根并核对封条工具受 Git 跟踪、规则 manifest、真实 `source-root`、可选 `external_control_plane_root`、CURRENT/HISTORY 结构、Unicode 路径、v3 草稿、实时来源和二次漂移；封条目录必须位于来源仓库内且实际命中 `.gitignore`，正式附件与回执必须位于规则仓库、来源仓库和外部控制面仓库之外。附件先写临时文件，附件 SHA-256 写入 `GENERATED_NOT_DELIVERED` 回执，最后才以不可覆盖方式原子生成 `final-*`。任一步失败不得留下正式文件；已经追加的不可变封条不删除，按失败事实留待诊断。阻断期间如需保存诊断草稿，使用 `codex-handoff-YYYYMMDD-draft-2.md` 等明确草稿名，不得改名冒充正式附件。不得用同名文件覆盖已发送版本。旧文件保留为历史兼容副本，并在新快照中明确哪个文件是当前主附件。快照正文、状态指针和发送说明必须指向同一个编号版本；生成新版本后，旧版本不得继续作为当前交接依据。

### 交接准备预检的强制执行顺序（2026-10-03）

真实交接反馈表明，规则文字已有多项门禁，但如果先手工拼草稿、再让最终生成器逐项报错，仍会产生长时间返工。以后准备交接必须把 `preflight_only` 当作第一道机器门，而不是失败后的补救工具：

1. **先锁定事实截点与规则基线，再生成预检输入。** 读取中央 CURRENT、唯一写者、工作区和远端后，固定 `fact_cutoff`、候选 `rule_baseline`（候选冻结快照）、公共规则源的 `live_rule_epoch` 和候选 ID。规则源变化时先分类，不把版本号相等与否当作唯一冲突条件：同一快照继续；公共规则前进且不影响当前门禁时记为 `NEWER_COMPATIBLE`；触及 01/02/04/07/09/10、schema、封条/生成器、身份、权限或安全边界时记为 `AFFECTED_RECHECK`。先沿同一断点重建新草稿并回读，再把新草稿交给 `preflight_only`；旧草稿只保留历史。候选只在重基线完成后才标记 `SUPERSEDED_BY_RULE_REBASE`，不得把所有版本变化统称为 `SUPERSEDED`。
规则基线变化的处理必须可恢复：如果只是公共规则版本更新，候选不得要求操作者在旧/新版本中择一，也不得把尚未受影响的业务和只读核对全局阻断。候选自动登记 `RULE_REBASE_PENDING`，在原断点重新捕获规则根、版本和 manifest 摘要，定点重读受影响的 01/02/04/07/09/10 或轻量配置，并先生成一份新的候选草稿；旧草稿保持只读历史，不能直接送入最终预检。新草稿必须重新计算来源摘要、工作区聚合指纹和必要远端观察，再运行 `preflight_only`。回读通过后将旧候选标记 `SUPERSEDED_BY_RULE_REBASE`，沿同一世代、单写者、工作区和断点生成新的候选截点；只有规则来源不可核验、重基线失败，或新规则改变身份/权限/安全边界时，才阻断正式切换。远端临时不可观察时，若下一步不依赖远端且草稿明确使用 `READY_WITH_RESTRICTIONS`，只记录 `UNKNOWN` 和恢复条件，不把网络错误写成来源损坏或全局阻断。1E/1F 只暂停依赖变化规则的接续动作，保留其余低风险断点。
2. **先做结构预检，再生成草稿。** 由预检读取 schema、来源类别、`root_ref`、模板必需占位符、项目绑定、输出路径和 `.gitignore` 边界；预检未通过不得手工追加封条。未知字段、来源类别不匹配和模板缺占位符必须在草稿阶段报告可执行的修复位置。
3. **远端探针与生成解耦。** 远端暂不可达、超时、连接重置、权限失败和基线漂移分别分类；同一 `fact_cutoff` 内已有成功观察可作为带时间和命令的复用证据，网络失败只允许有限重试和退避，不得把网络错误写成来源损坏，也不得无限等待。若当前交接下一步不依赖远端，候选可降为 `READY_WITH_RESTRICTIONS`，将远端写成 `UNKNOWN`、保留错误和恢复条件；只有需要远端基线的下一步才阻断。
4. **候选登记唯一化。** 在中央索引中预登记稳定候选 ID、封条目录、草稿、规则摘要、事实截点和状态；同一项目同时只能有一个 `ACTIVE` 候选，旧候选只能是 `SUPERSEDED / CANCELLED / HISTORY`。目录扫描只用于核对登记项，不以递归发现的目录名猜当前候选。
5. **附件与封条保持两阶段。** 主附件 ID 先登记但附件正文、大小和 SHA-256 只能写入封条来源之外的交付回执或外部清单；生成后回读封条、来源和回执，必要时追加独立 current attest，不把附件路径或哈希回写进其自身封条来源。

这些步骤不改写旧 v1/v2 链，也不把网络暂不可达升级为总阻断；它们只把失败尽量前移到可解释的只读预检阶段。

本段中的 `codex-handoff-...` 仅作为历史兼容示例；新生成的面向人类附件必须遵循上一段的项目/任务 slug 命名规则。机器封条和历史文件不因本条改名。

若封条已经成功追加但外部附件或回执写入中断，下一次准备必须先按事件 ID、世代、写者和封条摘要校验并复用原封条；不得重复追加同一事件或把链序号推进两次。复用仍须重新执行实时来源、规则 manifest 和附件内容校验；校验不一致时保持阻断并保留原封条供回查。

### 调度任务核验与重建说明

交接材料必须把“核验已有调度任务”和“任务缺失时从零重建”视为两个不同状态，不得用同一个“调度已恢复”字段混写。重建说明模板位于 [templates/SCHEDULER_REBUILD_GUIDE.md](templates/SCHEDULER_REBUILD_GUIDE.md)。交接快照应附带完整的非秘密重建条件，包括原始提示词、类型、名称、模型、推理设置、周期、时区、绑定对象、通知设置、状态和暂停/恢复条件；它仍不是任务创建授权卡，也不包含凭据。

1. **核验现有任务：** 只读查询任务是否存在、是否重复、是否可访问，并核对状态、周期、时区、抽象绑定和配置指纹。任务存在且指纹匹配时登记 `VERIFY_ONLY`；任务存在但发生漂移时只暂停受影响对象并展开差异，不自动修改任务。
2. **确认缺失后重建：** 只有只读查询在当前可访问范围内确认任务缺失、没有重复候选、重建条件可以安全读取时，才登记 `REBUILD_CANDIDATE_ONLY`。候选可使用交接快照中完整的非秘密提示词和配置条件，但不包含任务 ID、凭据或不可公开的秘密值；创建/恢复必须由操作者针对精确对象、动作和有效期另行授权，旧授权一律不继承。
3. **无法唯一判断：** 任务查询不可达、结果为空但接口语义不明、周期/时区/绑定含糊、配置指纹缺失或发现重复任务时登记 `BLOCKED`，不得自动创建、修改、暂停或恢复任何调度。只报告受影响范围和最小人工核对动作。
4. **写后验证：** 获得新授权并完成平台动作后，必须重新只读回读任务状态、周期、时区、抽象绑定和配置指纹；回读失败只能登记“结果未知/待核验”，不能写成已恢复或已运行成功。说明指纹一致只证明说明未漂移，不证明任务存在或执行成功。
5. **交接记录：** 交接快照保存本次重建所需的完整非秘密条件；`AI状态索引.md` 仍只保存说明路径、版本、SHA-256、状态和适用范围指针，避免建立第二份配置账本。快照不得保存任务 ID、凭据或秘密值。说明、入口、提示词、周期、时区、绑定、规则或授权任一变化时，相关候选和快照立即失效并按受影响范围刷新。

该分层不改变现有调度，也不产生创建、修改、发送或恢复权限。交接检查至少要用两个可验证例子覆盖：已有任务存在时只产生核验结论；任务缺失时只产生待授权重建指导，且任何缺少授权或存在歧义的输入都保持暂停。

### 正式切换后的专项联络恢复

本节是换任后专项汇报对象更新的唯一执行协议，不替代创建时的握手，也不引入定时心跳或消息总线。

1. 候选阶段只读定位现有专项的逻辑任务、批次、状态、输入与产物版本、精确断点，以及未送达或在途回执；不得发送换任通知、恢复业务或取得中央写权。平台 ID 只是定位线索，不代表访问权；换账号后须重新核验可达性。
2. 操作者正式确认切换、旧总指挥停止调度且中央单写者回读通过后，新总指挥才按本轮有效通信授权通知需要继续协作的专项。通知包含新汇报对象、世代、已核验断点和执行边界；不继承旧授权或运行进程。授权缺失时仅暂停对应通信，不把所有无依赖工作一并阻断。
3. 发送成功只登记 `source_delivery_status=SENT_PENDING_CONFIRMATION`；收到专项对新汇报对象、世代、断点和边界的明确确认后，才能登记 `source_delivery_status=RECEIVED_CONFIRMED`。单向工具回执不能证明双向可用。需要回执的消息按 `09` 的强制状态协议带唯一 `MESSAGE_ID` 和 `ACK_REQUIRED`；传统回执状态仍使用 `RECEIVED / BLOCKED / COMPLETED / FAILED`，但 `local_processing_status` 与 `source_delivery_status` 分开记录，不能把“本地处理完成、等待对方确认”合并成 `COMPLETED`。专项仅更新自己的短状态并回复确认，中央索引仍由新总指挥唯一写入。暂停专项的通知须明确“仅确认联络，不恢复执行”；若平台发消息必然触发业务续作，保持暂停并记录联络待核验。已完成任务从归档产物恢复证据，不为握手无谓唤醒。
4. 对执行中或结果未知的动作先只读核账，不重复派发，也不把旧进程认作新总指挥已接管。迟到的旧回报按逻辑任务、批次、输入与产物版本及已处理回执核对：匹配且未处理的证据登记一次；重复回执只关联已有记录；版本冲突保持待核验，不覆盖当前状态。旧总指挥的迟到指令不恢复其调度权。
5. 不可达或确认失败时，优先只读收取已有状态与产物；确实需要人工时给出最小转交内容和目标窗口。不自动重建或删除任务，不冒充专项确认，不为恢复联络扩展通信、远端或资源授权。无法安全继续的专项保持原状态并说明恢复条件。
6. 在已有任务表或联络记录中保存最小记录：逻辑任务、批次、版本、汇报世代、`MESSAGE_ID`、联络状态（未通知 / 已发送待确认 / 已收到 / 已阻断 / 已完成 / 已失败 / 不可达 / 归档取证无需通知）、确认与去重证据指针、下一行动方。读取接口不可见与目标没有收到分别记录，不用 `items: []` 单独判定丢失。真实平台任务 ID 仅用于获准的运行时联络，不写入公开仓库。联络未完成与调度权已切换分别报告，必要联络缺口未解决时不得称交接完全成功。

执行与独立审查协作（内部子 Agent、独立任务窗口或混合）时，按 [协作规范](docs/EXECUTION_AND_INDEPENDENT_REVIEW.md)保存原身份、逻辑角色、当前阶段、成果版本、问题状态、轮次与下一行动方；需要继续参与的两角色分别确认，不用一方确认代替另一方。内部助手结束或父任务交接前，按协作规范保留成果、原始证据入口、审查覆盖、轮次及授权边界；恢复先核对实例可达性和已有副作用，不假设助手仍存活，不重复执行或清零失败次数。人工反馈可直接到执行者，按已激活的共同契约继续有界互审或有限返工；开批简报、终点和例外交收口方，正常阶段不逐条转交。项目已有总指挥时仍由唯一总指挥写中央状态；累计失败及上限不因新消息清零，通信权限不足只记录待转交，不自行补授权。

### 6.1 最终交接汇报

本轮切换尝试结束，或恢复尚欠最终交付的接管时，必须向操作者发送独立完整的最终汇报，不能用状态文件或过程回执代替。适用范围与输出格式只维护在 [轻量启动配置第 8 节](总指挥轻量交接启动配置.md#8-统一接管汇报模板)，默认四句人话摘要，技术字段按需补充。已最终交付的交接不因中断恢复而重新收口；身份核验是业务恢复的前置，核完回到当前请求。跨账号、跨任务或同任务正式换任均遵守此范围，普通阶段推进不自动产生新世代。

- 身份按 10 规定的 discovery 顺序核验当前窗口平台实际任务 ID 和世代并记录探针证据；需要技术详情时才展示。平台确实不可见时写 `UNKNOWN` 及原因；尚未尝试时不得把 `UNKNOWN` 当作不可见。逻辑 ID、角色/写者 ID 或任务标题不得替代。ID 字段的可见性不单独决定切换状态；状态仍根据中央回读和其他控制面证据判定。ID 不产生跨账号、跨项目或跨宿主的访问权限，真实值遵守仓库禁止落盘边界。
- 结论：分别说明调度权切换是否完成，以及当前交接范围的必要证据是否齐备；存在未解决的重要缺口时不得笼统宣称“完全成功”。列出接管截点、旧写者停止与中央回读依据，并确认旧授权未继承。
- 关键缺口：只列影响交接可靠性或下一动作的问题，逐项说明已确认事实、待确认部分、实际影响范围、是否阻断切换、下一行动方及最小验证方式。没有有据可查的问题时明确写“未发现关键阻断”，不得为凑清单虚构问题。
- 边界：单写者、授权、当前活动断点或当前恢复必需证据不可靠时，仍阻断受影响的切换/执行；历史无关证据、辅助材料及画像适配问题仅暂停依赖它们的动作。未获授权而正确暂停的远端动作是授权门禁，不等同于交接失败；同样不能把未验证写成通过。
- 下一步：写明精确断点、可继续动作和仍暂停动作，并按 [03“每次汇报的下一步说明”](03-专项任务卡模板.md#每次汇报的下一步说明)给出当前行动方与最小操作，不自动扩大任务范围。新规则不追溯证明旧接管合规；发现既有接管结论过宽时如实收窄并记录依据。

## 7. 交接失败处理

如果没有稳定截点、存在重复调度、任务断点缺失或事实冲突，不宣布交接成功。正式切换尚未完成时，旧总指挥尚未停止则继续由其作为唯一有效控制面；旧总指挥已经停止或归档则保持无新调度者状态，不擅自恢复旧任务或激活候选，只列出最小补救动作。正式切换及中央单写者回读已经完成后，单个专项联络失败仅暂停依赖该联络的动作，不撤销已核验的中央登记，也不恢复旧总指挥；若发现中央身份或单写者证据本身失效，则暂停受影响调度并重新核验。

候选报告交接材料不可读、事实冲突、断点缺失或完成声明无法回溯时，按操作手册场景 1I 回退：由操作者把“交接失败时如何处理”提示词发送给移交方 AI，并要求其在原现场修订交接材料。场景 1I 只修复证据和快照，不改变中央调度权、唯一写者、远端授权或未提交成果；不得把新建空白对话、重复发送业务或平台“已完成”标记当作修复。移交方返回修订材料后，候选必须重新执行场景 1D 的独立只读核验；在此之前保持交接失败/不可切换状态。
