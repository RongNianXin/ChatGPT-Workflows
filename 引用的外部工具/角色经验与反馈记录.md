# 角色经验与反馈记录（AI 内部记录）

本文件只保存已经去重、核验并适合跨项目复用的经验。单个项目的原始聊天、私密材料、未核验结论和完整第三方角色正文不写入这里。

## 记录格式

每条经验由中央总指挥整理为：

- 工具编号 / 角色：
- 来源、版本或哈希：
- 适用项目类型或任务：
- 观察到的问题或新增价值：
- 证据位置：
- 建议动作：保留 / 调整说明 / 更新角色 / 新增角色候选 / 暂停使用
- 验证结果：
- 影响范围：
- 失效条件：
- 状态：`PROPOSED / VERIFIED / APPLIED / REJECTED / UNKNOWN`

## 自动反馈流程

1. 项目总指挥从自然语言中识别这是使用反馈、角色优化建议还是新增角色需求。
2. 它只读取判断该反馈所需的最小材料，生成结构化建议包，不直接改共享角色或中央状态。
3. 中央总指挥按来源、版本、角色和问题去重，核对证据后更新共享状态、工具 README 或安装记录。
4. 没有证据的意见保留为 `PROPOSED` 或 `UNKNOWN`，不直接改变角色文件。
5. 更新后回读共享状态和受影响项目入口；项目总指挥下次调用时自动看到最新状态。

自动化指 AI 整理与去重，不表示后台监控或自动发送已启用。跨窗口提交建议包须在当前有效通信授权内；未授权或不可达时先保存在当前项目允许的本地记录中，说明待汇总，不能声称中央已收到。共享库和公共规则仍只由获准维护者写入。

操作者始终只需要对当前项目总指挥说自然语言，例如：“这个角色对微信小程序表单检查帮助不大，建议增加异常状态检查。”

## EXT-001：完整职责覆盖、持续绑定与专项阶段调用

**事实与原因：**一个开发目标在首次适配时被缩成玩法复查；提出异议后才扩展候选。内部指南“选择一个角色”和引用契约“只推荐一个最小角色”混淆完整需求覆盖与当前调用规模。已有六份角色安装文件未进入共享登记，其他项目仅看中央记录无法复用。以上是本次可核验缺口，不能推导所有AI都会遗漏。

**共同方案与实施：**按场景5A，由维护者执行、另一项目总指挥只读独立审查，原身份与写权不变。先覆盖目标、交付物、阶段及平台职责，做轻量遗漏/不适配检查；关键未知最多追问1～3项，复杂或关键风险才评估独立分析者。安装集合、阶段加载与单次调用分开；代码审查不冒充引擎实现专家。长期职责、阶段和单次结果在唯一私有 `external_role_binding` 中分开保存，正式契约见 [`共同规范第2.1与5节`](外部工具自动对接规范.md#21-先覆盖职责再选择安装和调用)。

**持续工作边界：**调用开始前保存并回读消费、基线、原开始时间及恢复锚点；失败/未完也占一次，恢复续同次不清零。自足专项卡带有序阶段和触发条件，授权内自主继续，里程碑/终点及例外汇报；暂停、撤销、人工验收和独立互审终点收口优先。03/04/07/10及轻量交接配置提供紧凑恢复指针，继任者自行读正文核权；母任务换任不撤销专项职责，未取得实际加载确认不称迁移完成。不保证无限交接永不遗忘。

**共享核验与证据：**六份既有安装记录、原始副本及对应 TOML 的摘要匹配；固定上游版本字节独立核验，实际文件与指令解析回读。共享 JSON新增六条，保留原工作流架构师，不重新安装、不改全局配置。摘要和路径由 [`角色共享状态.json`](角色共享状态.json) 唯一登记；源项目原始聊天、标识与业务记录仅留私有证据。

**验证与失效：**文档入口、恢复链、消费/停止契约和共享登记结构作静态回归，实物摘要单独核验；最终结果见CHANGELOG。真实模糊需求覆盖、压缩/换窗/换任恢复、中断消费、局部角色失配、撤销与阶段自主调用仍待来源专项试验；文档通过不代签运行、原生发现或产品效果。来源、实物、权限、预算、目标或阶段计划变化时重核受影响部分。状态为 `APPLIED / LIVE_RETEST_PENDING`。

**独立产物复核收口：**第二轮实际读取必要正文及所有紧凑恢复入口，独立重核稳定版本、全部23项清单、入口检查及7份TOML解析/文件/指令摘要，与执行者冻结基线一致。职责覆盖、开始前消费、阶段行动/终点门及续接四项意见在静态契约层关闭；模糊目标、仅安装、压缩/换窗、中断、单角色失配、暂停/撤销、阶段触发及母任务换任八情形静态核对通过，无实质返工项，双方一致收口。审查者未重跑全仓检查或加载角色作为专业指令，作者检查与独立检查分别记账。真实专项试验未启动，原一次只读试验及预算不因新版新增；停止本次调用或暂停业务不等于撤销长期职责。

## EXT-001：单角色试验与安装后任务续接（历史截点）

本次在已授权范围内只共享安装 Workflow Architect，并由一个独立实例实际解析、完整读取角色正文，完成一轮有界只读审查。来源版本、原文件与安装文件指纹由共享 JSON 唯一登记，实际业务绑定留在任务私有记录，不存入共享库。本轮未安装其他角色，未修改产品代码或全局配置，未执行远端操作。

基线已有来源定位、共享复用、项目权限、AI 预填激活卡及一轮审查机制。审查新增四项发现：入口承诺与触发条件不一致；任务绑定缺少启动/恢复指针；绑定生命周期和本轮结果混用；安装后部分说明仍保留“未安装”的旧断言。已分别明确首次名称或专业审查意图触发、03/10 的绑定指针、绑定与结果分开登记、当前事实按共享登记及实物核验。已确认安装和使用后连续调用，完成一轮后待命；保留累计成本与已用轮次，不通过恢复获得新预算。

验证分层：TOML 解析与安装/正文指纹匹配，独立实例报告完整加载并完成限定审查；文档、共享 JSON、受管 manifest 和入口检查另作确定性核验。未验证原生自动发现、其他项目真实首次调用、压缩后的自动续接或用户体验改善。文档补齐不能写成所有窗口自动继承身份已经通过。

通用经验：安装、加载、绑定、单轮执行与任务效果分别记录；操作者只表达目标，AI 负责恢复角色指针、当前权限、预算和下一动作。新项目复用文件并建立自身绑定，不继承前项目权限。没有工作流入口的新聊天不会凭文件存在自行发现角色。失效条件为来源或实物变化、任务目标/权限改变、指针失效及预算耗尽；状态为 `APPLIED / LIVE_RECOVERY_PENDING`。

## EXT-001：规则已通知但自然语言调用没有进入正式工具目录

### 事件与证据边界

本次核对一个外部项目窗口连续两次可见记录：前一轮为规则更新，后一轮为“Agency Agents＋当前开发目标＋只读判断”。用户已经提供规则来源，并未要求安装、产品修改或远端操作。公共记录只保留可复用事实；原始对话的项目名称、任务标识、机器路径和业务材料不进入本文件。

规则更新轮读取的 manifest 为较早版本，核心文件中一项脚本内容与清单摘要不符。窗口仍报告刷新完成并采用可核验部分。它还执行了目录遍历和文件字节读取，但相关输出只呈现文件数量及大小，没有呈现相应正文；这些操作不能证明当前模型实际阅读并理解全部规则。仅凭该证据不能确定脚本与清单失配的修改时序，也不能证明其他窗口都成功更新。

调用轮优先搜索全局技能、插件和产品目录，没有读取正式外部工具目录、工具 README、维护记录或共享状态，随后要求用户提供上游链接或本地路径。然而正式登记中已经保存来源地址。查找路径没有进入登记源，是这次“AI 不知道工具在哪里”的直接证据；不是上游地址缺失或必须让用户重新填写。

独立核对本库共享状态：角色列表为空、共享根未建立，维护记录也明确未安装。因此“路由失败”和“尚未安装”同时存在，必须分开修复；补通入口不会让角色自动变成可用，更不证明角色审查或项目效果已完成。

### 通用问题及原因

| 问题 | 已有依据 | 影响 |
| --- | --- | --- |
| 刷新范围没有包含工具发现契约 | 原 manifest 只列核心工作流与脚本，工具目录不在其中 | 新工具文件夹已登记，但旧窗口刷新后仍可能没有名称到入口的映射 |
| 文件读取与正文理解混淆 | 遍历和字节统计没有向模型呈现必要正文 | 显示读过文件不能保证模型知道工具来源或规则内容 |
| 校验失败却报告成功 | 必需脚本失配后仍称完成并部分采用 | 用户误以为新版本生效，后续请求依赖了未成立的前提 |
| 先查技能目录，跳过正式登记 | 调用记录没有读取正式索引 | 将角色提示词库误当成必须存在于 skills/plugins 的插件；未搜到被混写成来源未知 |
| 文档中的“本项目”来源含糊 | 跨项目契约原来要求阅读“本项目 README” | 产品项目与规则来源不同，目标 AI 容易到产品根找不存在的文件 |
| 共享复用与项目安装表述冲突 | 共享规范要求统一目录，指南却推荐项目单独安装 | 新项目无法确定安装位置，可能重复安装或误认局部副本是共享版本 |
| 只验证模板词语和链接 | 既有入口测试是静态检查，没有真实跨项目调用证据 | 文档检查通过被过度解释成自动接入已经可用 |

### 本次措施

1. 增加统一自动对接规范，把工具名称、编号或登记别名路由到已核验规则来源中的正式目录，再到唯一工具 README；不先泛扫全局技能，也不要求用户补已登记的信息。
2. 将工具目录与共同发现契约纳入刷新 manifest；统一各消费者按 manifest 的仓库根前缀解析，保持相对路径可移动，不把作者机器路径固化成依赖。
3. 刷新必须把正文实际呈现给当前模型并补读截断内容；任一必需校验失败不得称完成或部分采用新版本。源变化时取消该批，校验稳定后再刷新。
4. 将已知来源、安装状态、实物哈希、本项目激活权限分开；默认共享安装、项目独立激活。未安装仍可只读核对实际候选，不能宣称正式角色绑定或审查完成。
5. 将跨项目提示词改为 AI 内部契约，用户入口保留在工具 README。共享库维护与本仓库中央登记分别核权，规则更新不产生用户目录写入许可。
6. 为新增工具模板加入跨项目冷启动、入口迁移、未安装、共享复用、失配、权限及来源不可访问的验收矩阵；EXT-002、EXT-003 均使用相同机制，不靠聊天提醒扩散。

### 以后登记外部工具的完成标准

接入至少包含正式来源和识别名、唯一用户入口、共享或安装状态入口、维护与反馈责任、AI 内部调用契约以及跨项目验收证据。只建立文件夹、只写 README、只通知“规则已更新”均不充分。所有需要读者自行猜测的路径、角色名和配置字段，先由 AI 从登记恢复；真正缺少来源锚点或存在歧义时，才向操作者请求最少补充。

规则发布前核对完整受管指纹，冻结期间不得继续修改；目标窗口刷新成功后，用仅含工具名称和目标的自然语言检查能否找出正式来源、安装事实和最小候选。登记、安装、激活和任务效果分别验收，不用一项成功代替其他状态。反馈先保存在当前项目允许的记录中；跨窗口汇总仍须通信授权，不承诺未授权的自动发送。

### 验证与失效条件

本次结论基于可见聊天动作、仓库正文与安装记录，不推测来源模型的内部原因。文档契约、manifest 内容与文件解析的回归见仓库测试及 CHANGELOG；静态验证不证明未来模型注意力、跨设备访问或真实角色效果。修复后的真实窗口复测尚待执行，状态为 `APPLIED / LIVE_RETEST_PENDING`。没有安装角色、没有联系来源窗口、没有修改来源产品。

来源记录出现新动作、平台路径或工具能力改变、共享记录与实际文件不符、目录迁移或规则版本变化时重新核验。不要把本次尚未安装的截点永久当作所有设备的安装结论，也不要把本次失败推导成所有总指挥必然失败。
