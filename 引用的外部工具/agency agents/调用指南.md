# Agency Agents 调用指南（AI 内部）

## 1. 它到底是什么

Agency Agents 是 GitHub 上的一组专业角色提示词。每个角色文件都描述一种工作方式，例如 Game Designer、Level Designer、UI Designer 或 Technical Artist。把一个角色文件交给现有 AI，等于请它用这个角色的检查清单重新看一遍材料。

它本身不提供新的模型，也不会自动读取我们的项目。它不会因为装过一次就自动参与所有对话，更不会自动接管总指挥权限。

## 2. 它和我们当前工作流怎么分工

用三层记忆最容易理解：

| 谁 | 负责什么 |
| --- | --- |
| 共享库维护者 | 记录来源、版本、共享安装范围、更新方式和安全边界。只有目标路径与动作已获授权时才安装或升级；本仓库中央登记由唯一维护者写入。 |
| 项目总指挥 | 判断适用性，先覆盖相关职责，再选本阶段角色，填写激活卡，决定是否继续。 |
| 专项任务 / 执行 AI | 在激活卡及主任务允许的范围内按阶段辅助规划、实现或审查并交付证据。不因角色获得安装、扩权或通信许可。 |

因此，操作者不需要记住每个角色的细节。你只需要把需求告诉项目总指挥；项目总指挥再根据这份目录选择角色。

## 2.1 提示词怎样组合

操作者不需要把两段提示词手工拼接。项目总指挥在内部生成一份组合后的执行契约，顺序固定为：

1. 总指挥工作流的安全、权限和停止规则；
2. 当前项目规则和专项任务边界；
3. 已核验的 Agency Agents 角色职责；
4. 本次目标、输入材料、输出格式和验收标准。

角色提示词只提供专业视角，不能覆盖前面的权限、隐私、单写者、远端写入或人工验收规则。发生冲突时，以项目规则和总指挥工作流为准。执行 AI 只接收总指挥生成的组合契约，不要求操作者转发原始角色文件。

## 3. 什么时候适合用

适合的情况（具体前置条件随用途核对）：

- 需要专业方法辅助规划、设计或已授权实现；早期可用目标与需求记录作为基线，不强制先有可运行产品。
- 已有可评审材料，需要专业角度检查遗漏；正式审查先固定该次输入基线。
- 角色的输入、输出和停止条件可以写清楚。
- 这轮工作可以先只读，结果能和现有方案逐项对照。

不适合的情况：

- 关键目标或权限不足以支持本次调用；只暂停依赖缺口的动作，仍可只读盘点职责和候选。
- 正在处理 Goal 中断、交接冲突或中央状态不一致。先恢复主任务状态，再考虑角色审查。
- 想靠“多装几个角色”代替需求、试玩、测试或人工验收。

首次试验可选一个当前角色做有限只读审查，但职责分析须覆盖整个目标。长期专业职责按共同规范第5节保留，调用与预算有界；已有实现授权时角色可辅助实现，不因首次只读永久禁用实现。没有新增价值则结束对应试验，不机械撤销其他适配职责。

## 4. 怎么接入

### 第一步：先确认是否已经安装

先按 [`外部工具自动对接规范.md`](../外部工具自动对接规范.md) 从规则来源定位本目录，读取 [`角色共享状态.json`](../角色共享状态.json) 与 [`安装与维护记录.md`](安装与维护记录.md)。正式来源已登记为 <https://github.com/msitarzewski/agency-agents>；不得让操作者重新提供地址或凭技能目录搜索判断来源未知。记录是 `NOT_INSTALLED` 时，仍可核对上游实际角色目录、形成适配与安装候选，不假装角色已经可用。

当前有两种技术路径：

1. **共享安装（本工作流默认）**：只把选定角色存入共享状态声明的 `<USER_CODEX_HOME>/agents`，现场核对上游转换方式、实际路径、版本和回滚。写入用户目录需覆盖精确路径与动作的授权；当前安装事实以共享登记、维护记录及实物核验为准。不得直接运行第三方批量脚本，把全部角色都装进共享目录。
2. **项目范围安装（例外）**：项目隔离要求或平台不支持共享时才提出候选；先核对可复用的共享版本，说明偏离默认的原因、版本与清理方式。例外不改写全局共享状态为已安装，也不让其他项目误用这份局部副本。

不要把“能访问 GitHub”理解成“已经安装”。没有安装记录、角色文件和版本证据时，状态写 `UNKNOWN` 或 `NOT_INSTALLED`。

### 第二步：覆盖职责并选择本阶段角色

按共同规范第2.1节先区分当前需要、后续可用和无需职责，再从实际文件中选择候选。游戏相关目标检查策划、关卡、工程、界面、技术美术及测试；不机械固定六角色，也不泛读全库。Game Designer可做首轮玩法检查，Level Designer用于关卡，UI Designer用于界面，Technical Artist用于美术管线；Code Reviewer不能冒充专门引擎工程师，缺适配角色时说明能力缺口。对抗式遗漏检查、关键追问及独立审查按共同规范执行，少量调用不缩窄需求。

### 第三步：填写角色激活卡

由 AI 按 [`角色激活卡模板.md`](角色激活卡模板.md) 在既有获准私有记录中预填来源、版本、目标、材料、权限、预算、停止条件和证据位置，并保存 `external_role_binding` 指针。绑定状态与本轮结果分别登记。安装及本次使用已获授权时，连续执行后续步骤，不要求用户再发激活提示词。

### 第四步：记录消费，再把卡和材料交给执行 AI

按共同规范第5.1节开始前持久化并回读一次消费、状态、基线、原开始时间和恢复锚点；不能完成后才计数。执行AI只加载本阶段获准角色和材料，中断沿同次续写不新领预算。规划或已授权实现按主任务交付成果与验证证据；补充审查在输出中分开写：

- 与基线重复的内容；
- 新增且有证据的发现；
- 最小验证办法；
- 额外时间或额度成本；
- 未能验证的部分。

没有真实试玩观察时，角色只能评价设计和证据缺口，不能声称玩家体验已经改善。

### 第五步：回读结果并决定是否继续

执行AI回读输出并与该次基线逐项对照；专项按有序任务卡在原授权内继续规划、实现和验证，不每次等待中央发卡，必要里程碑、终点和例外由项目总指挥核账。补充审查没有新增价值时结束对应试验：未开始才标记 `SKIPPED`，已开始按实际结果登记 `COMPLETED / BLOCKED`，无新增价值也保留消费。角色绑定转为 `IDLE` 待命，保留累计轮次和成本；同任务恢复按共同规范第5节读取绑定，未完成部分从断点继续，已完成本轮不重跑。角色不改变目标、预算、停止条件、单写者或远端权限。

## 5. “自动接入”到底是什么意思

这里的自动接入包含正式发现、职责覆盖、共享复用、阶段选择和任务绑定。按共同规范第5节，在有序任务契约内自行触发当前角色，开批、里程碑/终点和例外汇报；中央暂停、人工验收及独立互审终点收口继续生效。普通/专项换窗与总指挥交接携带绑定指针，继任者自行加载核权；未经专项加载确认不称已迁移。安装与使用已授权时连续推进，不自动加载全部角色，不额外安装、写产品或通信；原生自动注册未验证时显式读取。

自然语言路由已由工作流的共同对接规范负责，不要求用户额外配置才能发现本工具。可选的个性化配置见 [`个性化配置建议.md`](个性化配置建议.md)，它不能代替正式登记或被当成必需前置；不要把几十个角色全文塞进个性化配置。

## 6. Goal 中断时怎么办

Agency Agents 和 Goal 是两件事。角色审查完成后，Goal 是否继续运行取决于 Goal 自己的状态：

1. 先查看项目总指挥记录中的目标、停止条件和当前状态。
2. 如果 Goal 因人工反馈暂停，按当前平台的 Goal 恢复操作继续；普通聊天消息只会处理这条消息，不一定会恢复长任务。
3. 恢复后先确认它从哪一个精确断点继续，再决定是否重新启用角色。

不要因为角色输出已返回，就把 Goal 误判为已经恢复或已经完成。

## 7. 常见错误

| 现象 | 正确处理 |
| --- | --- |
| 项目 AI 说“有 Agency Agents”，但拿不出角色文件和版本 | 标记 `UNKNOWN`，回到中央记录核验。 |
| 想一次装完全部角色 | 暂停，先说明范围和回滚成本，只安装当前需要的角色。 |
| 角色要求修改代码或联系其他任务 | 按项目权限拒绝越界动作，只保留允许的审查结果。 |
| 角色输出只是重复基线 | 结束试用，不把重复内容算成效果提升。 |
| Goal 收到人工反馈后停住 | 单独核对 Goal 状态并执行平台恢复操作，不把普通对话当作恢复命令。 |

## 8. 最小成功标准

一次 Agency Agents 试用至少应留下：

- 一份试用前基线；
- 角色来源和版本证据；
- 一张完成的激活卡；
- 角色逐项输出及证据；
- 与基线相比的新增价值判断；
- 未验证项、停止原因和下一步。

缺任何一项，都只能说“完成了部分审查”，不能说 Agency Agents 已经改善了项目。
